OpenKosmos Design System

The visual and component language shared by every brand of the OpenKosmos / PM Studio desktop app. This page is the design system rendered in the design system — every color, radius, shadow, font and button below is the real token, pulled from src/renderer/styles/globals.css.

00 · Architecture

What the design system actually is

It is not Tailwind and not a single component library. It is three layers plus a governance engine that keeps them honest:

LayerLives inRole
1 · Design tokens
source of truth		globals.css @theme + :rootEvery color, radius and font value. Nothing downstream invents its own.
2 · UI primitivessrc/renderer/components/ui/Hand-rolled, accessible building blocks (Dialog, Badge, Card…). They consume tokens, never raw values.
3 · Feature componentssrc/renderer/components/**The app. Composes primitives + token-backed utility classes.
Governance enginescripts/check-design-tokens.js + CI + lint + hooksA ratchet gate that lets drift only decrease, never grow.

Two — and only two — homes for a raw color

Every hex/oklch value in the renderer lives in exactly one of these. Everything else references it with var(--color-*) or a Tailwind palette utility.

A · The SSOT

globals.css — the @theme block (primitives that feed both the .tsx utilities and the .css var() layer from one declaration) plus the :root semantic tier.

B · The syntax registry

code-styles.css — the independent --syntax-* registry for code/markdown rendering, deliberately decoupled from the brand palette so highlighting never drifts on a rebrand.

Three small, policy-forced carve-outs (the screenshot window, the fatal-error fallback, a content-excluded file) are the only places a raw hex is allowed in .tsx — and they are bounded by their own ratchet so they can never grow.

02 · Components

Component system

Buttons — black / red / white

One button family (.btn-*), one box model (8×16 padding, radius-lg, weight 600, 12px, 32px min-height, centered flex). The palette is deliberately black, red, white; sky is not a button color.

ClassBackgroundUse
.btn-primarywarm-900 (black)the one primary / submit action
.btn-secondarywhite + form bordersecondary / cancel
.btn-dangerdanger-600 (red)destructive
.btn-ghosttransparentlow-emphasis tertiary
.btn-icon / .btn-closewhite / transparenticon-only affordances

The legacy .btn-dark and the old cva Button primitive were both consolidated into this family. Buttons are CSS classes, not a React variant component.

Badges

default accent success danger

Badge is the one primitive still built with class-variance-authority; its variants map to status / accent tokens.

Primitive library

~19 hand-rolled primitives in components/ui/. Hand-rolled is a deliberate choice (Radix was removed) — each owns its own accessibility (focus, escape, stacking).

Dialog

The single modal standard. Owns Escape, stacking, focus, close-context. All legacy .modal-* shells were retired onto it.

Card

The elevated-panel recipe: white, border-panel, radius-lg, panel shadow.

Badge

cva variant API; the reference pattern for any future variant primitive.

DropdownMenu

The single menu implementation (DropdownMenu.css).

03 · Visual language

Visual language

Derived from the two reference surfaces — the Agent page and the Settings page — and adopted as the project-wide visual system (the pre-auth Startup / Sign-in / Data-loading screens were conformed to it).

Type

The quick brown fox — system sans
--font-sans: -apple-system, BlinkMacSystemFont, 'Segoe UI', 'Roboto', sans-serif
const tokens = oklch(0.7 0.2 250); // mono
--font-mono: 'Cascadia Code', 'SF Mono', 'Consolas', 'Monaco', 'Menlo', monospace

Body uses font-variation-settings: 'opsz' 32. No web fonts ship — the OS UI font keeps the app native and instant.

Off-scale one-offs live in :root: --radius-scrollbar 3px, --radius-bubble 20px (message bubbles / glass cards), --radius-card-xl 36px (onboarding card). lg (8px) is the workhorse — panels, buttons, inputs.

Elevation

panel · .06

Soft, low-spread black shadows. Depth grows with blur, not darkness.

The shared skeleton

What makes Agent and Settings feel like one app:

  • Elevated-panel recipe — radius-lg + 1px border-panel + panel shadow. The Settings content container is the Agent sidepane.
  • Unified header — 64px tall, white, border-panel bottom, 17px / 650 title. Every sub-page header reuses it.
  • Left navigation — warm-50, the same class on both pages.
  • Hover / active — rgba(0,0,0,.05) wash, one menu implementation, shared form-* / tool-card / list-search recipes.
04 · Governance

Governance engine

The system stays consistent because a machine enforces it. scripts/check-design-tokens.js walks the whole renderer tree and counts ten drift metrics against a frozen baseline. Counts may only ratchet down — a PR that raises any metric fails.

Baseline string today: 0 / 67 / 0 / 0 / 0 / 0 / 0 / 92 / 0 / 0 (frozen in scripts/design-system-baseline.json). Adding a genuinely new token does not raise a drift baseline; token definitions live in the sanctioned globals.css SSOT region. Baselines only change when a drift metric drops, and they may only ratchet down.

Three enforcement points

CI gate always on

.github/workflows/pr-design-system.yml runs the gate on every PR, appends the report to the job summary, posts a sticky comment for same-repo PRs only, and fails the check on any increase. Fork PRs skip the sticky comment because their tokens may not have PR-comment write permission. Once the base branch has a baseline, it also compares the PR baseline against that base-branch baseline so a PR cannot raise its own ceiling.

Pre-push hook local · opt-in

Wire check:design as a native .git/hooks/pre-push hook to catch drift before it leaves your machine. Local-only (hook files can't be committed); each dev opts in.

ESLint rule editor

A no-restricted-syntax rule red-flags a raw hex literal in renderer source the moment you type it.

05 · Day-to-day

Using & verifying the system

How to build UI with it

Token-first. Pick the highest row that fits before you ever consider a literal value.

You need…Reach forExample
a color in .tsxTailwind palette utilitytext-primary-600, bg-warm-900, text-danger-600
a color in .cssvar(--color-*)color: var(--color-text-default)
a corner radiusrounded-* / var(--radius-*)rounded-lg, border-radius: var(--radius-lg)
a button.btn-* class<button class="btn-primary">
a modalthe Dialog primitive<Dialog>…</Dialog>
a variant APIcva (see Badge)badgeVariants({ variant })
a brand-new valueadd ONE token in globals.cssthen reference it everywhere; do not raise a drift baseline

Do

  • change a color in one place (the token), let it cascade
  • use the semantic tier before a primitive
  • compose existing primitives

Don't

  • write a raw #hex in renderer source
  • hand-roll a button or modal shell
  • add a baseline/allowlist entry to silence the gate

How a PR is verified

Three layers of defense — machine first, human second, docs as the contract.

  1. Machine gate (automatic). CI runs check:design over the whole tree, fails on any metric increase, and once the base branch has a baseline rejects PR baseline increases relative to it; the optional local pre-push hook catches local metric increases earlier; the ESLint rule catches raw hex in the editor. Run it yourself with npm run check:design.
  2. Human review (the gate's blind spots). The gate counts drift vectors; a reviewer still checks semantic misuse (success-green for a destructive action), hand-rolled buttons/modals, spacing rhythm, contrast (body text ≥ 4.5:1), and accessibility.
  3. Docs as contract. ai.prompt/design-system.md and components/ui/ai.prompt.md describe intent; when a change adds a token or shifts a rule, the same PR updates them. Re-freeze the baseline only when a measured drift count drops.

The one-line check

npm run check:design → expect Design system check passed with the baseline 0 / 68 / 0 / 0 / 0 / 0 / 0 / 93 / 0. If it fails, it tells you exactly which metric grew and in which file.
