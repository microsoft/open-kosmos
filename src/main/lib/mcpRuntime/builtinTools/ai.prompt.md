## Architecture

**Registration vs. Execution split:** `initialize()` populates a `Map<string, BuiltinToolDefinition>` with tool *metadata only*. Heavy tools store their `inputSchema` inline at registration time or in a lightweight definition module, but do not import the implementation module. `executeTool()` is where modules are actually imported.

**Two loading tiers:**
- **Eager** (top-level imports): `read_file`, `write_file`, `search_file_contents`, `search_files`, `execute_command`, `get_current_datetime`, `request_interactive_input`, `search_skills`, facade tools (`manage_mcp`, `manage_agents`, `manage_skills`, `manage_hooks`), scheduler tools, `memex_memory` (**per-profile `memex.enabled` switch**).
- **Lazy** (`await import(...)` inside `executeTool`): `bing_web_search`, `bing_image_search`, `fetch_web_content`, `read_office_file`, `download_file`, `manage_process`, sub-agent tools, and `browser` (the embedded browser automation tool; lazy keeps the Electron `WebContentsView`/`debugger` dependency out of the static import graph).

**Local file move independence:** `move_file` is a provider-neutral filesystem capability used for local generated-file and workspace workflows. It does not depend on the retired Browser Control distribution or on the current embedded-browser tool, so `browser.enabled` must not hide or block it.

**Execution context:** `AgentChat` calls `BuiltinToolsManager.setExecutionContext()` before `executeTool()` and clears it after. `BuiltinMcpClient` captures that context before any await and passes the immutable snapshot into `BuiltinToolsManager.executeTool()`. `memex_memory` must use this captured snapshot for `userAlias`/`chatId`: current-agent scope resolves `getChatPrimaryAgent(chatConfig)` once and derives that same primary agent's id with `agentIdOf(...)` to open `agents/<agentId>/memory`, while profile-memory scope uses only `userAlias` to open `profile-memory`. For `capture`, the dispatcher additionally builds a `MemexCaptureSourceContext` from the same immutable snapshot and same primary agent (chat-session path, deliverables path, latest persisted user message id, save barrier, primary agent knowledge root, source-agent id/name, and sub-agent flag) and calls `executeDetailed()` so changed-write metadata is preserved. This prevents concurrent sessions from overwriting the mutable static context between async boundaries and prevents validating capture evidence against one agent while writing another agent's memory. `manage_hooks` also uses the captured `userAlias` for both the `hooksEnabled` gate and facade CRUD so a delayed tool call cannot validate against one profile and write another. `coding_agent` uses the same captured alias for the master-switch gate and CLI selection, and emits initial/heartbeat partial chunks through the captured `eventSender`/tool-call IDs instead of re-reading mutable static context after spawn. `create_schedule` consumes the same captured snapshot when defaulting to the current agent identity. `sub_agent` now also receives this captured snapshot from the dispatcher so foreground progress/cancellation wiring cannot be lost if the mutable static context is cleared or overwritten during the lazy import; `get_subagent_status`, `notify_parent`, and `send_to_subagent` still read the static context directly because they are existing role/context-gated tools.

**`tool_search` session-bound context:** `tool_search` receives its `chatSessionId` as an explicit parameter threaded from `builtinMcpClient.executeTool()` (captured before the `await getToolsManager()` async boundary) through `builtinToolsManager.executeTool()` into `ToolSearchTool.execute()`. This avoids reading the mutable static `currentExecutionContext` after an async gap where a concurrent session could overwrite it. The deferred tools list is stored in a per-session `deferredToolsContextMap` keyed by `chatSessionId`, set/cleared by `agentChatStreamingService`. `getDeferredToolsContext(sessionId)` is fail-closed: returns `null` when `sessionId` is absent (no fallback). Cleanup happens in `agentChatManager` when a session is disposed via `BuiltinToolsManager.clearDeferredToolsContext(chatSessionId)`.


**`browser` tool gate (per-profile switch, not a feature flag):** The `browser` tool is gated by the persisted `browser.enabled` field in `profile.json` (read synchronously via `profileCacheManager.getBrowserSettings(alias).enabled`, default **false**), toggled by users from **Settings → Browser**. `initialize()` always registers the metadata so the singleton does not need to be rebuilt after a settings change. Public inventory accessors (`getAllTools`, `getAllToolsInfo`, `getOpenAIToolDefinitions`, `getToolInfo`, `getStats`) hide it while disabled and expose it immediately when enabled; `hasTool()` still reports registered-tool existence so stale calls through `BuiltinMcpClient` can reach `executeTool()` and receive the recoverable disabled error `browser tool is disabled (enable it in Settings → Browser)` when off.

**`coding_agent` tool gate (profile-level master switch).** The tool is gated **solely** by a profile-level **user** switch: `codingAgentSettings.enabled` in profile.json (default **false**), toggled from **Settings → Coding CLI**. Registration is **unconditional** (the metadata is always added in `initialize()`, mirroring `browser`), so a mid-session enable needs no restart. `isCodingAgentEnabledForProfile(alias)` reads the switch; `shouldExposeTool('coding_agent')` returns it, so the tool is hidden from `getAllTools`/`getAllToolsInfo`/`getOpenAIToolDefinitions`/`getStats` while off. `executeTool` is fail-safe: master switch off → `coding_agent tool is disabled (enable it in Settings → Coding CLI)`; else delegate. This mirrors the profile-level `manage_hooks` precedent (`isHooksEnabledForProfile`); the settings view calls `mcpClientCacheManager.refresh()` after a successful toggle so the renderer tool list updates without a chat switch. The global system prompt section is gated by the **same** master switch (read via `profileCacheManager.getCodingAgentSettings(alias).enabled`), so the model is only told about `coding_agent` when the tool is exposed.

**`manage_hooks` tool gate (Hooks master switch):** The `manage_hooks` metadata is registered once, but public inventory accessors hide it while the active profile's `hooksEnabled` is false. Execution-time stale calls use the captured per-call user alias when available; the same alias is passed into `ManageHooksFacade.execute(...)`, so gate and CRUD cannot drift across profile switches. Calls without an enabled Hooks profile return a recoverable disabled error instead of executing. The facade intentionally does not include a `set_master_switch` action; the profile-level switch stays in user-facing Settings because Hooks are persistent command/HTTP execution.


**Return format:** `executeTool()` always returns `ToolExecutionResult`. On success `data` is `JSON.stringify(result)`. Errors are caught and returned as `{ success: false, error: message }` — they do NOT throw.

### Cancellation / AbortSignal Contract

All built-in tools that perform network I/O **must** honor an `AbortSignal`. When the user cancels a chat session, the agent framework terminates the executing tool via `AbortController.abort()`.

**1. Tool handler signature convention:**
```typescript
// Network I/O tools — must accept signal
static async execute(args: MyToolArgs, options?: { signal?: AbortSignal }): Promise<Result>

// Pure local tools (read_file, write_file, etc.) — no signal required
static async execute(args: MyToolArgs): Promise<Result>
```

**2. Signal propagation chain (every layer must pass it through; no gaps):**
```
AgentChatToolExecutor (creates AbortController, listens to CancellationToken)
  → mcpClientManager.executeTool({ signal })
    → BuiltinMcpClient.executeTool({ signal })
      → BuiltinToolsManager.executeTool(name, args, signal)
        → Tool.execute(args, { signal })
          → provider client request / fetch(url, { signal })
```

**3. Merging signal with an internal timeout:**
When a method already has an internal timeout `AbortController`, merge it with the external signal:
```typescript
const timeoutController = new AbortController();
const timeoutId = setTimeout(() => timeoutController.abort(), TIMEOUT_MS);
const mergedSignal = signal
  ? AbortSignal.any([signal, timeoutController.signal])
  : timeoutController.signal;
const response = await fetch(url, { signal: mergedSignal });
clearTimeout(timeoutId);
```
In the `AbortError` catch, use `signal?.aborted` to distinguish external cancellation from an internal timeout.

**4. Playwright tools — special handling:**
Playwright does not support `AbortSignal`. Use a signal listener + `page.close()` to implement cancellation:
```typescript
const onAbort = () => page?.close().catch(() => {});
signal?.addEventListener('abort', onAbort, { once: true });
try { /* page operations */ }
finally { signal?.removeEventListener('abort', onAbort); }
```

**5. New tool development checklist:**
- [ ] Does the tool perform network I/O? → Must accept `{ signal?: AbortSignal }`
- [ ] Is the signal passed all the way down to the final `fetch` / HTTP call?
- [ ] Does the `if-else` branch in `builtinToolsManager.executeTool` pass `{ signal }`?
- [ ] For multiple network calls (loops, `Promise.all`), is the signal passed to each call?

## Anti-Patterns
- Do NOT add a new tool only in `initialize()` and forget the `else if` branch in `executeTool()` — it will silently throw "Execution not implemented".
- Do NOT import Playwright, mammoth, or other heavy modules at the top of the file — use lazy `await import()` inside the `executeTool` branch.
- Do NOT call `executeTool()` and assume a thrown exception — it always returns `ToolExecutionResult`; check `result.success` instead.
- Do NOT re-read `currentExecutionContext` after an async boundary for per-agent identity. Capture before the boundary and pass the snapshot explicitly (as `memex_memory`, `manage_hooks`, and `create_schedule` do), otherwise concurrent sessions can route work to the wrong agent or profile. For `memex_memory capture`, also preserve the detailed result path; using the compatibility `execute()` path drops write metadata and must reject capture.
- Do NOT let `inputSchema` and the tool's TypeScript args interface drift — the LLM sends args matching the schema but the implementation reads them by interface field names.
- Do NOT swallow `AbortSignal`. `BuiltinMcpClient.executeTool` passes `signal` through `BuiltinToolsManager` to each tool handler. All network-IO tools **must** propagate it to their final `fetch()` / HTTP calls. Missing signal causes cancel to hang for the full request timeout (30-60s), blocking the user from sending new messages. (See: v2.7.x cancel-blocks-send bug.)
- `execute_command` has **no fixed execution-duration cap** — it relies on the central 10-min no-response watchdog in `AgentChatToolExecutor`. Each stdout/stderr chunk must keep calling the captured `executionContext.reportActivity()` (that is what resets the budget), and the tool must keep honoring `options.signal` (the watchdog aborts the signal; it does NOT invoke the tool's `registerCancellationHandler`). Do not reread `BuiltinToolsManager.getExecutionContext()` inside this tool for watchdog activity; concurrent sessions can otherwise reset the wrong timer. A consequence to keep in mind: a command that runs long while producing **no output** (e.g. `sleep 600`) is intentionally killed at 10 min. Interactive-auth commands are the lone exception — a 60s `reportActivity` keepalive pins the watchdog for their bounded 15-min window so a silent browser-wait is not cut off. Full rationale in [../ai.prompt.md](../ai.prompt.md) "Time constraints".
- `execute_command` is also the chat-facing recovery layer for app-managed Python. In internal runtime mode, Python/pip commands (`python`, `python3`, `pip`, `pip3`, `uv pip`) must wait for runtime shims before execution. If a foreground Python/pip command exits with `No module named pip`, the tool may call `RuntimeManager.ensurePythonPipAvailable()` and retry the original command exactly once. Do not replace this with hidden loops or `ensurepip`; venv repair belongs in RuntimeManager and uses `uv pip --python <venvPython>` to preserve user packages. See [Postmortem: app-managed Python venv missing pip](../../../../../ai.prompt/postmortem-app-managed-python-pip-unavailable.md).
- Foreground `sub_agent` calls must use the captured per-call `executionContext` passed by `builtinToolsManager.ts`, pass child progress to `context.reportActivity()`, proxy child `eventSender.send`, bind all proxied WebContents methods to the original sender, and link `options.signal` into the child cancellation token. The parent tool is also builtin-watchdoged, so a `no_auto_promote` child that streams or reports steps for more than 10 minutes must reset the parent watchdog, while a silent child that times out must be cancelled instead of continuing in the background. Do not reread `BuiltinToolsManager.getExecutionContext()` after the dispatcher's lazy import; concurrent tool calls can clear or overwrite the mutable static context.
- `download_file` streams the HTTP response body to a same-directory temp file chunk-by-chunk and is builtin-watchdoged, so it must call the captured `executionContext.reportActivity()` on **each** received chunk; otherwise a slow-but-still-progressing transfer is mistaken for "no response" and aborted at the 10-min idle budget. It receives the captured per-call context from `builtinToolsManager.ts` (`DownloadFileTool.execute(args, { signal, executionContext: callExecutionContext })`); do not reread `getExecutionContext()` inside the tool. The fixed 30s `fetch` timeout only bounds the initial request/headers, not the body transfer. On success the temp file is renamed to the final path; on any mid-stream error or abort the tool **tears down the write stream (`destroy()`) and unlinks only the temp partial file** so a corrupt leftover cannot block a later retry and an existing `overwrite=true` target is not deleted before a successful replacement. A pre-stream failure (e.g. existing file with `overwrite=false`) leaves the user's file untouched because the partial path is only tracked once the temp write stream is created.
- `bing_web_search` / `bing_image_search` are builtin-watchdoged and run multiple queries with bounded concurrency (`QUERY_CONCURRENCY = 2`), so each tool threads the captured `executionContext.reportActivity` from `builtinToolsManager.ts` (`execute(args, { signal, executionContext: callExecutionContext })`) and calls it in the **settle-`finally`** of every query — each completed query (success **or** failure) is genuine progress that resets the 10-min idle budget. Without this the unified watchdog degenerates into an effective total cap and a slow-but-advancing multi-query search is wrongly idle-killed at 10 min. The fixed 60s `page.goto` timeout only bounds a **single** navigation (fail-fast on a dead endpoint), not the whole call. Do not reread `getExecutionContext()` inside the tool; use the per-call context passed by the dispatcher (the two Bing tools are copy-paste siblings — keep the wiring identical).

## Gotchas
- ⚠️ **`manage_agents action=update` is additive by default for `mcp_servers`, `skills`, and `hooks`.** Passing `mcp_servers:["x"]` adds `x` to the agent's existing servers. To overwrite, pass `mcp_servers_mode:"replace"` (same for `skills_mode` / `hooks_mode`). The merge/replace decision lives in `updateAgentTool.ts` itself, so direct `update_agent` MCP calls are protected too.
- ⚠️ **Agent-management tools must not expose agent-owned `workspace`.** Chat workspace is derived from `{profile}/chat_workspaces/{chat_id}`. `manage_agents`, `create_agent_from_config`, and `update_agent` reject `workspace` instead of silently accepting a no-op. For multi-agent chats, list/status/set_primary/update must scan `getChatAgents(chat)` so secondary agents are visible and updateable.
- ⚠️ **Schema/interface mismatch is silent.** The CRITICAL CHECKLIST comment at line ~292 of the manager is there for this reason — always verify param names, types, and required fields match between the inline `inputSchema` and the tool's TypeScript interface.
- ⚠️ **Lazy tools have first-call latency.** Playwright-dependent tools import the entire browser automation stack on first call; this can take 1–2 s on a cold start.
- ⚠️ **`manage_process` is eager in registration but lazy in execution** (to avoid `ipcMain` side effects in Jest). This is an exception to the normal pattern.
- ⚠️ **`resetInstance()` exists for tests only.** Do not call it in production code — it destroys the singleton and all registered tool metadata.
- ⚠️ **`bing_image_search` / `bing_web_search` must run queries on ONE shared browser with a fresh per-query `newContext()` and bounded concurrency — never unbounded parallel with a shared state file.** The original code ran `args.queries.map(performSingle)` + `Promise.allSettled` (one full Chromium per query) and every query read/wrote/deleted ONE hardcoded `storageState` file in `os.tmpdir()`. The same-IP burst tripped Bing anti-bot degraded pages and the state-file race tore cookies, so exactly one query returned a full grid and the rest each returned exactly 1 junk result (aggregated output was all-junk). Current model: launch one browser in `execute()`, run queries via the inline `runWithConcurrency` pool (`QUERY_CONCURRENCY = 2`), give each query a fresh isolated `browser.newContext()` with **no** `storageState`, and retry once when a query yields 0 results, or 1 result when `maxResults` allows more. Do NOT reintroduce a persisted browser-state file or unbounded parallelism. The two `addInitScript` callbacks are browser-serialized and cannot run under Vitest, so they are wrapped in `/* v8 ignore start/stop */`. See [Postmortem: Bing image/web search returns irrelevant or zero aggregated results](../../../../../ai.prompt/postmortem-bing-search-parallel-degradation.md).
- ⚠️ **`coding_agent` CLI detection (`pickBestCliPath` in `codingCli/registry.ts`) returns only a standalone, launchable path on Windows.** `where copilot` (and other CLIs) lists every PATH match including (a) extension-less POSIX wrappers and (b) the VS Code Copilot Chat extension's bundled copy under `globalStorage\github.copilot-chat\copilotCli`, both of which the integrated-terminal PATH injects ahead of a real npm-global install. Detection **excludes any `\globalStorage\` path outright** (the editor-bundled copy is private to the extension and must never be driven by OpenKosmos) **and** drops every candidate without a `.exe/.cmd/.bat/.com` extension (an extension-less wrapper cannot be spawned and fails mid-execution with the cryptic `"The system cannot find the file specified."` ENOENT). When nothing survives both filters it returns `null`, so the tool surfaces the actionable `not found. Install with: npm install -g @github/copilot` message. **Restart the dev process after changing this — a stale `npm run dev` main process keeps the old detection and will still pick the editor-bundled copy.**
