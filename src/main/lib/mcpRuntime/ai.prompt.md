## Architecture

```
AgentChat.executeToolCall()
        │
        ▼
MCPClientManager.executeTool(toolName, toolArgs)
        │
        ├─ toolToServerMap lookup
        │
        ├─── serverName == "builtin-tools" ──► BuiltinMcpClient ──► BuiltinToolsManager
        │                                                           │
        │                                                  (eager) lightweight tools
        │                                                  (lazy)  playwright / mammoth / external tools
        │
        └─── serverName == external ──► VscMcpClient
                                              │
                                    ┌─────────┼─────────┐
                                  stdio      SSE       HTTP
                               (child proc) (remote) (streamable)
```

**Tool routing:** On server connect, `MCPClientManager` fetches the tool list and populates `toolToServerMap` (`Map<toolName, serverName>`). At call time, it looks up the server, finds the right client instance, and delegates. Agent-scoped calls normally prefer the provided server names and then fall back to the global map for main-agent compatibility; calls with `strictAgentMcpServerNames: true` never fall back outside the provided scope. Sub-agent execution uses strict mode to enforce its narrowed MCP allowlist.

**All transports use VscMcpClient.** The original `MCPClient` (MCP SDK) is disabled (`// 🚫 MCPClient (SDK) disabled` at line 1 of `mcpClientManager.ts`). `defaultImplementation` is hardcoded to `'vscodeMcpClient'`.

**Time constraints (`toolTimeoutPolicy.ts`).** Two unified metrics replace the old ad-hoc per-call timeouts. The connection budget is external-MCP-only; the no-response budget is applied to **every builtin tool** (centrally) and to external MCP `tools/call` (inside the MCP client):

1. **Connection budget (5 min).** `VscodeMcpClient.connect()` races its three serial steps — transport `start` → `initialize` handshake → required `tools/list` — against `MCP_CONNECT_TIMEOUT_MS`. The `initialize` handshake and connect-time `tools/list` otherwise have no per-request timeout, so without the outer budget a misbehaving server can hang the UI in `connecting` forever; `tools/list` errors are fatal because a server without discoverable tools is not usable. Any failed connect attempt rejects in-flight requests, `await`s `transport.stop()` to kill the child process, clears the transient transport/tool/resource state, and then sets state `error` (UI maps `connecting` → `error`); timeout failures surface `ConnectionTimeoutError`. Note `transport.start` itself is process spawn / socket open and is *inside* the raced budget — there is no separate uncapped "process launch" phase. `resources/list` is deliberately outside the connect budget: it runs after `running` as a non-fatal fixed-timeout control request so a server with usable tools is not rejected because resource discovery is slow or unsupported.
2. **Idle / no-response budget (10 min).** No tool has a fixed total-duration cap; a tool is force-terminated only after `TOOL_IDLE_TIMEOUT_MS` elapse with no activity. There are **two enforcement sites**, never both on the same call:
   - **External MCP `tools/call`** is watched inside `VscodeMcpClient`: the previous hardcoded 1-hour `timeout: 3600000` no longer governs execution. Each tool call sends a unique MCP `_meta.progressToken`; only that request's JSON-RPC response or a `notifications/progress` event with the matching token re-arms the per-call `InactivityTimer`, so concurrent server traffic cannot keep a different silent tool alive. **A single idle timeout fails ONLY that request** — `handleRequestIdleTimeout` rejects the one timed-out request with `ToolIdleTimeoutError`, sends a best-effort `notifications/cancelled`, and **keeps the transport** so other in-flight and future tool calls on the same healthy server still work. Only **`IDLE_TIMEOUT_ESCALATION_THRESHOLD` (3) consecutive** idle timeouts within `IDLE_TIMEOUT_ESCALATION_WINDOW_MS` (30 min) escalate to a full connection reset (`failConnection`), which stops/clears the transport and sets state `error` (→ auto-reconnect). Any matched response resets the consecutive counter. `VscMcpClient` re-emits that `stateChange`, and `MCPClientManager` treats `error` as authoritative by clearing the server's tools and `toolToServerMap` entries while setting runtime status `error`. Short non-connect control requests (`resources/*`) keep a fixed, config-independent `MCP_CONTROL_REQUEST_TIMEOUT_MS` timeout via `sendRequestTracked({ deadline: { kind: 'fixed' } })`; `tools/call` uses `{ kind: 'idle' }`.
   - **Builtin tools** are watched by the active agent path: `AgentChatToolExecutor.executeToolCall` on the main-agent path and `SubAgentToolExecutor.executeToolWithIdleWatchdog` on the sub-agent path. Each path owns a per-call `AbortController`, arms an `InactivityTimer(TOOL_IDLE_TIMEOUT_MS)` **iff** `mcpClientManager.isBuiltinTool(name, agentMcpServerNames) && !SELF_MANAGED_IDLE_TOOLS.has(name)`, injects `reportActivity` into the `ToolExecutionContext`, and races the tool's promise against an idle-rejection promise. The main-agent path passes the same agent-scoped server list to `isBuiltinTool` and `executeTool`, so an external MCP tool selected by agent scope is not accidentally watched as builtin when the global fallback map has a colliding builtin name. Built-in tools that depend on identity must use the captured context; for example, `memex_memory` uses captured `userAlias`/`chatId`, resolving the primary agent once for `scope:'current-agent'` and using profile-scoped storage for `scope:'profile-memory'`. It forwards `isSubAgent` for every Memex call so sub-agents remain read-only (`capture` and `archive` are rejected), while parent-chat `capture` also uses captured chat-session provenance (`chatSessionFilePath`, deliverables root, current persisted user message id, save barrier, primary-agent knowledge root, source-agent id/name, and `isSubAgent`) and must run through the detailed result path so durable-write metadata drives `cardsChanged`. The sub-agent path additionally passes `strictAgentMcpServerNames: true`, so a child can execute only builtin tools or the explicit external server/tool subset granted at spawn time. On idle it both `abortController.abort(new ToolIdleTimeoutError(...))` (so signal-aware tools tear down) **and** rejects the race (so the loop unblocks even if a tool ignores the signal); the timer is disposed in `finally`. External MCP tools are deliberately **not** gated here — they self-manage their idle budget and never call `reportActivity`, so double-watching would false-kill a streaming MCP server at 10 min.
   - **`reportActivity` must reflect real downstream activity only** (a streamed output chunk, an inbound server message) — never a synthetic UI heartbeat, or a hung tool emitting a periodic "still working" ping would never be killed.
   - **No builtin tool exposes an agent-facing timeout parameter.** `execute_command` and `coding_agent` omit `timeoutSeconds`; web search and fetch tools omit `timeout`/`timeoutSeconds`. Internal navigation and HTTP constants may still fail fast on dead endpoints, while the unified 10-minute no-response budget governs overall tool activity.
   - **`coding_agent` is in `SELF_MANAGED_IDLE_TOOLS`** (exempt from the path watchdogs). It **no longer accepts any agent-facing timeout argument**; `codingAgentTool.executeViaSpawn` arms its own `InactivityTimer` fixed at `TOOL_IDLE_TIMEOUT_MS`, re-armed by each `child.stdout`/`child.stderr` chunk; SIGKILL + `timedOut: true` fire only after the budget elapses with no output, and it already honors the external `signal`. It stays self-managed because `coding_agent` runs on both the main-agent and sub-agent paths; arming a path watchdog on top of the intrinsic one would double-watch the same call. Its 5-second UI heartbeat is outbound-only and does **not** reset the watchdog.
   - **`execute_command` is migrated** off its fixed `60s` / `15-min` total cap onto the central watchdog and **no longer accepts a `timeoutSeconds` argument**. The terminal's own `timeoutMs` is set to a far `NO_RESPONSE_BACKSTOP_MS` (24 h) for ordinary commands — a runaway-terminal backstop, not a practical limit — and each `stdout`/`stderr` chunk calls the **captured** `executionContext.reportActivity()` passed through `BuiltinToolsManager.executeTool()` (not the mutable global context). The tool now also **honors `options.signal`**: on abort (idle watchdog *or* user cancel) it stops the terminal, because it otherwise only tears down via its `registerCancellationHandler` (which the watchdog never invokes). Interactive-auth commands (`gh auth login`, etc.) keep their bounded 15-min terminal window **and** a 60-second `reportActivity` keepalive so a silent browser-wait is not mistaken for "no response"; the keepalive interval is cleared in `finally`.
   - **`sub_agent` forwards foreground child progress** to the parent tool's `reportActivity()`: the dispatcher passes the captured per-call `executionContext` into `SubAgentTool.execute()` so the bridge cannot lose progress/cancellation wiring if the mutable static context is cleared or overwritten during lazy import. Existing turn-completion progress is passed through `onProgress`, and the child `eventSender` is proxied so state/step updates sent through the normal renderer channel also reset the parent watchdog. It also links the watchdog `AbortSignal` into a child `CancellationTokenSource` for foreground ad-hoc runs, so a parent idle timeout actually cancels the child run. Without this bridge, a `no_auto_promote` foreground child that is actively reporting steps but takes longer than 10 minutes could be false-killed by the parent `sub_agent` watchdog, or a silent child could keep running after the parent timed out.

**Online auth retry:** HTTP/SSE transports include a first-phase OAuth bridge for protected online MCP servers. On `401/403`, the transport parses `WWW-Authenticate`, discovers OAuth metadata via `McpAuthMetadataService`, and asks `McpAuthService.getTokenForServer` for a Bearer token before retrying. The auth service routes by issuer:

Every issuer flows through `OpenKosmosOAuthProvider`, which implements the MCP SDK's `OAuthClientProvider` against `OpenKosmosTokenCache.mcpOAuth`. The flow uses standard PKCE Authorization-Code grant, supports Dynamic Client Registration (RFC 7591), and persists credentials in the profile-scoped cache. A local HTTP server (`CallbackServer`) listens on a per-server port, and concurrent calls for the same server are deduplicated by `getMcpOAuthServerKey`.

Renderer-side prompts (`requestConsent`, `requestClientIdFromUser`) are bounded by `MCP_AUTH_PROMPT_TIMEOUT_MS` (5 min, matching `CallbackServer.waitForCode`) and honor the caller's `AbortSignal` — without these the promise can hang forever if the renderer crashes, the user closes the window, or the upstream auth flow is cancelled. Timeout/abort resolves as `cancel`/`{ cancelled: true }` and propagates through the standard `MCP_AUTH_CANCELLED` path.

When an authorization server explicitly restricts DCR to approved partners (e.g. Lovable), `performOAuthFlow` throws `MCP_DCR_RESTRICTED` — this is a terminal error with no user action possible, surfaced via the connection failure toast. When an authorization server does not support DCR and the user has not pre-configured `oauth.clientId` in `.mcp.json`, `performOAuthFlow` throws `MCP_DCR_REQUIRES_USER_CLIENT_ID`. The auth service catches this, sends `mcpAuth:requestClientId` to the renderer, and the user is shown a dialog (`RequestOAuthClientIdDialog.tsx`) with provider-specific guidance (8 built-in catalog entries; plugin authors can override via `cfg.oauth.setupUrl/setupInstructions`). The supplied `clientId` (and optional secret) are persisted via the provider's `saveClientInformation` and the flow retries once.

**OAuth credential storage:** `OpenKosmosTokenCache.mcpOAuth` keys entries by `getMcpOAuthServerKey(name, cfg)` — a stable hash of name + transport + url + headers + oauth.clientId + callbackPort. Renaming a server, changing its URL, or adjusting auth-relevant headers automatically invalidates the slot. Token entries store accessToken/refreshToken/expiresAt/scope plus the (optional) clientId/clientSecret so DCR-issued credentials survive across sessions. The legacy cache filename remains profile-scoped under `{profile}/credentials/browserAuthTokenCache(.enc)` for backward-compatible local loading; old tenant fields are stripped and rewritten without network access. Deleting an MCP server calls `McpAuthService.clearOAuthForServer(name, cfg, 'all')` from `mcpClientManager.delete()`, which wipes the entire slot (tokens + DCR client info) so re-adding the same server later starts a clean OAuth flow rather than reusing stale credentials.

**Runtime state** (`MCPServerRuntimeState`: status, tools, lastError) is managed in-memory by MCPClientManager and pushed to the renderer via IPC on every change. It is never persisted to disk. Tool-list readers (`getAllTools()` and the `mcp:getServerStatus` IPC handler) refresh the built-in server's tool snapshot before reading runtime state so per-profile tool gates (for example Settings → Browser hiding/showing `browser`) update both the renderer-visible inventory and `toolToServerMap` without reconnect/restart. During MCP consent dispatch, the server temporarily enters `needs-user-interaction` so the renderer can show a sign-in-needed state while the consent dialog is open. If the user dismisses that dialog, the subsequent auth cancellation maps to `error` so the server does not remain stuck in a pending sign-in state.

**Server-readiness API (for consumers that must wait for connections).** `MCPClientManager` exposes an event-driven gate so callers can wait until external servers reach a stable state instead of racing the background connection sweep:
- `getInUseServerNames()` returns the currently bound profile's in-use external server names (excludes `builtin-tools`). A server counts as in-use unless `in_use === false`, so an `in_use` left `undefined` is treated as in-use — this mirrors `agentChatPromptService.getCurrentAvailableTools()` and `schedulerMcpReadiness.resolveSchedulerJobMcpServers()` semantics. Scheduler all-tools jobs derive wait targets from the resolved cached profile alias rather than this current-alias helper, so early cold-start scheduling does not depend on `MCPClientManager.initialize()` having already bound the alias.
- `waitForServersSettled(serverNames, timeoutMs)` delegates to `McpServerSettleWaiter`, which resolves once every named server is **settled** — has a status that is not `connecting`/`disconnecting` (i.e. `connected`/`error`/`disconnected`/`needs-user-interaction`) — or the timeout elapses. It filters out `builtin-tools` and empty names, returns immediately if the (filtered) set is empty or already all-settled, and otherwise registers a one-shot waiter. `_updateServerStatus` calls `settleWaiter.notify()` on every status change, which re-evaluates each waiter. The timeout timer is `unref()`-ed so it never keeps the process alive, and `settle()` is idempotent (clears the timer, removes the waiter, resolves once). This is the mechanism the **scheduler MCP-readiness preflight** uses to avoid running jobs with a partial toolset on cold start; if required servers remain disconnected, the scheduler creates a visible failed run instead of skipping silently (see [Scheduler](../scheduler/ai.prompt.md)). Note: settled does not mean healthy — `error`/`disconnected` count as settled, so callers that require a live connection must additionally check `getMcpServerRuntimeState(name).status === 'connected'`.

**Execution context injection:** Before dispatching a built-in tool call, `AgentChat` calls `BuiltinToolsManager.setExecutionContext()` (cleared after). `BuiltinMcpClient.executeTool()` must capture the full context before its first async boundary and pass that immutable snapshot into `BuiltinToolsManager.executeTool()`; tools that need per-agent or per-profile identity (notably `memex_memory`, `manage_hooks`, and `coding_agent`) must use the captured per-call snapshot, not re-read the mutable static context after awaits. It also captures the explicit `workspaceRoot` before any lazy-import await, resolving the workspace from `getChatWorkspace(chatConfig)` so workspace-confined tools (including embedded browser local-file actions) use the chat-owned working directory and do not re-read mutable static context after an async boundary. Never derive security roots from `process.cwd()` or from `agent.workspace`.

**Live command output:** `execute_command` can emit partial `tool_result` chunks while the process is still running. The final `tool_result` still represents command completion, but intermediate chunks can surface prompts such as device-login codes and URLs before the command exits.

**Interactive auth timeout:** `gh auth login`, `gh auth refresh`, `npm login`, `npm adduser`, `pnpm login`, and `yarn npm login` are detected as interactive auth commands (`isInteractiveAuthCommand`). The model can no longer set a timeout (there is no `timeoutSeconds` arg); instead these commands get a **fixed 15-minute terminal window** (`INTERACTIVE_AUTH_TIMEOUT_MS`) rather than the 24-hour `NO_RESPONSE_BACKSTOP_MS` used for ordinary commands, **and** a 60-second `reportActivity` keepalive (`INTERACTIVE_AUTH_KEEPALIVE_MS`) so the central 10-min no-response watchdog (`TOOL_IDLE_TIMEOUT_MS`) does not cut off a silent browser/device login. Ordinary commands carry no total cap and rely on the central watchdog alone.

**Interactive auth hints:** `execute_command` attaches structured auth metadata to partial/final tool results whenever one of the known interactive auth commands is running. The renderer uses that metadata to show a timeline-native auth card with verification link, copyable device code, a cancel action, and a live timeout countdown while still keeping raw terminal output visible below.

**Interactive auth interruption handling:** If an interactive auth command is canceled by the user or times out, `execute_command` sanitizes the terminal tool result before completion. Final results replace the stale device code / verification URL with a short restart-required message so ended auth sessions do not keep exposing expired credentials in the timeline.

**Agent knowledge persistence through built-in tools:** `update_agent` persists `agent_config.knowledge.knowledgeBase` as the renderer/main-process source of truth for profile-level knowledge settings. Retired tenant briefing sources are no longer part of the persisted agent knowledge contract and must not be written through `update_agent`.

## Gotchas

- **SDK client is permanently disabled.** Do not re-enable `mcpClient.ts` (MCPClient/SDK approach) without understanding why it was disabled — HTTP transport had a memory leak, and the VSCode client is now the sole implementation.
- **Agent tool prompts persist as file maps.** Built-in agent creation/update facades may accept legacy string `system_prompt` inputs from older callers, but must normalize them into `{ "Base.md": "...", "AGENTS.md": "" }` before writing profile data. Do not pass a raw object into chat prompt messages; rendering belongs in the chat prompt service.
- **`builtin-tools` is a reserved server name.** `BuiltinMcpClient` registers under the constant `BUILTIN_SERVER_NAME = 'builtin-tools'`. Never use this name for a user-configured MCP server.
- **Tool name collisions.** `toolToServerMap` is a flat `Map<toolName, serverName>`. If two servers expose identically named tools, the second connection silently overwrites the mapping. Ensure external server tool names do not clash with built-in tool names.
- **MCP `tools/call` is bounded by no-response time, not total time — and one idle timeout fails only the request, not the connection.** A server that keeps the call's no-response budget fresh stays alive indefinitely; one that goes silent for `TOOL_IDLE_TIMEOUT_MS` (10 min) has **that single request** rejected with `ToolIdleTimeoutError` plus a best-effort `notifications/cancelled`, while the transport stays up so other/future tool calls still work. The connection is only reset (`failConnection` → state `error` → auto-reconnect) after `IDLE_TIMEOUT_ESCALATION_THRESHOLD` (3) **consecutive** idle timeouts within `IDLE_TIMEOUT_ESCALATION_WINDOW_MS` (30 min); any matched response resets the counter. The idle countdown is reset by **exactly two** signals, both keyed so concurrent tool calls never reset each other's budget (`touchActivityForMessage`): (1) the **matching request's** response (keyed by JSON-RPC `id` via `requestActivityListeners`), and (2) a `notifications/progress` whose `progressToken` matches the one this call advertised (`tool-call-<requestId>`, via `progressActivityListeners`). Unrelated server traffic does **not** keep a silent call alive. Progress plumbing therefore **does** exist, but a server doing long work without emitting matching progress will still hit the idle cap — long-running tools should emit periodic progress to reset the watchdog. Do not reintroduce a fixed total-duration cap on `tools/call`, do not widen the reset to "any inbound message", and do not revert to killing the whole connection on the first idle timeout (one hung tool must not tear down a healthy server).
- **Lost-session JSON-RPC error responses must NOT be dropped — and a matched one is just as fatal.** In a prior MCP incident, the upstream proxy returned `{"error":{"code":-32001,"message":"Session not found"},"id":""}` with an **empty `id`**, which `handleMessage` treated as a notification and ignored, so the pending `tools/call` hung until the idle watchdog killed the whole connection 10 min later. Now `handleMessage` classifies **every** `message.error` via `classifyProtocolError` (in `mcpReconnectPolicy.ts`), whether it matched a pending request or not: a `connection-lost` error (`-32001` / "session not found|expired|closed") calls `failConnection` immediately (→ auto-reconnect), **regardless of the error's `id`** — including a **matched** error whose id echoes the in-flight request (otherwise a dead session would be left `running` and only the one request would fail). For an **unmatched** non-connection-lost error: an **id-less** (absent/empty) error with exactly one in-flight request rejects that request; a **concrete-id miss** is a stale/late reply for an already-settled call (e.g. one removed by the idle timeout) and is **logged only** — never reattributed to a different in-flight request, which would fail the WRONG tool call. For a **matched** non-connection-lost error, only that request is rejected (normal business error). Do not restore the old `else if (!message.id)` "treat as notification" path for **error** responses, do not widen the lone-request rejection to concrete-id misses, and do not revert matched lost-session errors to a single-request reject.
- **Manual ops supersede in-flight auto-reconnect — they do not throw.** `connect`/`disconnect`/`reconnect` **and `update`** call `autoReconnect.cancel(serverName)` (bumps the cancel epoch) then `opLock.run(...)`. (`update` cancels synchronously, then wraps its background disconnect+reconnect in a single `opLock.run(serverName, 'connect', …)` so a config edit cannot interleave with — or be clobbered by — an auto-reconnect using the old config.) Inside `OperationLockManager.run` (`mcpOperationLock.ts`), a manual op that finds an `isAutoReconnect` lock held **waits for that attempt to settle** and then proceeds, so the user's action always wins; only manual-vs-manual (or anything vs a *starting* manual op) rejects with "is currently …ing, please wait". The `finally`/in-loop deletes are identity-guarded (`locks.get(server) === ourLock`) so a superseding op or `clear()` never deletes a newer lock. Do not change `run` to throw on an auto-vs-manual collision — that resurrects the bug where a background reconnect could block the user from manually reconnecting.
- **Profile teardown must abort operation-lock signals before clearing state.** `cleanup()` calls `autoReconnect.resetAll()` and `opLock.clear()` before client cleanup/maps are cleared. `clear()` aborts every held operation signal, and `_performConnect`/`_performReconnect` return without writing runtime state/tool mappings once that signal is aborted. Keep this ordering: clearing maps/currentUserAlias before aborting in-flight auto-reconnect lets a stale reconnect finish later and repopulate old-profile state. `VscMcpClient.cleanup()` must call the underlying `disconnect()` even when the adapter is not marked connected, because starting/error transports still need to be stopped during teardown.
- **`_forceCancelConnection` must not touch the operation lock.** Its only caller (`_performDisconnect`, reached from `disconnect` and `update`) always runs *inside* an `opLock.run`, which owns the lock lifecycle. `_forceCancelConnection` only tears down the in-flight connection process (`activeConnections[server].abortController` + client cleanup) and the client/tool mappings. If it aborted/deleted the operation lock (as it once did), `disconnect`/`update` would release their own lock at the very first step of `_performDisconnect` and finish unserialized — letting a concurrent op slip in. In-flight connect cancellation is unaffected because it rides the `activeConnections` abort controller, not the operation lock's.
- **The 5-min connect budget covers the whole handshake, not just `initialize`.** `transport.start` (process spawn / socket open), `initialize`, and the first `tools/list` all share one `MCP_CONNECT_TIMEOUT_MS` race in `connect()`. `resources/list` must stay outside that race and remain non-fatal after `running`. On timeout, reject pending requests *before* `await transport.stop()` so the hung `initialize` unblocks; do not call `disconnect()` from the timeout path — it would set state `stopped` and clobber the `error` message the UI needs.
- **Builtin tools are watched centrally; external MCP tools are NOT.** The 10-min no-response watchdog for builtin tools lives in `AgentChatToolExecutor.executeToolCall`, gated by `isBuiltinTool(name) && !SELF_MANAGED_IDLE_TOOLS.has(name)`. Do **not** extend that gate to external MCP tools — they self-manage the same budget inside `VscodeMcpClient` and never call `reportActivity`, so a second watchdog would false-kill a healthy streaming MCP server at 10 min. Conversely, do not add a per-tool idle timer to a *new* builtin tool: feed the central one via `executionContext.reportActivity()` on real output instead.
- **`reportActivity` must signal genuine downstream activity, not UI liveness.** It is wired to real output chunks / inbound messages only. Calling it from a synthetic heartbeat (e.g. a periodic "still working" ping) would make the no-response budget unkillable. `coding_agent`'s 5-second heartbeat deliberately does not touch it (and `coding_agent` is exempt anyway).
- **A silent-but-working builtin command IS killed at 10 min — by design.** Per the product rule ("a tool that hangs with no response for >10 min auto-terminates"), `execute_command` running e.g. `sleep 600` with no output is aborted at `TOOL_IDLE_TIMEOUT_MS`. Commands expected to run long must emit periodic output. The lone exception is interactive-auth commands (`gh auth login`, etc.), which a 60-second `reportActivity` keepalive pins for the duration of their bounded 15-min terminal window so a silent browser-wait is not cut off.
- **`coding_agent` is no-response-bounded; a long *silent* CLI run is killed at the budget.** It exposes **no** agent-facing timeout arg; `executeViaSpawn` arms an `InactivityTimer` **fixed** at `TOOL_IDLE_TIMEOUT_MS` (no override), re-armed by each stdout/stderr chunk. It is listed in `SELF_MANAGED_IDLE_TOOLS` so both path watchdogs skip it; arming a path watchdog on top of the intrinsic one would double-watch the same call. Reset only on real CLI output — never on the outbound 5-second UI heartbeat.
- **`execute_command` must honor `options.signal`.** It historically ignored the abort signal and tore down only via its `registerCancellationHandler`. The central idle watchdog aborts the signal (it does not invoke that handler), so the signal listener that stops the terminal is what actually enforces the no-response kill. Removing it would let a hung command keep running while the agent loop reports it terminated.
- **`execute_command` must use captured context.** `BuiltinMcpClient` captures `ToolExecutionContext` before async boundaries and passes it through `BuiltinToolsManager.executeTool()`. Keep passing that snapshot into `ExecuteCommandTool.execute()`; rereading `BuiltinToolsManager.getExecutionContext()` inside the tool can reset the wrong session's watchdog under concurrent tool calls.
- **Computer Use must remain main-agent local-UI only.** Real-desktop control cannot be delegated to background sub-agents or non-interactive turns where the local interactive UI/visibility safety model is unavailable. Keep all layers: `MCPClientManager.getToolsForSubAgent()` must filter `computer_use` from inherited built-ins, and `BuiltinToolsManager.executeTool()` must reject direct `computer_use` calls when the captured execution context has `isSubAgent: true` or `interactionPolicy !== 'allow-ui'`.
- **Manager runtime state must follow external MCP idle errors.** `VscodeMcpClient` owns the actual transport teardown, but `MCPClientManager` owns UI/runtime state and tool routing. Keep the `VscMcpClient` `stateChange` bridge and manager handler together; otherwise a timed-out server appears connected and stale tool mappings can route later calls to a dead client.
- **Auto-reconnect only recovers previously-healthy, in-use, external servers — and is cancelled by manual ops.** When `_registerClientStateHandlers` sees a `stateChange` to `error`, it captures whether the server was already `needs-user-interaction`, then calls `autoReconnect.onServerError(serverName, causeMessage, { wasAwaitingUserInteraction })` on the `McpAutoReconnectCoordinator` after updating runtime state. The coordinator self-gates via `shouldAutoReconnect` (non-builtin AND profile `in_use !== false` AND in its `everConnected` set AND not currently `needs-user-interaction`) plus `shouldSuppressAutoReconnectForError` and the pre-error user-interaction snapshot, so a never-connected server, a deselected server, the builtin server, OAuth/client-registration/account-gated failures, invalid transport config, or one blocked on sign-in is **not** retried. The snapshot is required because auth/consent failures may briefly set `needs-user-interaction` and then intentionally settle as `error` to avoid leaving the UI stuck in a pending sign-in state. Eligible attempts route through the host adapter's `executeReconnect` → the per-server operation lock → `_performReconnect` (which never writes `in_use=false`), with exponential backoff (5s/30s/2m/5m/15m/30m + jitter, cap `MAX_AUTO_RECONNECT_ATTEMPTS`=8). Public `connect`/`disconnect`/`reconnect`/`update` and `cleanup` call `autoReconnect.cancel`/`resetAll` **before** taking the lock, so a manual action or profile teardown always supersedes a pending schedule; the underlying `McpAutoReconnectManager` also bumps a per-server cancel epoch so an attempt already awaiting cannot reschedule after cancellation. Between attempts the server stays `error` with an informative `lastError` (`<cause>; auto-reconnecting (attempt N) in Ns`, where `<cause>` is the captured failure message) — there is **no** new `MCPServerStatus` enum value, by design, to avoid renderer churn. A successful attempt (`getStatus === 'connected'`) resets the counter. The coordinator's `everConnected` set is profile-session scoped and cleared on `cleanup` (via `resetAll`).
- **Lazy-loaded tools have first-call latency.** Built-in tools with heavy dependencies (Playwright, mammoth) are only imported on first use. The first call after app start will be slower.
- **Execution context is mutable global state.** Do not read `BuiltinToolsManager.currentExecutionContext` after an async boundary for per-agent identity or persistence routing. `BuiltinMcpClient` captures the full context before `await getToolsManager()` and passes that snapshot into `BuiltinToolsManager.executeTool()`; new per-agent tools must follow that explicit snapshot pattern.
- **`tool_result` is not always terminal.** Some built-in tools, notably `execute_command`, may emit in-progress `tool_result` chunks with `isPartial`; downstream consumers must not treat every tool-result chunk as a completed execution.
- **`request_interactive_input` does not render arbitrary UI.** It only validates model-supplied JSON schema and hands it back to `AgentChat` for conversion into existing `choice` / `form` cards. Supported form controls include `time`, which renders a native `HH:MM` picker in the renderer for schedule-style run-time input.
- **The tool tolerates common LLM near-misses after required fields are present.** Choice payloads must include an explicit `mode` (`single` or `multi`) plus `options`, and form payloads must include `fields`. Form fields may arrive as `id`, `fieldName`, or `name` instead of `key`; choice payloads may put the prompt text in `schema.question`, which is lifted into the request description; select options may arrive as `string[]`; and option objects may omit either `label` or `value`. These variants are normalized before strict validation so real chat turns do not fail on trivial shape mismatches.
- **Runtime state is memory-only.** `MCPServerRuntimeState` is never written to `profile.json`. On app restart all servers are in `disconnected` state regardless of prior sessions.
- **Installed global MCP servers live in `mcp.json`, owned by `McpConfigManager` — not `profile.json`.** As of the global-MCP extraction (Option B), `mcpConfigManager` (`userDataADO/mcpConfigManager.ts`) owns the per-profile `McpServerConfig[]` in `{userData}/profiles/{alias}/mcp.json` and is its only writer; `ProfileCacheManager` writes only `profile.json`. `mcpClientManager` is unaffected: it still reads installed server configs through `ProfileCacheManager` (`getAllMcpServerInfo` / `getMcpServerInfo`, which delegate to the manager — never from disk directly), and the `profile:cacheUpdated` payload re-injects `mcp_servers` from the manager so the renderer wire contract is unchanged. Per-agent `chat.agent.mcp_servers` name+tool bindings remain in `profile.json`. See [userDataADO](../userDataADO/ai.prompt.md).
- **Online MCP auth is provider-neutral.** Every issuer goes through `OpenKosmosOAuthProvider` + `performOAuthFlow` with PKCE Authorization-Code grant and Dynamic Client Registration (RFC 7591). Restricted or unsupported DCR is surfaced through the existing `MCP_DCR_*` errors.
- **The external browser success page is now the primary path.** Interactive MCP sign-in should always open the external browser loopback flow rather than relying on native broker UX.
- **HTTP transport state survives application-level errors.** `VscodeHttpTransport.send()` distinguishes transport-level failures (network errors, DNS failures, connection refused) from application-level HTTP 4xx/5xx responses. HTTP status errors throw an `HttpStatusError` (with `httpStatus: number`) and the transport stays in `'running'` state so subsequent requests on the same session can still succeed. Only transport-level errors transition the state to `'error'`. This prevents one server-side rejection (e.g. `resources/list` returning 400 because the server doesn't support resources) from killing a healthy connection and blocking later `tools/call` requests. When adding new error paths inside `_sendStreamableHttp`, throw `HttpStatusError(status, message)` for any response with status >= 300 instead of a generic `Error` so the `instanceof HttpStatusError` check in the outer catch can keep the transport alive.

- **`waitForServersSettled` resolves on "settled", not "connected".** A server in `error`/`disconnected` is *settled* and will satisfy the wait. Callers that need a usable connection (e.g. the scheduler readiness preflight's `requiredServers` check) must additionally verify `getMcpServerRuntimeState(name).status === 'connected'`. Also note "settled" is event-driven off `_updateServerStatus` → `settleWaiter.notify()`; a server that never receives any status update will only release the waiter via the timeout, so always pass a finite `timeoutMs`.
