# Computer Use Module

> Lets an agent drive the **real local desktop** — capture screenshots and dispatch synthetic mouse/keyboard input to any native macOS/Windows app — through the single `computer_use` built-in tool. Default off, OS-permission gated, with a per-action human-in-the-loop confirmation gate. Browser automation is intentionally out of scope (handled by `embeddedBrowser`).

## Architecture

### Action surface (single tool, action enum)
`screenshot`, `list_displays`, `list_windows`, `focus_window`, `move_mouse`, `click`, `double_click`, `right_click`, `drag`, `scroll`, `type_text`, `press_key`, `hotkey`, `wait`.

### Grounding (image-space coordinates)
The model reasons in screenshot-image pixels. Pointer actions (`move_mouse`/`click`/…) **throw until a `screenshot` has set `lastFrame` for the same chat session**. Each pointer method calls `groundPoint(imageX, imageY)`, which maps image coords via `coordinateMapping` and returns **both** the **logical** DIP point (used to position the on-screen AI cursor) and the **driver** point (physical px off macOS, handed to nut.js), plus the target display. Out-of-range coordinates return an error rather than clicking blindly.

### On-screen AI cursor overlay (`cursorOverlay.ts`)
Computer Use drives the desktop with **synthetic** input. By itself nut.js moves the user's **real** hardware cursor (so it would visibly jump to every target — confusing, and the opposite of "my mouse isn't moving but things are being clicked"). Two pieces together fix this so the user sees **two independent cursors**:
1. **The real cursor is kept in place.** `inputDriver.ts` wraps every pointer action in `preservingCursor`: read the OS cursor position, act at the target, then restore the cursor to where the user left it. The user's hardware pointer therefore appears unaffected.
2. **The AI cursor visualizes the action.** The manager emits a `CursorSignal` (logical DIP point + display, plus drag end / button) from every pointer method **before it `await`s the synthetic input** (so the cursor renders at / starts gliding toward the target *ahead of* the real action, not after the app has already reacted — grounding still runs first, so an out-of-range point never shows a cursor); the overlay positions a per-display window over the target display and injects a tweened glowing "AI" pointer with **lifelike interaction effects**. For `click`/`double`/`scroll` the manager additionally `await`s `cursor.settle()` **between** the signal and the synthetic input, and `drag` first emits a `move` signal + `settle()`s onto the grab point before pressing — `settle()` resolves when the in-page glide actually lands (awaitable `window.__cuSettle`, resolved by the glide's arrival callback with a ~1s in-page safety cap so it never blocks the action), so the real input fires **only once the AI cursor has visibly arrived** (every mouse op "moves there, *then* acts", like a human — not "act, then the cursor catches up"). A click fires **when the cursor arrives** at the target — the spring `moveTo` runs an `onArrive` callback on settle, so the click stamp is co-located in space *and* time instead of fading out mid-glide: a spring "tap" + bright core flash + a bold expanding **"sonar" ring** (`ping`) that radiates outward past the cursor's own glow so the click reads clearly on both light and dark app backgrounds (right-click styled distinctly; double-click pulses twice). A drag holds a sustained **"button held down"** grab state (contracted ring + swollen core + breathing halo) for the whole duration of the drag along a drag trail with a release ripple, and scroll gets a gentler pulse.

The AI cursor **stays solid while the agent is active** (no inter-action fade) so it reads as a persistent second cursor, and is kept alive across the model's think-time by `cursor.ping()` — called from `screenshot()` **and from every keyboard/focus action** (`type_text`/`press_key`/`hotkey`/`focus_window`), so non-pointer steps don't make it vanish. The window self-hides only after `IDLE_HIDE_MS` (**20s**) of no signals/pings — sized to bridge the model's per-step think-time so the cursor stays **continuously visible throughout an operation** instead of blinking out between steps, and only disappears once the agent has truly stopped. During capture the overlay is hidden then re-shown the instant the frame returns (**before** awaiting the slower frontmost-app probe), so it's hidden only for the capture itself. The whole surface is **display-only and fire-and-forget** — `CursorIndicator.signal/ping/settle/hide/dispose` MUST never throw (a visualization failure can't break an action); `settle()` additionally waits briefly for the first overlay window to become ready before pointer dispatch, never rejects, and is capped so it can never block the action it gates. On by default in v1 with no settings toggle (a toggle is a possible follow-up). **Known tradeoff:** because `move_mouse` also restores the real cursor, a pure hover does not persist for the next screenshot — the agent should rely on clicks rather than hover-reveal UIs.

### Permission gating
- Windows ARM64 is blocked before permission checks or tool import: the current native input driver ships no Windows ARM64 addon, so Settings shows an unavailable card, `shouldExposeTool('computer_use')` hides the tool, and stale execution returns a recoverable unsupported-platform error.
- `screenshot` requires Screen Recording granted.
- Keyboard/focus actions require Accessibility granted (`ensureAccessibility`).
- Missing permission → structured error with a "Settings" hint, never a throw.

### Confirmation gate (HITL) — owned by `computerUseTool.ts`, not the manager
- Read-only actions (`screenshot`, `list_displays`, `list_windows`, `focus_window`, `wait`) never gate. The low-impact pointer actions **`move_mouse` and `scroll` also never gate** — moving the pointer or scrolling a view is non-destructive and gating them would make the feature unusable (scroll deltas are clamped to ±`MAX_SCROLL_DELTA` so an oversized model delta can't flood native input).
- The remaining mutating actions (`click`/`double_click`/`right_click`/`drag`/`type_text`/`press_key`/`hotkey`) gate. `press_key` bypasses only true navigation keys (tab/esc/arrows/home/end/page up/down); letters/digits can type text and must flow through the same allowlist/confirmation gate as `type_text`. Standalone activation/destructive keys (enter/return/numenter/space/delete/backspace/del), whether sent through `press_key` or a single-key `hotkey`, are high-impact and **always** confirm, even for allowlisted apps. `highImpactReason` (RISKY_PATTERNS regex: publish/post/delete/remove/pay/purchase/authorize/grant access/submit/confirm/save/merge/approve, plus standalone activation/destructive keys and structural save/submit shortcuts) **always** confirms.
- Coordinate pointer actions (`click`/`double_click`/`right_click`/`drag`) always confirm unless the call is a confirmed retry. v1 has screenshot-only coordinate grounding and cannot prove whether a coordinate targets a benign control or a high-impact control such as Send/Delete/Submit, so allowlists and `requireConfirmation:false` do not bypass this uncertainty.
- Ordinary mutating actions confirm unless the **current OS frontmost app** is in `alwaysAllowedApps` or `requireConfirmation:false` globally disables ordinary confirmation. The match is **candidate-based**: `manager.refreshForegroundAppCandidates(chatSessionId)` re-probes the OS immediately before the gate can bypass confirmation, updates the per-session cache, and returns every identifier the OS frontmost app is known by — on Windows the **friendly name** (`Microsoft Edge`) *and* the raw **process name** (`msedge`); on macOS just the one app name — so a user can allowlist whichever form they see. `focus_window` also refreshes that identity from the OS after a successful focus. If the OS foreground cannot be resolved after focus or before dispatch, the foreground stays unknown and ordinary mutating actions confirm; never use a stale screenshot/focus cache or the model-supplied `focus_window` query/title as an allowlist identity. Both candidates and allowlist entries are normalized with `trim().toLowerCase().replace(/\.exe$/,'')` (the Settings field is free-text "App name or process name"), so `Microsoft Edge`, `msedge`, and `msedge.exe` all match Edge.
- When confirmation is required, `execute` returns a **blocked envelope** `{ ok:false, requiresConfirmation:true, confirmationId, confirmationRequest, error:'…call request_interactive_input with exactly confirmationRequest…retry with confirmed:true and confirmationId' }`. The agent must pass the locked `confirmationRequest` payload unchanged to `request_interactive_input`; the post-processor approves the id only when the submitted payload exactly matches the server-generated title/description/schema/metadata and the user selects the preset approve value (`selectedPresetValues`, not free-form `customValues`). A prompt-injected model can still display a spoofed choice request or ask the user to type `approve` into "Other", but it cannot approve the stored id because mismatched cards and custom-choice values are ignored. The retry dispatches only when `confirmed:true`, the approved `confirmationId`, chat session, and action fingerprint all match. No native input is dispatched on the blocked path or on fabricated `confirmed:true`.

### Vision return shape
`screenshot` returns `{ type:'image', data:<raw base64>, mimeType:'image/jpeg', width, height, description }`. The frame is a **downscaled JPEG** (long edge ≤ `MAX_SCREENSHOT_LONG_EDGE` 1280px, `SCREENSHOT_JPEG_QUALITY` 80) produced by `desktopControl.defaultCapture` — see the 413 Gotcha. The turn runner injects `data` as a vision part and threads `width`/`height` into that part's `metadata` (token sizing) and surfaces `description` as the tool's **text** result. `description` is built by `ComputerUseTool.describeShot(shot)`: captured display id, the full multi-display layout (bounds + primary/secondary role, captured display tagged `[captured]`), the **OS frontmost app**, and a hint to `focus_window` / re-screenshot another display when the target is unfocused or off-screen. Do NOT drop these siblings — see the "screenshot must surface situational context" Gotcha.

## Settings & Wiring
- Profile master switch `computerUse.enabled` (default off) in `profile.json`, alongside `browser`/`memex`. Shape: `{ enabled, requireConfirmation, alwaysAllowedApps }`, `DEFAULT_COMPUTER_USE_SETTINGS = { enabled:false, requireConfirmation:true, alwaysAllowedApps:[] }`.
- CRUD: `userDataADO/profileSettingsCrud.ts` `getComputerUseSettings`/`updateComputerUseSettings` (mirror Browser).
- ⚠️ **Persistence requires a `computerUse` branch in `userDataADO/profileSanitizer.ts` `sanitizeProfileV2`** — that function is the write-time "single source of truth" and **rebuilds the profile object field-by-field**, silently dropping any block it doesn't list. A settings block missing from it survives in the in-memory cache (so it appears to work during the session) but is **stripped on every disk write**, resetting on the next launch. See the persistence Gotcha.
- IPC: `startup/ipc/profile.ts` `profile:updateComputerUseSettings` validates the renderer alias against `ctx.currentUserAlias`, rejects malformed settings patches, and triggers `mcpClientManager.refreshBuiltinTools()` for live advertise/hide.
- Registration: `builtinToolsManager.ts` registers `computer_use` metadata eagerly; advertise gate (`shouldExposeTool`) and run gate (`executeTool`) both read `profileCacheManager.getComputerUseSettings(alias).enabled`. Execution also blocks missing captured main-agent context, sub-agent contexts, remote IM contexts, and any runtime whose `ToolExecutionContext.interactionPolicy` is not `allow-ui` before importing `computerUseTool.ts`, so renderer IPC/direct builtin calls and scheduled/non-interactive runs cannot screenshot or focus the local desktop.
- Settings UI: `renderer/components/settings/ComputerUseSettings{View,HeaderView,ContentView}.tsx`; nav entry in `SettingsNavigation.tsx`; route in `routes/AppRoutes.tsx`.

## Anti-Patterns
- Do NOT `require('electron')` here — use static `import { screen, desktopCapturer } from 'electron'` (and `systemPreferences` in `permissions.ts`). The global test mock only overrides static imports, not `require`.
- Do NOT import `@nut-tree-fork/nut-js` at module top level — load it lazily inside `inputDriver.ts` so it stays an `optionalDependency` and never breaks non-desktop test/CI paths.
- Do NOT dispatch a pointer action before a `screenshot` — there is no frame to map against; the manager throws by design.
- Do NOT call `AgentChatInteractionService` from here. Confirmation is the agent-driven `request_interactive_input` + `confirmed:true` retry pattern.
- Do NOT rely on the last screenshot/focus foreground cache to bypass confirmation. Ordinary allowlisted dispatch must refresh the OS foreground app immediately before the gate allows it through; unresolved foreground fails closed to confirmation.
- Do NOT clamp/silently fix out-of-range coordinates — return an error so the agent re-screenshots and re-grounds.
- Do NOT make the AI cursor overlay focusable or interactive, and do NOT route it through a preload/IPC/HTML entry — it must stay **click-through + non-focusable**, injected via `executeJavaScript` on `about:blank`. A focusable overlay steals foreground and breaks both `getFrontmostApp()` and nut.js targeting. Do NOT add `setContentProtection(true)` to keep it out of screenshots — on Windows that makes the transparent window invisible (see Gotchas); the manager hides the overlay during capture instead.

- Do NOT remove the `preservingCursor` wrap in `inputDriver.ts` or let its restore throw — it is what keeps the user's real hardware cursor in place so Computer Use shows **two independent cursors** (real + AI overlay) instead of hijacking the user's pointer. The restore is best-effort (`finally`, swallowed failures) and degrades to "leave the cursor at the target" if `mouse.getPosition` is unavailable.

## Gotchas
- ⚠️ **Two independent cursors: the real cursor is restored after every pointer action.** nut.js `setPosition` moves the user's **real** OS cursor, so without intervention Computer Use would hijack the user's pointer (it flies to each target). `inputDriver.ts` wraps every pointer action in `preservingCursor`: `mouse.getPosition()` → act at target → `mouse.setPosition(home)` in a `finally`. The click/scroll/drag still happens at the target (the cursor is there for the actual event), then snaps home — so the user perceives their pointer as unaffected while the **AI cursor overlay** does the visible work. The brief round-trip is unavoidable for click/drag/scroll (the OS event needs the cursor at the target); it is most visible on `move_mouse`, whose only purpose is the overlay. **Tradeoff:** a pure hover does not persist for the next screenshot (the cursor is restored), so prefer click over hover-reveal UIs.
- ⚠️ **`computerUse` settings only persist if `sanitizeProfileV2` (in `userDataADO/profileSanitizer.ts`) emits a `computerUse` block.** That function reconstructs the profile field-by-field at **write time**, so any block it omits is dropped from `profile.json` even though `updateComputerUseSettings` wrote it to the in-memory cache. Symptom: the toggle / always-allowed-apps work for the rest of the session (cache hit) but **reset on every relaunch / `npm run dev`** (disk never had them), which also makes the allowlist look broken (it's empty after restart). The block normalizes `enabled` (`=== true`), `requireConfirmation` (`!== false`), and prunes `alwaysAllowedApps` to non-empty strings. Tested in `profileSanitizer.test.ts`. **`updateComputerUseSettings` also normalizes `alwaysAllowedApps` (same prune rule) before `writeProfileThenCommitCache`**, because that helper caches the **raw** merged object while only the on-disk copy goes through `sanitizeProfileV2` — so without the write-path prune a malformed allowlist (e.g. a non-array from a buggy IPC caller) would survive in the cache until relaunch. The confirmation gate (`computerUseTool.ts`) additionally guards defensively (`Array.isArray` + filter-to-strings) so it can **never** throw on settings shape — a security gate must fail closed (re-prompt), not crash the feature for the session.
- ⚠️ **`@nut-tree-fork/nut-js` MUST stay externalized in the main bundle, or all input silently breaks.** It lives in `optionalDependencies`, which electron-vite/webpack do **not** auto-externalize (they only externalize `dependencies`). If bundled, its native loader (`libnut-darwin/permissionCheck.js` → `require("bindings")("libnut")`) is inlined and `bindings` resolves from the app root instead of the package dir → `Input driver unavailable: Could not locate the bindings file ... libnut.node`. Screenshots still work (Electron `desktopCapturer`), so only the *acting* half dies. Externals live in `electron.vite.config.ts` (`rolldownOptions.external` `/^@nut-tree-fork\//`), `webpack.main.config.js` (`nativeModules`), and `electron-builder.config.js` (`asarUnpack` `node_modules/@nut-tree-fork/**`). See tech-doc §8.1.1.
- ⚠️ **Keep `package.json`'s `overrides.jimp = 1.6.1` unless the native input dependency changes.** `@nut-tree-fork/nut-js@4.2.6` normally pulls `jimp@0.22.10 -> @jimp/core -> file-type@16.5.4`, which fails dependency review for GHSA-5v7r-6r5c-r473. The override upgrades that chain to `file-type@21.3.x` while keeping nut's keyboard/mouse APIs loadable. OpenKosmos only uses `keyboard`/`mouse` through `inputDriver.ts`; nut's optional image-resource helpers are not part of this feature and must be revalidated before use. See tech-doc §8.1.2.
- ⚠️ **Windows/Linux need PHYSICAL-pixel coordinates; macOS needs logical.** nut.js consumes logical points on macOS but physical device pixels on Windows/Linux (Electron is per-monitor DPI-aware by default — no `high-dpi-support` override in `src/main` — so libnut's `SetCursorPos`/`SendInput` are physical). `coordinateMapping.mapImagePointToScreen` yields a **logical** DIP point; the manager's `groundPoint` then calls `desktop.toDriverPoint(point, lastFrame.scaleFactor)` (and keeps the logical point for the cursor overlay). The real Electron-backed `DesktopControl` keeps macOS unchanged and uses `screen.dipToScreenPoint` on Windows/Linux so Electron handles mixed-DPI physical origins correctly; the pure `coordinateMapping.toDriverPoint` helper is only the fallback for non-Electron seams where only `scaleFactor` is available. Historical bugs: returning the logical point directly made every scaled Windows click/drag land short by the scale factor; multiplying the absolute logical point by one display's scale factor misplaced secondary mixed-DPI displays whose physical origin differs from `logicalOrigin * scaleFactor`. Keep DIP -> driver conversion in `DesktopControl`, not in `ComputerUseManager`, because only the Electron layer owns the accurate platform conversion.
- ⚠️ **NEVER combine `transparent:true` with `setContentProtection(true)` on the AI cursor overlay — on Windows it renders the window completely INVISIBLE.** This is a known Electron/Chromium limitation: for protected content Windows forces DirectComposition overlays, which Chromium disables for transparency, so the two flags conflict and nothing paints. Historical bug: the overlay originally set `setContentProtection(true)` to keep the AI cursor out of the model's screenshots; on Windows this meant the user **never saw the AI cursor at all** (signals fired, the DOM rendered — verified via `webContents.capturePage()` — but the transparent window was never composited to the physical screen; an actual `desktopCapturer` screen grab with content protection OFF showed the cursor compositing fine). **Fix:** `cursorOverlay.ts` does NOT call `setContentProtection`; instead `ComputerUseManager.screenshot()` calls `this.cursor.hide()` before `desktop.capture()` and `this.cursor.ping()` after (the ping runs in the capture promise's **`.finally()`** so a *failed* capture still re-shows the cursor — otherwise a throw would strand the overlay hidden), so the cursor is hidden only for the ~tens-of-ms of capture and is otherwise solidly visible. Tradeoff: the hide/capture/show is a best-effort race (not an OS-level guarantee), so on rare timing the cursor could appear in a frame — acceptable vs. an invisible cursor.
- ⚠️ **Re-assert always-on-top + `moveTop()` on EVERY show, not just at window creation.** `signal()`/`ping()` both go through the private `raise(win)` helper, which calls `showInactive()` then re-stamps `setAlwaysOnTop(true,'screen-saver')` and `moveTop()`. On Windows, once the agent activates a real foreground app — e.g. a **maximized** Paint/editor it is driving — a window whose always-on-top level was set only at creation can silently fall **behind** that newly-active app, so the AI cursor paints *under* the target and the user sees nothing (it looks like the cursor "regressed"/disappeared, even though it is mechanically healthy and renders fine in isolation — verified via `desktopCapturer`). `showInactive()` alone re-shows but does **not** re-raise. `raise()` also logs each hidden→visible transition at low frequency (`[ComputerUse] cursor overlay shown (ready=… bounds=…)`) so a "cursor not visible" report is diagnosable from the dev harness: a `shown ready=true` with no on-screen cursor points at compositing/z-order, **not** at signal/disposal.
- ⚠️ **The AI cursor overlay MUST be click-through and non-focusable.** `cursorOverlay.ts` sets `setIgnoreMouseEvents(true)` (so neither the synthetic click nor the user's real click is intercepted by the overlay), `focusable:false` + `showInactive()` + `setAlwaysOnTop(true,'screen-saver')` + `skipTaskbar:true` (so it never grabs foreground — otherwise it would pollute `getFrontmostApp()` on the next screenshot **and** misdirect nut.js clicks). `webPreferences.backgroundThrottling=false` keeps rAF/timers running even though the window is permanently non-focused. The page is `about:blank`; all DOM + animation is injected from main via `executeJavaScript` (runs in the page main world, bypasses any page CSP), so there is **no** preload / IPC channel / HTML entry / build-config change. The window loads asynchronously, so a signal arriving before `did-finish-load` is stashed (latest-wins) and flushed once the one-time bootstrap resolves. Lifecycle is observable in the dev harness via `[ComputerUse] cursor overlay window created` / `ready and visible` INFO logs.
- ⚠️ **The AI cursor overlay must self-destroy when all real app windows close, or the process never exits on Windows/Linux.** The overlay is a process-wide singleton BrowserWindow that, between actions and after the idle timeout, is only `hide()`-d — **never** closed. A hidden window still counts in `BrowserWindow.getAllWindows()`, so a lingering hidden overlay keeps Electron's `window-all-closed` event from firing; `main.ts onWindowAllClosed` then never calls `app.quit()` and on Windows/Linux the process **stays alive after the user closes the main window** (the window disappears but the process lingers). Historical bug: after a Computer Use run the overlay was left hidden, so closing the OpenKosmos window left the process running. **Fix (self-contained in `cursorOverlay.ts`, NOT `main.ts` — `main.ts` is below the 90% coverage gate and must not be edited):** on first window creation the overlay arms `watchHostWindowsForShutdown` (once per process via `shutdownArmed`), which attaches a `once('closed')` listener to every real (non-overlay) window — those open now **and** any opened later via `app.on('browser-window-created')` — and calls `overlay.dispose()` once none remain, destroying the overlay window so `window-all-closed` fires and the existing quit path runs. Overlay windows are excluded via the `__cuCursorOverlay` tag stamped in `createOverlayWindow` (`isHostWindow`). On **macOS** the main window only hides on close (it is never destroyed), so the watcher never fires there and the Dock-resident app lifetime is unchanged. `dispose()` is idempotent and post-dispose `signal`/`ping`/`settle` early-return, so a late in-flight action can't respawn the window and re-block quit. The watcher is wrapped in try/catch so a visualization-layer failure can never break shutdown.
- ⚠️ **"OpenKosmos window closed mid-run" during Computer Use is almost always OCCLUSION, not a real close.** Computer Use runs entirely in the **main process**, fully decoupled from which window is foreground/visible — it MUST keep driving the target app while OpenKosmos is not foreground (the `isProtectedSession` "main window is not foreground" logs are the **normal**, healthy CU state, not an error). On a **single display**, launching/maximizing the controlled app (e.g. macOS Freeform opens a large board, frequently in its **own fullscreen Space**) fully covers OpenKosmos, so the user perceives it as "closed" and is alarmed that CU "keeps running in the background." It was never closed: every `AgentChatManagerSessionCoordinator` window-state sample stays `{destroyed:false, visible:true, minimized:false, focused:false}` (Electron `isVisible()` stays `true` under occlusion **and** for a window sitting on another Space), there is no `window-all-closed` / `app.quit` / `render-process-gone`, and the cursor overlay is never disposed. Switching back (Cmd+Tab / Mission Control) reveals OpenKosmos intact and logs `Main window regained foreground`. **Diagnosis recipe:** grep the dev log for `visible":false`, `destroyed":true`, `window-all-closed`, `render-process-gone` — their **absence** proves occlusion, not a close; cross-check the screenshot `description` `Frontmost app:` + `Displays:` (a single `primary [captured]` display means the driven app simply covered the screen). Confirmed 2026-06-21 (session `5xs3586gs`, task "open the drawing app and draw a red hexagon" → drove Freeform to completion; OpenKosmos `visible:true` throughout, regained foreground the instant the user clicked back). **This is by design, not a bug.** Mitigation options if it keeps confusing users — both DEFERRED pending product sign-off, and both touch window lifecycle so do not add unprompted: (a) an always-on-top "Computer Use active" HUD (same seam as `cursorOverlay.ts`) that stays visible while OpenKosmos is occluded and offers a stop button; (b) raise OpenKosmos to the foreground **on task completion only** (never mid-run — that would steal foreground from the app being driven).
- ⚠️ **The AI cursor overlay hides the macOS Dock icon unless it re-asserts `app.dock.show()` — restore it on every show.** The overlay is a `transparent` + `frame:false` + `skipTaskbar:true` BrowserWindow; putting that window on screen makes macOS drop the owning app to an "accessory" activation policy and **hide OpenKosmos's Dock icon** as a side effect — the exact same reason `ScreenshotManager.cleanup()` calls `app.dock?.show()` around its region-capture overlay (see `src/main/lib/screenshot/ai.prompt.md`). Combined with the occlusion above (the driven app covers the main window), a vanished Dock icon makes the user believe OpenKosmos was **closed and unrecoverable** — no window AND no Dock icon to click back to. Historical bug (2026-06-21): mid-CU-run the Dock icon disappeared and users reported "the window closed and I can't get it back." **Fix (self-contained in `cursorOverlay.ts`):** `ensureDockIconVisible()` — a darwin-only, idempotent helper that calls `app.dock?.show()` wrapped in try/catch (Dock restore is best-effort and must never break the cursor) — is invoked inside `raise()`, the single chokepoint every overlay show (`signal`/`ping`) passes through, so the Dock icon is re-asserted on **every** action and recovers within one action cycle regardless of which transition hid it. It is a no-op off macOS. Keep the call in `raise()` (not only at window creation): creation alone can hide the icon, and re-asserting on each show also defends against any later macOS re-hide. Do NOT route Dock restore through `main.ts` (below the 90% coverage gate).
- ⚠️ **The `screenshot` result MUST surface situational context (frontmost app + display layout) and pixel dims — do not return a bare image.** The frame alone leaves the model blind to *which* app is frontmost and *which* of several displays it is looking at, so it clicks on the wrong window/screen when its target is unfocused or off-screen (observed: agent flailing while foreground was a browser and the target app was absent from the captured display). `ComputerUseManager.screenshot()` already computes `foregroundApp`, `displayId`, and the full `displays` layout; `computerUseTool.ts` MUST forward them via `describeShot` (the tool's text result) plus `width`/`height`. The dims are **also** load-bearing for tokens: `agentChatTurnRunner.persistToolResult` threads them into the injected vision message's `metadata`, and without them `ImageTokenCalculator` throws *"Width and height are required for auto/high detail calculation"* on every screenshot turn, aborting the compression check (context-overflow risk per the token-estimation postmortems). Regression-tested in `computerUseTool.test.ts` (describeShot multi-display) and `agentChatTurnRunner.test.ts` (width/height/description threading + partial-dims).
- ⚠️ macOS Screen Recording / Accessibility are separate permissions; capture can succeed while input is blocked (and vice-versa). Both are checked independently.
- ⚠️ **Mutating actions check Accessibility BEFORE the confirmation gate, not only at dispatch.** `runMutating` calls `manager.accessibilityError()` (the single source of the permission message, also used by `ensureAccessibility`) right after argument validation and **before** `confirmationGate`, matching the documented decision flow (`enabled? → permission ok? → mutating? → confirm?` in the tech-doc). Historical gap: the gate ran first, so with Accessibility missing the user was asked to approve a click/type that then failed on dispatch — they approved an action that could never run. Keep the permission check ahead of the gate; do not move it back inside dispatch only. (Ungated `move_mouse`/`scroll` surface the permission error directly from dispatch since no gate masks them.)
- ⚠️ **`hotkey.keys` must validate element *types*, not just array shape.** `validateMutating` requires `keys.every(k => typeof k === 'string' && k.trim())` — a non-string element (e.g. a JSON number) would otherwise pass the `Array.isArray && length>0` check and reach `key.trim()` in `highImpactChordReason`, surfacing a leaked internal `trim is not a function` error instead of a clean, recoverable validation message.
- ⚠️ `nutKeyName(' ')` must NOT rely on a `' ': 'Space'` alias — `.trim()` strips a lone space first. Map space via the explicit token path.
- ⚠️ **`hotkey`/`pressKey` MUST release the chord in the SAME code order as the press (never reversed), inside a `finally`.** nut.js (`@nut-tree-fork/libnut`) `pressKey`/`releaseKey` each reverse their args internally and treat the **last** code as the key + the rest as **modifier flags** (filtered to native strings of length > 1). Historical bug (severe): `hotkey` called `releaseKey(...[...codes].reverse())`, so nut.js reversed again and treated the **key** as a modifier flag. For `cmd+c` the bogus modifier `"c"` was filtered (length 1) and the bug stayed hidden; for `cmd+space` the bogus modifier `"space"` (length 5) reached libnut as an invalid flag → **`"[nut.js] - Error: Invalid key flag specified."`** → `releaseKey` threw → **`Cmd` was never released and stuck down**, so every later keystroke became `Cmd+<letter>` (windows closed via Cmd+W/Cmd+M, Spotlight unusable) and clicks became Cmd+clicks. Fix: release with identical order + `releaseChord()` falls back to per-key release if the chord release fails, so a modifier can never remain held. Reproduced by the faithful nut.js simulator in `inputDriver.test.ts`.
- ⚠️ **App/window-closing shortcuts must be structurally high-impact, not just intent-text high-impact.** The confirmation gate explicitly treats `cmd+q`, `cmd+w`, `cmd+m`, `ctrl+q`, `ctrl+w`, `alt+f4`, and `ctrl+f4` as high-impact before dispatch, even when the model's `intent` does not mention quit/close/minimize. `alt+f4` is the Windows app-quit analog of `cmd+q` and `ctrl+f4` closes the active document/tab like `ctrl+w`; both keys resolve in `inputDriver.ts` (`alt`→`LeftAlt`, `f4`→`F4`), so a missing structural entry would let an agent close the Windows app with no prompt. A benign alt chord like `alt+tab` (window switch) is intentionally NOT gated. This protects against accidental workflow interruption during Computer Use and must not be bypassed by `alwaysAllowedApps` or `requireConfirmation:false`.
- ⚠️ **`press_key` bypasses confirmation only for true navigation keys.** A bare `press_key` for tab/esc/arrows/home/end/page up/down dispatches without prompting, but letters/digits can type text and must flow through the normal allowlist + `requireConfirmation` gate like `type_text`. `enter`/`return`/`numenter`/`space` (activation) and `delete`/`backspace`/`del` (destructive) also gate. Historical gap: destructive keys and then alphanumeric keys used to early-return before *any* check, so `press_key:"delete"` could wipe selected content and `press_key:"a"` could type into a non-allowlisted field with no prompt. **Keep key sets in sync with `inputDriver.ts`' `nutKeyName` alias map** — a gated key missing from the alias map gates, gets approved, then dies on dispatch with `Unsupported key`. Structural high-impact shortcuts (`cmd/ctrl+s`, `cmd/ctrl+enter`) always confirm even if the model omits intent text.
- ⚠️ The foreground app used by the allowlist is the **current OS frontmost app**, refreshed by `ComputerUseManager.refreshForegroundAppCandidates(chatSessionId)` immediately before an ordinary mutating action can bypass confirmation. The screenshot and `focus_window` paths still update the per-session foreground cache for model context and diagnostics, but the gate must not trust that cache when deciding to skip a prompt; if the OS probe fails, the foreground becomes unknown and ordinary actions confirm. Historical bugs: the gate once read only the model-supplied `focus_window` target (so allowlists almost never matched when the model opened apps by clicking the Dock), and later trusted the last screenshot/focus foreground (so focus drift could send text to a non-allowlisted app without a prompt). Keep the allowlist tied to a fresh system foreground probe; coordinate pointer actions remain always-confirm because screenshot-only targeting cannot prove the exact control under a pixel.
- ⚠️ **Computer Use approval descriptions must HTML-escape every model/tool-provided value.** `request_interactive_input` descriptions are rendered by `InteractiveRequestCard` through `dangerouslySetInnerHTML` so normal formatted prompt descriptions can use markup. `confirmationGate.describeAction()` therefore escapes dynamic fields (`text`, `key`, `keys`, coordinates, button/action names) before putting them into the trusted Computer Use confirmation request; otherwise a malicious `type_text` payload could execute renderer HTML/script while asking the user for approval.
- ⚠️ **The Windows allowlist matches both the friendly name and the process name.** `getForegroundApp()` returns the **friendly** name (`Microsoft Edge`) for display, but the gate compares `getForegroundAppCandidates()` (`['Microsoft Edge', 'msedge']`) so a user who typed either form into Settings matches. Historical bug: the gate matched only the win32 `ProcessName` (`msedge`), so allowlisting the app's real/friendly name never worked on Windows. The friendly name comes from the process's `MainModule.FileVersionInfo.FileDescription`. Candidates intentionally **exclude the window title** (too dynamic — it would cause false allowlist matches) and bundle IDs (not available from the current foreground-app probes), so the Settings field says "App name or process name".
- ⚠️ **Windows helper probes must never steal focus.** `desktopControl.defaultCommandRunner` sets `windowsHide:true` on every `execFile` call because Windows Computer Use probes run PowerShell for `list_windows`, `focus_window`, and `getFrontmostApp`. If the helper console appears or takes focus, the concurrent screenshot/frontmost-app path can observe PowerShell instead of the target app, corrupting screenshot context and allowlist decisions.
- ⚠️ **The Windows foreground probe compiles a cached assembly, not inline C# per call.** `desktopControl.getFrontmostApp()` resolves the foreground window's PID via a tiny user32 P/Invoke. The probe DLL (`FOREGROUND_PROBE_DLL`, a per-process-randomized name in `os.tmpdir()`) is compiled on first use (~0.8–1.2s) and only **reloaded** thereafter (~0.5s), instead of re-running `csc` every screenshot or allowlist check (~1.2s each). The script falls back to an inline `Add-Type` if the cache can't be written/loaded, so it never hard-depends on disk. The randomized filename avoids loading an attacker-plantable predictable path. Do NOT switch to a fixed DLL name or a stale-while-revalidate cache of the *result* — the allowlist is a confirmation relaxation, so the frontmost identity must be fresh before each allowlist bypass. Because the name is randomized per launch, `createDefaultDesktopControl` registers `app.once('will-quit', cleanupForegroundProbe)` **on win32 only** to best-effort `unlinkSync` the DLL on exit so launches don't accumulate stale `openkosmos-cu-fg-*.dll` files (cleanup swallows all errors; the OS temp dir reclaims it anyway).
- ⚠️ **Windows `focusWindow` activates by PID, not by window title.** It matches the query against process name → window title → file description, then calls `WScript.Shell.AppActivate($pid)` and returns `OK`/`FAIL`/`NONE` so `focusWindow` reports the real outcome (the old title-only `AppActivate('<name>')` almost never matched an app/process name and **always returned `true`**). The window-title match is a **case-insensitive literal `.ToLower().Contains()`, NOT a `-like '*..*'` wildcard** — a `-like` pattern would treat `[`, `]`, `?`, `*` in a title (e.g. "Word [Protected View]") as wildcard metacharacters and match the wrong window or none. Raw `SetForegroundWindow` was rejected — the Windows foreground-lock makes it return `FALSE` when the caller isn't the active app; `AppActivate` handles the lock. The interpolated query is escaped via `psQuote` (doubles `'`).
- ⚠️ **macOS `focusWindow` escapes the model-supplied app name before interpolating it into the `osascript` AppleScript program** — `asQuote` escapes `\`, `"`, CR and LF, the AppleScript-string analogue of the Windows `psQuote`. The argv form (`runner('osascript', ['-e', script])`) already prevents *shell* injection, but without escaping a `"` or newline in the name would close the `tell application "<name>"` literal and inject arbitrary statements into the single `-e` program. Keep the surrounding quotes at the call site; `asQuote` returns only the escaped inner content.
- ⚠️ **Windows multi-monitor capture selects the source positionally when `display_id` is empty.** `desktopCapturer` sources frequently report an **empty** `display_id` on Windows, so the old `find(byId) ?? sources[0]` silently captured the **primary** monitor for any non-primary target. `selectCaptureSource` falls back to the target display's **index** in `screen.getAllDisplays()` order (which Electron mirrors in source order) before defaulting to `sources[0]`.
- ⚠️ `ComputerUseTool.wait` clamps ms to `[0, 10000]` and really sleeps — tests use fake timers (`vi.runAllTimersAsync()`).
- ⚠️ **Every mutating/side-effecting action checks `signal?.aborted` right before dispatching synthetic input** and returns `{ok:false, error:'aborted'}` without acting, so a cancelled turn (the confirmation card dismissed, or an abort landing between steps) can never click/type/drag into whatever now holds focus. The `signal` is threaded `execute → runMutating` for `click`/`double_click`/`right_click`/`drag`/`type_text`/`press_key`/`hotkey`, and checked inline for `move_mouse`/`scroll`; this mirrors `embeddedBrowserTool` and satisfies PRD §151. **The manager re-checks too**: `signal` is also carried on `DispatchContext`, and `ComputerUseManager.throwIfAborted(ctx)` runs immediately before *every* native driver dispatch — crucially **after** the ~1s pre-action `cursor.settle()` glide on click/double/right/drag/scroll. Without that second check an abort arriving *during* the settle would still land the click; the thrown `Error('aborted')` is caught by `execute` and mapped to the same `{ok:false, error:'aborted'}` envelope as the tool-layer guard. **The non-mutating actions honor cancellation too**: `list_displays`/`list_windows`/`screenshot`/`focus_window` short-circuit to `aborted()` when the signal is already aborted, so a cancelled turn never captures the screen or re-focuses an app — `focus_window` in particular changes the OS foreground, a real side effect that must not fire after cancel.
- ⚠️ **`mapImagePointToScreen` clamps the mapped point to the display's last addressable pixel (`origin + size - 1`), not `origin + size`.** A model point on the exact right/bottom edge (`x === imageWidth`) has fraction `1`, which maps to `bounds.x + bounds.width` — the **first pixel of the adjacent display** (or off-screen on a single monitor), so an edge click would land on the wrong screen. Points strictly `> imageWidth/Height` are still rejected with an `outside` error; only the in-range edge is clamped. Tests assert edge inputs land on `width-1`/`height-1`.
- ⚠️ **`profile:updateComputerUseSettings` calls `mcpClientManager.refreshBuiltinTools()` after a successful persist** so toggling the master switch advertises/hides the `computer_use` tool **within the running session** instead of only after relaunch. It is **best-effort and isolated**: wrapped in its own `try/catch` so a refresh failure logs but cannot flip the already-persisted `{success:true}` to failure, and it is skipped entirely when the persist returns `false`. `refreshBuiltinTools` is itself a no-op when the builtin tool-name set is unchanged.

## Verification Steps
1. Enable Settings → Computer Use; confirm the `computer_use` tool appears in the advertised inventory (toggle off → it disappears live).
2. Without a prior `screenshot`, issue a `click` → expect a grounding error, not a click.
3. `screenshot` → confirm a single image vision part is returned.
4. `type_text` into a non-allowlisted foreground app → expect a `requiresConfirmation` envelope with a `confirmationRequest`; retry with `confirmed:true` only after approving that exact card → dispatches.
5. A high-impact target (e.g. a "Submit"/"Delete" button label) → always confirms, even for an always-allowed app.
6. macOS: revoke Screen Recording → `screenshot` returns a permission error with a Settings hint.
