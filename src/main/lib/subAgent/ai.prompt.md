# Sub-Agent System

> Manages spawning, lifecycle, and scoped execution of task-focused sub-agents from within a parent agent conversation.

## Key Files
| File | Responsibility | Size |
|------|---------------|------|
| `subAgentManager.ts` | Singleton lifecycle manager; enforces parallel/session limits, parent-child tracking, background promotion | ~large |
| `subAgentChat.ts` | Lightweight non-streaming conversation engine; ≤25 turns, 30s timeout, context compression | ~large |
| `subAgentTaskStore.ts` | Persistence layer for sub-agent task records; debounced JSON writes, dual history | ~medium |
| `subAgentDeliveryLedger.ts` | Durable global outbox for completed background results; persists pending deliveries keyed by parent session id so they survive an app restart before the in-memory queue is drained | small |
| `subAgentTaskWatcherRegistry.ts` | Tracks which tasks have an active frontend viewer; gates streaming chunk emission | small |
| `subAgentTaskTypes.ts` | Types for persisted task files (`SubAgentTaskFile`, `SubAgentTaskMetadata`) | small |
| `subAgentPromptBuilder.ts` | Builds sub-agent system prompts, including read-only Memex guidance when `memex_memory` is inherited or explicitly allowed. | small |
| `types.ts` | Runtime types (`SubAgent`, `SubAgentChatOptions`, `SubAgentStepUpdate`) separate from persistence types in `userDataADO/types/profile.ts`; shared `ToolExecutionContext` includes chat provenance fields used by built-in tools. | small |

## Architecture
- **SubAgentManager** is a singleton (`getInstance()`). All spawn limits from `SUB_AGENT_LIMITS` in `profile.ts` have been removed (set to `Infinity`); no hard caps on parallel instances, total spawns per session, or background tasks. The system relies on turn budgets and `CancellationToken` cascades for resource protection.
- **SubAgentChat** uses streaming fetch internally (SSE parsing identical to AgentChat) and forwards chunks to the renderer via `SubAgentTaskWatcherRegistry` when a UI panel is actively watching the task. Results are also returned to the parent after the loop completes.
- Context compression in SubAgentChat uses claude-haiku-4.5 summary when message count or token threshold is exceeded; tool results are never discarded (only text messages are summarised).
- Sub-agents **default to the parent's LLM model**, but the spawning `sub_agent` call may specify a non-`inherit` `model` override for multi-model collaboration. They still **share the parent's `CancellationToken`** — cancelling the parent auto-terminates all running sub-agents.
- Sub-agent deliverables are placed under the parent chat's workspace (`getChatWorkspace(parentChatConfig)`) with path shape `{workspace}/{YYYYMM}/{parentSessionId}/{safeName}-{shortTaskId}`. Do not derive deliverable roots from the parent agent config; knowledge remains agent-owned and is not the working directory.
- When `sub_agent` omits `tools` or passes an empty list, `SubAgentManager` inherits the parent Agent's external MCP tools. When `tools` is non-empty, every requested tool is validated against the parent's available tool set; only the matching external MCP server/tool subset is passed into the child, and `allowedToolNames` filters both external and built-in tools to the requested names. If the parent Agent's `mcp_servers` list is empty, that matches the main-agent contract and means all currently available external MCP servers are inherited or considered for explicit validation/narrowing. If the parent Agent config cannot be found, explicit tool requests fail closed instead of expanding to all connected servers. `SubAgentToolExecutor` re-enforces the same boundary at execution: unlisted tool calls are rejected, and external calls require a server entry that explicitly lists the called tool while using strict MCP server scope with no global fallback.
- Recursive spawning is explicitly blocked: sub-agents cannot call `sub_agent`. Parent-only task-control tools are also kept unavailable to child agents through the shared tool block list and execution-time role checks.
- Memex is read-only in sub-agents. If `memex_memory` is available, `subAgentPromptBuilder` tells the child to use `recall`, `search`, and `read` only; execution still rejects `operation:"capture"` through the Memex source resolver because prompt text is not an authorization boundary.
- State updates to the renderer are throttled at 100 ms (`STATE_UPDATE_THROTTLE_MS`); up to 30 steps are kept per task (`MAX_STEPS_IN_STATE`).

### Timeouts & Hard Stops
- **Turn budget**: Hardcoded loop guard of 200 turns per sub-agent (`turnCount < 200` in `SubAgentChat`). No configurable `maxTurns` parameter — the limit is a safety bound, not a tuning knob.
- **CancellationToken**: Inherited from parent `AgentChat`. User cancel or parent dispose fires `AbortController.abort()`, killing the in-flight streaming fetch.
- **Auto-background promotion**: After 120s (`AUTO_BACKGROUND_TIMEOUT_MS`), a synchronous sub-agent is promoted to background — does NOT kill the agent, just unblocks the parent.
- **Context compression timeouts**: 20s for message-count compression (haiku), 15s for tool-result summarization (haiku). Both fall back to hard truncation on timeout; neither terminates the sub-agent.
- **No per-LLM-call timeout**: Long streaming calls (60–100s for opus-class models) are normal. The stream actively receives SSE chunks the entire time. Tool execution is governed by a unified 10-minute **no-response** budget, not a fixed execution cap. On the **main-agent path** builtin tools are watched in `AgentChatToolExecutor`; on the **sub-agent path** builtin tools are watched in `SubAgentToolExecutor`. Both paths pass the same agent-scoped MCP server names into `mcpClientManager.isBuiltinTool(..., agentMcpServerNames)` and `executeTool(...)`, inject `ToolExecutionContext.reportActivity()`, and pass an `AbortSignal` so real output resets the watchdog and silence aborts signal-aware tools such as `execute_command`. Foreground `sub_agent` calls forward child turn-completion progress and proxy child state updates through `reportActivity()` so a long live child task does not look idle to the parent tool watchdog; they also link the parent `AbortSignal` into the child `CancellationToken` so a parent idle timeout stops the child run. External MCP tools self-manage the same budget inside `VscodeMcpClient`. `coding_agent` is listed in `SELF_MANAGED_IDLE_TOOLS` and remains self-managed with its own intrinsic `InactivityTimer` because it runs on both main-agent and sub-agent paths. No builtin tool exposes an agent-facing timeout parameter. See [mcpRuntime/ai.prompt.md](../mcpRuntime/ai.prompt.md) "Time constraints".

### Task Persistence (SubAgentTaskStore)
- **Storage**: `{userData}/profiles/{userAlias}/sub-agent-tasks/{YYYYMM}/{taskId}.json`
- **Task ID**: All tasks use prefix `sa_` (e.g., `sa_1716000000000_abc123`). Background is a state, NOT an ID distinction.
- **Dual history**: `chat_history` (full, for UI replay) vs `context_history` (compressed, for LLM context window). After context compression triggers, `context_history` diverges from `chat_history`.
- **Lifecycle**: `createTask()` → `appendMessage()` (per turn) → `incrementTurnCount()` (per turn) → `completeTask(status, result?, error?)` (on finish)
- **Background promotion**: When a foreground task exceeds 120s, it is promoted to background. The task retains its original ID — only in-memory runtime state changes. `completeTask()` is called when the background execution finishes.
- **Writes**: Debounced at 2s idle; `completeTask()` force-flushes immediately.
- **`executeInBackground`**: Creates a single task, passes `externalTaskId` to the spawn call to avoid creating a duplicate TaskStore entry.
- **Chat deletion cleanup**: `deleteTasksForChat(userAlias, parentChatId)` removes matching in-memory entries and task files under the per-profile `sub-agent-tasks/{YYYYMM}/` tree. It is used by chat deletion after the profile write succeeds; it is not a session-dispose path.

### Result Delivery (SubAgentLifecycle + SubAgentDeliveryLedger)
- Completed background results are pushed onto an **in-memory result queue** keyed by `parentSessionId` (`enqueueResult`), and the parent is woken via the `subAgentResultReady` event. The parent pulls them with `drainResults(parentSessionId)` on its next turn (auto-wake or user message).
- The in-memory queue is lost if the app exits before a drain. To prevent silent result loss, `enqueueResult` ALSO records the result to a durable on-disk **delivery ledger** (`subAgentDeliveryLedger.ts`), and `drainResults` merges any ledger entries (`peekPendingDeliveries`) deduped against the in-memory queue by `taskId`. The ledger entry is **peeked, not deleted, on drain**; the parent acks it (`ackPendingDeliveries`) only **after it has SUCCESSFULLY persisted the injected `<task-notification>` into the saved chat session** (see `AgentChat.drainBackgroundSubAgentResults` → `saveChatSession` → ack gated on `saved.success`). `saveChatSession` resolves `{ success: false }` on a failed write WITHOUT throwing, so the ack is gated on that flag, not just the surrounding catch. So a crash OR a silent failed persist re-delivers rather than dropping the result (at-least-once), and — because the entry is removed only on a confirmed persist — an already-delivered result is gone from the ledger and is never replayed after a restart. `drainResults` itself never acks (it is pure peek+merge), so re-delivery before the parent persists is always safe.
- **Proactive post-restart replay**: after a restart the in-memory `subAgentResultReady` event never re-fires, so without a kick a recovered result would wait for the user's next message to that session. To close that gap, `agentChatManager.switchToChatSession` calls `SubAgentAutoWakeController.recoverPendingForSession(sessionId)` when a session is activated. It peeks the ledger and, only if a pending result exists, schedules the same debounced auto-wake used for live completions — so a result that completed while the app was closed is injected when the user reopens the session, with no message required. The one-shot guard is consumed **only when a pending result is actually found** (not on an empty peek), so a session whose ledger is empty at activation can still be recovered on a later activation if a result arrives — or is dropped by a busy parent — in the meantime; once a recovery is actually scheduled the guard prevents duplicating live event-driven delivery.
- **Busy-parent wake retry**: `SubAgentAutoWakeController.trigger` injects the synthetic wake only when the parent is idle. If the parent is mid-turn it does NOT drop the wake — it re-arms the debounce (retry every ~500ms) so the wake fires once the parent goes idle, instead of stranding the result until the user's next message. The retry is bounded by the ledger still holding a pending entry (`peekPendingDeliveries`): once the result is drained+acked by any turn, or the instance is disposed, the retry self-terminates.
- **Ledger storage**: `{userData}/sub-agent-pending-results.json`, shape `{ [parentSessionId]: SubAgentTaskResult[] }`. It is intentionally **global, not per-profile**, so draining needs only a `parentSessionId` (the result payload is self-contained; the durable per-profile task record still lives in `SubAgentTaskStore`).
- **Semantics**: entries are PEEKED on drain and acked only after the parent durably persists the injected notification (`ackPendingDeliveries`, called from `AgentChat.drainBackgroundSubAgentResults`) → at-least-once delivery (a crash before persist re-delivers rather than dropping a completed result; a delivered+persisted result is removed so it is not replayed after a restart). Reads/writes are wrapped in try/catch and use atomic temp-file + rename; any I/O failure degrades gracefully to the in-memory path.

## Gotchas
- ⚠️ **`getParentAgentConfig` (sub-agent MCP inheritance) must resolve the parent via `getChatPrimaryAgent`, NOT raw `parentChatConfig.agent`.** Post agent/chat separation, `profileCacheManager.getAllChatConfigs` returns agent_ids-only cache chats (inline agents stripped), so `chat.agent` is `undefined` for every migrated/separated chat — reading it directly makes `getParentAgentConfig` return `undefined`, `spawnAdhocSubAgent` fails with "Parent agent config not found", and sub-agents silently stop inheriting the parent's external MCP tools. The accessor (`agentAccessor.getChatPrimaryAgent`) resolves `agent_ids` through the store; the sibling `deriveDeliverablesPath` already does this. Any new code in this module that reads a parent/other chat's agent config must go through the accessor, never `chat.agent`.
- ⚠️ **`deriveDeliverablesPath` must use `getChatWorkspace`, not `parentAgent.workspace`.** Workspace moved to `ProfileV2.chats[].workspace`; agent configs own knowledge only. A sub-agent spawned from a shared agent must write deliverables into the current chat's workspace, not the shared agent's knowledge or any legacy workspace fallback outside `getChatWorkspace`.
- ⚠️ Persistence types (`SubAgentConfig`, `SubAgentRuntimeState`) live in `userDataADO/types/profile.ts`, NOT in `types.ts` here (which holds runtime-only types). Confusing these causes type mismatches.
- ⚠️ SubAgentChat wires streaming chunks to the renderer **only when a watcher is registered** via `SubAgentTaskWatcherRegistry`. Streaming is conditional — do not expect chunks unless the UI panel is open for that task.
- ⚠️ The `sub_agent` built-in tool is declared in `mcpRuntime/builtinTools/` and dispatches through `SubAgentManager`; changes to the tool argument schema must be mirrored in both places.
- ⚠️ Sub-agent MCP permissions are enforced twice: `SubAgentManager` validates and narrows the advertised tool set at spawn time, and `SubAgentToolExecutor` validates every emitted tool call before routing it with strict MCP scope. Do not rely on LLM tool schemas alone; tool-call names are untrusted at execution time.
- ⚠️ Do not allow sub-agent Memex writes. A child may inherit `memex_memory` for research, but `capture` changes durable parent/profile memory and must remain parent-chat only. Keep `isSubAgent` in `ToolExecutionContext` and keep the Memex resolver's rejection path covered by tests.
- ⚠️ Foreground `sub_agent` progress is also a watchdog signal for the parent tool, and parent abort is linked into child cancellation. `BuiltinToolsManager` must pass the captured per-call `executionContext` into `SubAgentTool.execute()`; do not reread mutable static context after lazy imports because concurrent tool calls can clear or overwrite it. If you add a new foreground spawn path, keep both pieces: progress must flow through `params.onProgress` or the proxied child `eventSender`, and `options.signal` must cancel the child token.
- ⚠️ **Task ID does NOT distinguish foreground vs background.** All tasks use `sa_` prefix. Background is a runtime state, not an identity. Never create a separate task ID for background promotion.
- ⚠️ `executeInBackground` passes `externalTaskId` to spawn methods with `skipTaskStoreCreate` to avoid double-creating TaskStore entries. If adding a new spawn path, respect this pattern.
- ⚠️ `completeTask()` must be called on ALL exit paths (success, failure, cancellation). Without it, the on-disk status stays "running" forever.
- ⚠️ Background result delivery has TWO layers: the in-memory `resultQueue` (fast path) AND the durable `subAgentDeliveryLedger` (restart-safe outbox). `enqueueResult` writes BOTH; `drainResults` merges BOTH deduped by `taskId`. If you add a new result-emitting path, route it through `enqueueResult` so it inherits the ledger fallback — do not push to `resultQueue` directly.
- ⚠️ The ledger is **peek-then-ack-on-persist**, NOT delete-on-read and NOT ack-on-next-drain: `drainResults` only PEEKS entries (pure peek+merge, it never acks). The parent acks via `ackPendingDeliveries` from `AgentChat.drainBackgroundSubAgentResults` **after** `saveChatSession` has durably persisted the injected `<task-notification>`. Do NOT move the ack back into `drainResults`/the lifecycle (ack-on-next-drain) — its delivered-set was memory-only and lost on restart, so an already-delivered entry got replayed (duplicate); and do NOT ack before the persist — that re-opens the crash-after-drain loss window. `cancelAllForSession` intentionally leaves the on-disk ledger entry so a result completed just before disposal still survives a restart.
- ⚠️ Proactive post-restart replay lives in `chat/subAgentAutoWake.ts` (`recoverPendingForSession`), invoked from `agentChatManager.switchToChatSession`. It is gated by an in-memory `recoveryAttempted` set that is added to **only when `peekPendingDeliveries` returns a pending result** — an empty peek (or a peek that throws) leaves the guard UNSET so a later activation can still recover a result that arrived, or was dropped by a busy parent, in the meantime. So it never duplicates a scheduled live delivery yet never permanently skips a session that was merely empty at first activation. `peekPendingDeliveries` is imported **statically** (the ledger is already in the static graph via `subAgentLifecycle`); do NOT switch it to a dynamic `import()` or `check-mixed-imports` will fail. The peek is wrapped in try/catch because `peekPendingDeliveries` calls `app.getPath` before its own guard.
- ⚠️ `SubAgentAutoWakeController.trigger` only injects the synthetic wake when the parent is idle, but a busy parent does **not** drop the wake — it re-arms the 500ms debounce (`handleResultReady`) so the wake retries until the parent goes idle. The retry is bounded by `peekPendingDeliveries` still returning a pending entry, so it self-terminates once the result is drained+acked or the instance is disposed; a `!instance` (unknown/disposed session) returns without re-arming, ending the loop. Without this, a result completing while the parent is mid-turn would sit undelivered until the user's next message.
- ⚠️ **`SubAgentLLMClient` must convert tool history for the `/responses` endpoint.** `formatMessageForAPI()` emits the `/chat/completions` shape (`assistant.tool_calls` + `role:'tool'`). For `/responses` models (GPT-5.x — the parent default), that history MUST be converted to `function_call` / `function_call_output` items via the shared `../chat/responsesInputConverter.ts` before being placed in `requestBody.input`. Sending `assistant.tool_calls` to `/responses` returns `400 Unknown parameter: 'input[N].tool_calls'`, and because turn 1 has no tool history the bug only bites on turn 2+. Do not re-fork this conversion; reuse the shared converter (the main transport in `agentChatUtilities.ts` does the same). See [postmortem](../../../../ai.prompt/postmortem-subagent-responses-toolcalls-400.md).
