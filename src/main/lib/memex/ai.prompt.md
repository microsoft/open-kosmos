# Memex Memory (native)

> Persistent long-term memory: current-agent memory plus profile-memory shared by every agent in the current profile. Both scopes are Zettelkasten-style linked markdown cards (YAML frontmatter + `[[wikilink]]` bodies). The memex source is **vendored** under `vendor/` and called natively — no CLI, no stdio-MCP server, no child process, no embeddings, no sync.

## Architecture

### Two consumers, one store
```
                 ┌─ memex_memory tool (main/lib/mcpRuntime/builtinTools) ── capture/archive + reads (text, scope-aware)
MemexService ────┤
  (stateless)    └─ memexIPC handlers ────────────────────────────────────── sidepane READS current-agent; Settings manages profile-memory
                                                                                      ▲
        tool capture/archive or Settings archive/delete → emitCardsChanged(scope) → memexEvents bus ─────────────┘
                      (current-agent fans out to referencing chats; profile-memory broadcasts to Settings)
```

- **Agent writes go through high-level `capture`; Settings can archive/delete only profile-memory.** The `memex_memory` tool exposes `capture` for durable writes (`remember`/`update`/`correct`) plus read/archive operations; raw `write` and `retro` are intentionally not in the V1 tool schema. Sub-agents are read-only and cannot call `capture` or `archive`. The chat sidepane remains read-only. Renderer mutation IPC intentionally excludes create/edit and never writes current-agent memory.
- **`MemexService` is stateless.** Every method takes a freshly-resolved `MemexHome`, so a single singleton serves every agent and profile-memory scope without caching `home` across calls. This keeps current-agent isolation safe while allowing profile-memory sharing inside one profile.
- **Change notification is process-local first.** Mutations emit on `memexEvents` with `userAlias` + `scope`. Current-agent events also carry `agentId` and are fanned out to chats that reference that agent. Profile-memory events broadcast `{ scope: 'profile-memory' }` so Settings refreshes.
- **Capture provenance is resolved in main process.** The model supplies a source descriptor, but `memexCaptureSourceResolver` validates the current persisted chat-session anchor or canonical file path before `MemexService.capture()` writes a card. Capture is a `memex_memory` tool operation, not a separate tool and not a background extractor.
- **Capture writes are serialized per memory home.** `capture()` wraps source resolution plus remember/update/correct mutations in a per-`cardsDir` in-process queue. Keep provenance validation, duplicate-title checks, and append read-modify-write inside this serialized section so queued captures re-check evidence immediately before writing and cannot fork a title or lose one update/correction append.

### Failure-mode split
Text methods (agent tool) throw `Error` on not-found/validation/rejected-sensitive-input so the tool returns `{success:false,error}`. `capture()` returns a detailed result with `changed`, `status`, and write metadata so the dispatcher can emit exactly one `cardsChanged` event after a successful durable mutation. Structured methods (sidepane) are wrapped by `memexIPC` in try/catch returning `MemexResult<T>`. Do not blur these — the tool relies on throws/detailed capture metadata; the IPC relies on typed results.

### Enablement (per-profile master switch)
Enablement follows the **embedded-browser** pattern — there is NO feature flag. A single per-profile master switch `memex.enabled` (in `profile.json`, default `false`, managed by `profileCacheManager.getMemexSettings(alias)`) gates everything, surfaced in Settings → Memex Memory:
- `memexIPC` always registers its handlers; each one gates per-call via `resolveHome` (resolves the current alias from `ctx.currentUserAlias`, then returns `'Memex Memory feature is disabled'` when off), so the Settings toggle takes effect at runtime without re-wiring.
- The `memex_memory` tool metadata is always registered in `builtinToolsManager`; `shouldExposeTool` hides it from the advertised inventory when off (resolving the alias via `profileCacheManager.getCurrentUserAlias()`), and `executeTool` returns a disabled message. Its `scope` argument defaults to `current-agent`; `profile-memory` uses only `userAlias` and does not require a primary agent.
- The renderer sidepane/toggle read the switch via `useMemexMemoryEnabled()` (which reads `profile.memex?.enabled` from `useProfileData()`) and render `null` when off. Both the chat sidepane detail and Settings detail behave like file viewers: a title header above `FileContentRenderer` rendering the full raw `.md` card, including YAML frontmatter, through the shared `OverlayFileViewer` file-format pipeline. They pass the scoped `CardDetail.resolvedWikilinks` map so known `[[slug]]` and `[[slug|label]]` references remain clickable card navigation inside the Markdown body. Settings mirrors the Hooks management pattern: header switch + disabled empty state while off, and a two-column Profile Memory list/detail manager while on; row actions are archive/delete only. Parent agents create/update/correct profile-memory only through the gated `capture` operation.
- When the switch flips, `profileDataManager.handleProfileCacheUpdate` detects the `memex.enabled` change and calls `mcpClientCacheManager.refresh()` so the Agent page tool list updates immediately (otherwise it stays stale until the next chat switch).

## Gotchas
- **Resolve `home` per-call from execution context; never cache it across scopes.** Caching would leak one agent's memory into another or leak profile-memory into current-agent memory.
- **`memexHome.ts` is the path-traversal chokepoint.** Both `alias` (profile dir name) and the profile-resolved `agentId` are validated as single safe segments (`assertSafeSegment`: rejects `/`, `\`, `.`, `..`, and absolute paths) before `path.join`. Use `buildAgentMemexHome` for current-agent memory and `buildProfileMemexHome` for profile-memory; do not compose paths by hand.
- **`MemexService` rejects nested (path-like) slugs.** The store is built with `nestedSlugs=false`, so `scanAll` collapses a nested file to its basename — a nested write would appear to succeed but later reads could not resolve it. `assertFlatSlug` (called by `capture` append targets, legacy helpers, `read`, and `archive`) rejects any slug containing `/` or `\`. `slugify()` already produces flat slugs, so derived slugs never trip it.
- **`parser.ts` patch must preserve upstream fallback** (strip frontmatter on YAML parse failure). The only change vs upstream is gray-matter → js-yaml.
- **`emitCardsChanged` only fires for mutations.** `recall`/`search`/`read`/`links`/`organize` are read-only and must NOT notify. A mutation that throws or a capture that returns `changed:false` must NOT notify. Current-agent notifications include `agentId`; profile-memory notifications do not.
- **Sub-agents are read-only for Memex.** Prompt guidance tells them to use `recall`/`search`/`read` only, and execution rejects `capture` when `isSubAgent` is present in the captured tool context. Do not rely on prompt text as the only guard.
- **Do not capture streaming assistant text.** `capture` may cite the current persisted user message, an existing knowledge file, or an existing session deliverable. It is invoked during a parent-chat tool call and writes only evidence that already exists at execution time.
- **Default retrieval is status-aware.** `read`, `recall`, `search`, `listCards`, and `searchCards` exclude active-dir cards marked `resolved`, `superseded`, or `archived`; legacy missing/unknown statuses remain visible. Cards marked `conflict` remain visible but include a warning so callers do not treat them as unqualified current truth. Malformed-frontmatter cards are excluded from list/search/recall so corrupt metadata is not promoted as current truth.
- **Legacy chat-scoped memory migrates to the primary agent only.** `runAgentStoreMigrations` moves `<profile>/memex_memory/{chat_id}` into `agents/{agent_ids[0]}/memory`. Multi-agent legacy memory cannot be safely split, and copying it to every agent would duplicate/share potentially private memory. When multiple legacy chats share one target agent and slug conflicts occur, the existing target card wins and the later legacy file is moved with a `-{chatId}` suffix so it remains visible.
- **Sidepane navigation only exposes known-card links.** `readCardStructured().outbound`, `readCardStructured().resolvedWikilinks`, and `getGraph()` all resolve wikilinks with `store.buildLinkResolver` and drop non-existent targets, so every clickable Markdown wikilink is a navigable card slug.
- **`setupMemex` is idempotent and always wires handlers.** Calling it twice is a no-op (`isWired`). Unlike a flag-gated setup, it registers the IPC handlers regardless of the master switch; gating happens per-call inside `resolveHome`, so flipping `memex.enabled` in Settings takes effect without re-wiring or restart.
- **No per-agent install lifecycle.** The old `MemexManager.ts` + the old Settings `MemexView` install/enable UI + `profile.ts` `onAgentCreated/onAgentDeleted` memex hooks were deleted. The current `/settings/memex` route renders a per-profile master switch in the unified header and a Hooks-aligned Profile Memory manager gated by that switch; memory trees are still lazily created on first write. Do not re-introduce a per-agent install/enable lifecycle.
- **Toggling the switch must refresh the renderer MCP cache, or the Agent tool list goes stale.** The built-in tool inventory is computed live (`shouldExposeTool` reads `profileCacheManager.getMemexSettings(alias)` on every `getAllTools()`), but the Agent page is driven by `mcpClientCacheManager`'s cache. A chat switch happens to refresh that cache; a Settings toggle does not — so `profileDataManager.handleProfileCacheUpdate` must call `mcpClientCacheManager.refresh()` when `memex.enabled` flips between the previous and next profile (mirrors the `browser.enabled` branch).
