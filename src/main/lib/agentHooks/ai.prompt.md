# Agent Hooks (runtime)

> Profile-level Hook resources resolved per-Agent at runtime and executed around eight Agent Loop lifecycle events (`SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, plus the observational `Stop`, `PreCompact`, `PostCompact`). This module covers the **runtime foundation** (Phase 1), the **management surface** (Phase 2), and **extended actions + events** (Phase 3) of `docs/agent-hooks-prd.md` / `docs/agent-hooks-tech-doc.md`: data model, resolver, command + HTTP runners, executor, manager facade, the typed IPC contract, the renderer Settings UI, and the Agent-friendly `manage_hooks` built-in facade. It is OFF by default behind the profile-level `ProfileV2.hooksEnabled` master switch. Each Hook is flat — one `event`, one optional `matcher`, and one `action` (command or http) — and the action may carry an optional `if` permission-rule condition evaluated on tool events.

## Architecture

**Resource model lives in shared profile types.** `HookDefinition` and friends are defined in `src/shared/agentHooks/profileTypes.ts`; `userDataADO/types/profile.ts` uses that shared type for `ProfileV2.hooks?` and re-exports the types for compatibility. Persisted hooks are sanitized by the single source of truth, `sanitizeProfileV2` → `sanitizeHooks`. `types.ts` here only re-exports them and adds runtime types. Adding the field is additive (no migration needed). Hooks retain required `version` + `source` (`'IN-LIBRARY' | 'ON-DEVICE'`) and optional `remoteVersion` as persisted-schema compatibility metadata. Locally authored hooks (Settings editor and the `manage_hooks` tool) always use `source: 'ON-DEVICE'`, `version: '1.0.0'`, and `remoteVersion: ''`; these fields never trigger network access or update checks.

**The persisted hook *list* lives in `hooks.json`, not `profile.json`.** Mirroring the MCP (`mcp.json`) and Skills (`skills.json`) splits, the per-profile hook library is owned by **`HooksConfigManager`** (`userDataADO/hooksConfigManager.ts`, singleton `hooksConfigManager`), the only writer of `{userData}/profiles/{alias}/hooks.json`. `ProfileCacheManager` mirrors `profile.hooks` only during the load/migration window, then strips the list from the cached profile. This module is unaffected at the API level: `AgentHookManager` still reads the library through `profileCacheManager.getHooks(alias)` (which now delegates to `hooksConfigManager.getHooks`) and `agentHooksIpc` / `manageHooksFacade` CRUD still calls `profileCacheManager` (which delegates list writes to `HooksConfigManager` via `profileHookCrud`). **The one asymmetry vs. mcp/skills:** the master switch `ProfileV2.hooksEnabled` STAYS in `profile.json`, so `isHooksEnabled`/`setHooksEnabled` are unchanged. See [Profile & Data Mgmt → Hooks subsystem](../userDataADO/ai.prompt.md).

**Two-stage validation/normalization.** Persisted Hooks are *normalized* leniently by `profileSanitizer.sanitizeHooks` on every read/write (drops malformed hooks with an invalid `event` or `action`, dedups by id, backfills timestamps, defaults provenance — `version` to `1.0.0`, `remoteVersion` to `''`, `source` to `ON-DEVICE` unless explicitly `IN-LIBRARY` — and clamps official `timeout` / legacy `timeoutMs` values to the 600s runtime maximum). CRUD writes additionally *reject* structurally invalid input via `isValidHookDefinition` (`profileEntityCrud.addHook/updateHook`), which strictly requires a string `version` and a `source` of `IN-LIBRARY`/`ON-DEVICE` (and an optional string `remoteVersion`). The guards in `schemas.ts` are the lighter boolean check; they do not mutate.

**Resolution is agent-selected, deterministic.** A Hook is effective for an Agent when its id is present in `ChatAgent.hooks` (selected in the Agent editor Hooks tab, exactly like `skills`/`mcp_servers`). There is no source precedence or multi-level merge. Each Hook is flat: one `event`, one optional `matcher`, one `action`. Order = profile `hooks[]` order → first-wins id dedup. This makes "last successful action wins" aggregation well-defined across the hooks matched for an event.

**Manager is the only surface the Agent Loop touches.** `AgentChat` calls `runHooks(...)` and `isEnabled()` through `AgentHookManager.getInstance()`; it never deals with persistence or resolution. The manager reads the profile library and the master switch through `AgentHookManagerDeps`, so unit tests construct it with fakes. `getInstance()` wires the real caches via `createDefaultDeps()`.

**Layer B wiring (implemented).** The Agent Loop integration lives in `chat/agentChatHookRuntime.ts`, with `chat/agentChat.ts` acting as the host/facade. It stays at the **tool dependency boundary**: `SessionStart` (official `source: 'startup' | 'resume'`, legacy `trigger: 'new' | 'resume'`) and `UserPromptSubmit` run in `startChat`/`streamMessage`; public `streamMessage` captures fresh/resume state before adding the user message so the first turn still emits `startup`/`new`. The three tool deps passed to `createTurnRunner` are wrapped: `preToolUseAndApprove` (PreToolUse → block + `updatedInput` + re-approval on final args, official `permissionDecision: 'allow'` skips normal approval only when the hook did not mutate input, `ask` forces a real user confirmation prompt via the new `requestHookApproval` dep (ask-flagged tool calls are excluded from the batch approval input and routed through `agentChatInteractionService.requestHookApprovalInteraction`, which drives the interaction layer directly and so bypasses the agent's bypass-all batch-approval stub; it fails closed — rejects — when no UI receiver is available or the interaction is blocked by policy, and uses the captured `approvalDecisionReason` as the prompt message), and `defer` makes no hook decision so normal approval runs; the assistant tool-call message is persisted only after this pass so mutated args are what future context sees), `executeToolCallWithHooks` (short-circuits blocked tools with a synthetic denied `role:'tool'` result; PostToolUseFailure on throw), and `postProcessToolResultWithHooks` (PostToolUse → block replaces output with a synthetic denied result; otherwise official `updatedToolOutput` replaces first, legacy `updatedMCPToolOutput` second; returned tool failure objects run PostToolUseFailure instead of PostToolUse). Hook inputs emit official aliases (`session_id`, `agent_type`, `transcript_path`, `permission_mode`, `tool_use_id`, `tool_response`) alongside OpenKosmos legacy fields. Each wrapper calls `isEnabled()` first and delegates byte-identically when OFF. Tool hook calls receive the active turn cancellation as `AgentHookRunContext.signal`, so command/HTTP hooks abort with the turn. Hook `additionalContexts` and `systemMessages` are buffered by scope (session / observational / turn), capped at 32 entries per scope and 4096 chars per entry; turn-scoped buffers clear in `streamMessage` finally.

**Master switch (default OFF).** `profileCacheManager.isHooksEnabled(alias)` reads `profile.json` `hooksEnabled` (default `false`). When disabled, `resolveHooksForAgent` returns `[]` so no command ever runs for that profile. This is the rollout gate — the feature ships dark per profile. The Settings Hooks nav/route remains reachable so users can enable the switch, but the management UI is hidden until ON. The same switch controls `manage_hooks` availability for the active profile. Stale direct calls to `manage_hooks` return a disabled-tool error. The built-in tool intentionally has no action that changes the master switch.

**Phase 2 — IPC contract + renderer UI (implemented).** The management surface is split into a main-side IPC layer and a renderer-side Settings page, joined by a single typed contract.
- **Contract:** `src/shared/ipc/agentHooks.ts` declares `connectRenderToMain<RenderToMain>('agentHooks')` with 6 methods (`listHooks`, `createHook`, `updateHook`, `deleteHook`, `getMasterSwitch`, `setMasterSwitch`) and re-exports the hook types from `profile.ts` via `import type`. This is the single source of truth for both sides. Binding is not part of this contract — Agents store selected Hook ids in `ChatAgent.hooks` via the Agent editor.
- **Main:** `registerAgentHooksIPC(ctx)` (wired in `src/main/startup/ipc/index.ts`) registers the handlers; `hookInputValidation.ts` holds the pure logic. Preload exposes the method whitelist via `src/preload/agentHooks/invoke.ts` → `electronAPI.agentHooks.invoke`.
- **Renderer:** `src/renderer/ipc/agentHooks.ts` exposes a lazy/crash-safe `agentHooksApi` (reads `window.electronAPI?.agentHooks?.invoke` at call time). The Settings page lives at route `/settings/agent-hooks` (registered in `AppRoutes.tsx`, nav entry in `SettingsNavigation.tsx`) and remains reachable while the master switch is OFF so users can enable it; `AgentHooksView` hides the hook-management UI until ON. The master-switch enable confirmation warns that Hooks can run local shell commands and send prompt/tool/session data to remote HTTP endpoints. When ON, the UI mirrors the MCP settings UX: the shared `.unified-header` has a right-side `+` action button. The content body is a true two-column split: `HookListPanel` is the left pane (selectable Hook rows with enabled status dot, single operation summary, and `data-hook-menu-trigger` three-dot button per row) and the right pane **always** shows `HookDetailPanel` (read-only selected Hook operation details). **New/Edit Hook is a separate full-page route view, not an inline panel** — exactly like MCP's `AddNewMcpServerView`. The `+` button and the row menu's **Edit** item `navigate(...)` to dedicated routes `agent-hooks/new` and `agent-hooks/edit/:editHookId` (registered in `AppRoutes.tsx` next to `agent-hooks`), which render `HookEditorView`. `HookEditorView` owns the whole editor lifecycle: it renders its own `.unified-header` (back button + "New Hook"/"Edit Hook" title — `HookEditor` itself no longer renders a title) over the shared `HookEditor` form. Edit mode loads the target via `listHooks()` then `.find(h => h.id === editHookId)` (there is no `getHook` IPC). The editor primary button reads **Create** (new) / **Update** (edit) — `HookEditor` switches on its `isNew` prop. The editor has **no manual enable toggle**; enabling is automatic on save. On a successful **Create**, `HookEditorView` auto-enables the freshly created hook (`updateHook(id, { enabled: true })`) and opens `ApplyHookToAgentsDialog`, mirroring the MCP/Skill "Apply to Agents" flow; if that auto-enable write fails, the editor shows the error and does **not** open the apply dialog. The dialog writes the new hook **id** into each selected agent's `ChatAgent.hooks` (single-agent chats use `chatOps.updateChatAgent`; multi-agent selections are grouped per chat and written once through `chatOps.updateChatConfig` so multiple selected `chat.agents[]` members in the same chat cannot overwrite each other), and on close `HookEditorView` navigates back to `/settings/agent-hooks?selectHook=<id>`. On a successful **Update**, the hook is auto-enabled too — `hookFormModel.formStateToUpdatePatch` always emits `enabled: true` — but the apply dialog is **not** opened (editing an existing, already-bound hook should not re-prompt for agent binding) and `HookEditorView` navigates straight back with `?selectHook=<id>`. To disable a hook, use the row dropdown menu's Enable/Disable toggle, not the editor (saving the editor always re-enables). **Selection** in the list: on open the first hook is default-selected so `HookDetailPanel` is populated; `AgentHooksView` reads a `?selectHook=<id>` query param (via `useSearchParams`, captured once at mount in a ref) and, when it matches a loaded hook, selects it instead of the default first row — this is how the editor returns focus to the created/updated hook (and how the Agent editor Hooks tab's per-item "Manage Hook" gear button deep-links). The per-row three-dot button opens `HookDropdownMenu` (reusing the shared `.dropdown-menu` / `DropdownMenu.css`, positioned via `dropdownPosition.ts` `hookMenu` preset) with **Enable/Disable, Edit, and Delete (danger)** items; Delete routes through a confirm `Dialog`. The row menu closes on outside mousedown — the menu root and the row trigger both `stopPropagation` on mousedown so the document listener only fires for genuine outside targets. All form↔payload mapping + client validation is isolated in the pure `hookFormModel.ts` (one event/matcher/action; command actions support shell-form or exec-form `args`, HTTP actions support URL/method/headers/body, both support an optional `if` permission-rule condition, timeout is official seconds). Styling lives in `src/renderer/styles/AgentHooks.css` (shared `.unified-header` + MCP-like left-list/right-panel split, reusing `Header.css` / `Badge variant="normal"`; `.hook-editor-view-body` is the route view's scroll container).
- **Renderer enable review:** The row menu's **Enable** action on a disabled hook explicitly selects that hook first, then opens a review `Dialog` that renders `HookDetailPanel` for the target hook. `updateHook(id, { enabled: true })` only runs after the user confirms, so a hook cannot be enabled from a row menu while the detail pane is still showing a different hook. The row menu's **Disable** action remains a direct `updateHook(id, { enabled: false })`.
- **Built-in tool:** `manage_hooks` is registered with built-in tool metadata but public inventory accessors hide it while the active profile's `hooksEnabled` is OFF. Inputs are Agent-friendly and flat (`event`, `matcher`, `action_type`, `command`/`url`, optional `if`). Hooks created from **programmatic/import paths** (`manage_hooks` and any future bulk-import path) are always disabled, and `manage_hooks` refuses enable requests; it also refuses event/action edits on already-enabled hooks and refuses disable/delete for enabled or Agent-bound hooks. Enabling or removing persistent automatic execution from those paths requires user review in Settings/Agent editor. (The Settings UI **Create** action is the explicit user-review path, so it auto-enables the hook the user just authored.) The facade does **not** bind hooks to Agents — binding is done by selecting hook ids in the Agent editor Hooks tab (`ChatAgent.hooks`). That tab (`AgentHooksTab.tsx`) renders each hook as a `.skill-card` whose header holds the name plus an `Enabled`/`Disabled` status pill; the long-form description is rendered below the header as a plain `.skill-card-description` text block (not a badge/pill) and is left-aligned under the name. Each card has a hover-revealed `.skill-actions` gear button (`Manage hook <name>`); clicking it dispatches `agent:closeEditor` and navigates to `/settings/agent-hooks?selectHook=<id>` so the Settings page opens with that hook selected (mirrors the Skills per-item manage action). Only **enabled** hooks can be newly bound: a disabled hook's checkbox is disabled (and its card shows a `not-allowed` cursor) so it cannot be selected. A hook that was bound while enabled and later disabled stays checked and can still be **unbound** (the checkbox/card stay interactive when already selected), so users can clean up stale bindings — `handleHookToggle` enforces this (`hook.enabled || isSelected`).

**Safety: hooks must never crash the Agent Loop.** `runCommandHook` and `runHooks` are written to resolve a structured result on every failure path (validation, spawn error, timeout, abort, non-zero exit, stdin EPIPE). Command output is capped at `MAX_HOOK_OUTPUT_BYTES`.

## Official hook protocol interop (implemented)

OpenKosmos aligns key runtime protocol behavior with official hook conventions so manually created command/HTTP hooks can run compatible scripts:

- `commandHookRunner.buildEnv` exports `OPENKOSMOS_WORKSPACE_PATH` (Agent workspace) and `OPENKOSMOS_HOOKS_ARTIFACTS_PATH` (per-profile `<userData>/profiles/<alias>/hooks-artifacts`, created on first use), and substitutes both `${OPENKOSMOS_WORKSPACE_PATH}` and `${OPENKOSMOS_HOOKS_ARTIFACTS_PATH}` placeholders in shell-form commands and exec-form args. `agentHookManager.runHooks` derives the artifacts path from `context.userAlias` via `getHooksArtifactsPath`; resolution failures fall back to an empty string and never crash the Agent Loop.
- `agentHookExecutor.buildActionOutcome` treats a command **exit code 2** as a blocking error (the first non-empty stderr line becomes the block reason; a default reason otherwise), matching the official primary block mechanism.
- A successful hook's **plain stdout** is ignored for context safety; hooks must emit structured JSON with `hookSpecificOutput.additionalContext` to inject context. JSON stdout flows through `parseHookOutput`/`aggregateHookOutcomes`.

## Phase 3 — extended actions + events (implemented)

Phase 3 (tech-doc §18) is **partially implemented**, faithful to the doc's "if needed" gating:

**Implemented — HTTP action type (item 3).** `HookAction` is now a discriminated union `CommandHookAction | HttpHookAction` (`type: 'command' | 'http'`). HTTP actions carry `url` + optional `method`/`headers`/`body`/official `timeout` seconds (legacy `timeoutMs` still read). They are validated (`isHttpHookAction`/`validateHttpAction`/`sanitizeHttpHookAction` with URL + header + body bounds and the SSRF host blocklist), executed by `httpHookRunner.runHttpHook`, dispatched in `executeHooksForEvent.runAction`, and surfaced in the renderer (`hookFormModel` single-operation form + `HookEditor` action-type selector with URL/method/headers/body fields). HTTP responses flow through the **same** `parseHookOutput`/`aggregateHookOutcomes` protocol as command stdout, so blocking/`updatedInput`/`additionalContext` all work identically.

**Implemented — observational lifecycle events (item 4, partial).** `Stop`, `PreCompact`, and `PostCompact` are wired end-to-end. They are **observational only**: `AgentChatHookRuntime` buffers their `additionalContexts` and `systemMessages` at **session scope** (surviving the per-turn reset, with oldest-first eviction) and **ignores** blocking/mutation fields (`Stop`/compaction cannot block the loop — PRD only specs blocking for `UserPromptSubmit`/`PreToolUse`/`PostToolUse`). `Stop` fires in `streamMessage` after `runStreamMessage` resolves (so not on cancel/error, which throw earlier). `PreCompact`/`PostCompact` fire via the optional `onBeforeCompaction`/`onAfterCompaction` deps on `agentChatContextService` — `onBefore` before `compressContextHistoryWithFullMode`, `onAfter` only after a successful compaction — both with `trigger: 'auto' | 'manual'` (manual = forced compaction). Compaction callbacks swallow errors (`invokeCompactionCallback`) so a misbehaving hook can never break compaction.

**Still deferred (no code) — documented scope decisions:**
- **LLM `prompt` + `agent` (subagent) action types (items 1–2)** — explicitly *out of MVP* (PRD §6.2/§9.3) and officially **experimental** in the Agent Hooks standard. **The official `agent` handler type maps to a OpenKosmos *subagent*** (`SubAgentManager.spawnAdhocSubAgent`, surfaced today via the `sub_agent` builtin tool): an `agent` hook carries a `prompt` (+ optional `model`) and spawns a subagent that uses tools to verify a condition and return a decision. OpenKosmos **does** own this surface — the gap is wiring, not capability (see "Add the `agent` (subagent) action type"). The `prompt` type is a single-turn LLM evaluation with no subagent. The `HookAction` union extends additively when one is needed.
- **`mcp_tool` action type** — calls a tool on an already-connected MCP server and treats its text output like command stdout. Deferred; needs an MCP-client bridge from the runner.
- **Sub-agent events (`SubagentStart`/`SubagentStop`)** — these are *events* (matched on agent type), not the `agent` handler. Emission would live in `SubAgentManager` (which is below the coverage gate's 90% bar) and is conceptually close to `PreToolUse`/`PostToolUse` on the `sub_agent` tool. The data model intentionally does **not** declare these literals yet; add them with the matching `SubAgentManager` wiring + tests when needed.

## Common Changes

- **Add a new lifecycle event:** add the literal to `AgentHookEvent` (in `userDataADO/types/profile.ts`), to `VALID_EVENTS`/`VALID_HOOK_EVENTS` (in `schemas.ts` and `profileSanitizer.ts`), to `VALID_EVENTS` + `HOOK_EVENTS` (`hookInputValidation.ts` / `hookFormModel.ts`), define a `*HookInput` interface + extend the `AgentHookInput` union in `types.ts`, extend `getMatchQueryForInput`, then integrate the call site in `chat/agentChat.ts`. For a **blocking/mutating** event follow the tool-dep wrappers; for an **observational** event (no block/mutate) route the result through `applyObservationalHookResult` (session-scoped) like `Stop`/`PreCompact`/`PostCompact`.
- **Add a new action type (e.g. LLM/prompt) — Phase 3:** extend the `HookAction` union in `profile.ts` (add a `type` discriminant + sibling interface), add a guard in `schemas.ts` (`isHookAction`), normalize it in `profileSanitizer.sanitizeHookAction`, validate it in `hookInputValidation.validateAction`, add a runner (mirror `httpHookRunner.ts`: never throw, return a `CommandHookResult`), inject + dispatch it in `executeHooksForEvent.runAction` (and thread the runner through `agentHookManager`), then surface it in `hookFormModel.ts` (`HOOK_ACTION_TYPES` + row mapping) + `HookEditor.tsx` (action-type selector branch). The `command` and `http` types are the existing templates.
- **Add the `agent` (subagent) action type — maps to OpenKosmos subagent:** the official `agent` handler (`{ type: 'agent', prompt, model? }`) spawns a subagent that verifies a condition and returns a decision. Implement it as a new `AgentHookAction` following the recipe above, with a `subAgentHookRunner.ts` that calls `SubAgentManager.getInstance().spawnAdhocSubAgent({ task: prompt, model, parentSessionId, parentChatId, userAlias, eventSender, cancellationToken, ... })` using `BuiltinToolsManager.getExecutionContext()` (available because hooks fire inside `agentChat.ts`), then maps the subagent's text result into a `CommandHookResult` so the existing `parseHookOutput`/`buildActionOutcome` protocol applies (structured JSON decision → block/context; plain text ignored unless a future product decision changes the protocol). **Before implementing, resolve these product decisions** (they are why it is deferred): sync-blocking vs `async` fire-and-forget (a subagent turn can take 60s+), whether an `agent` hook may *block* the loop or is context-only, and the recursion policy (a subagent must not re-enter the same `agent` hook — gate on `context.isSubAgent`). The official feature is itself flagged experimental. **Do not collapse `agent` into `command`.**
- **Add a sub-agent lifecycle event (`SubagentStart`/`SubagentStop`):** distinct from the `agent` handler — these are *events* matched on agent type. Follow "Add a new lifecycle event" and emit from `SubAgentManager` (`subAgentLifecycle.ts`). For OpenKosmos, `PreToolUse`/`PostToolUse` on the `sub_agent` tool already cover most of this need.
- **Expose more CRUD to the renderer:** add a method to the `RenderToMain` map in `src/shared/ipc/agentHooks.ts`, a handler in `agentHooksIpc.ts`, whitelist it in `src/preload/agentHooks/invoke.ts`, and call it from `src/renderer/ipc/agentHooks.ts` / `AgentHooksView.tsx`. Keep validation in the pure `hookInputValidation.ts`.
- **Change command sandboxing:** edit `DANGEROUS_PATTERNS` / `validateHookCommand` in `commandHookRunner.ts` (kept aligned with `executeCommandTool`).

## Gotchas

- **`sanitizeProfileV2` is the persistence gate during the load window.** `profile.hooks` must remain listed in the object `sanitizeProfileV2` rebuilds, or the transient hook slice mirrored onto the raw profile by `loadHookRegistryForProfile` is stripped *before* `HooksConfigManager` can migrate it — losing legacy inline hooks on first load. Tests guard this. (After sanitization, `ProfileCacheManager.readProfileFromFile` deliberately `delete`s `sanitizedProfile.hooks` so the cached profile carries no hook-list facade; the durable list lives in `hooks.json`. `hooksEnabled` is **never** stripped.)
- **Hooks are bound from the Agent side.** `ChatAgent.hooks: string[]` stores the selected Hook **ids** (mirroring `skills`/`mcp_servers`); the resolver matches those ids against the profile Hook library. There is no binding data on the Hook itself. The Agent editor Hooks tab (`AgentHooksTab.tsx`) is the only UI that writes `agent.hooks`.
- **`setHookAdditionalContexts` REPLACES, not appends.** When Layer B injects `additionalContexts`, it must append + consume, never blindly overwrite the prompt-context buffer.
- **Never insert a message between an assistant `tool_calls` and its tool results** (API 400). PreToolUse `additionalContext` must be routed through the prompt-context buffer, and every blocked PreToolUse tool still needs a `role:'tool'` message with the exact `tool_call_id`.
- **`createDefaultDeps` swallows cache errors** (returns `[]` / `false`). Tests that exercise the real-cache closures must `vi.mock` both cache modules. `getHooks` resolves through `profileCacheManager.getHooks` → `hooksConfigManager.getHooks` (the durable list now lives in `hooks.json`), while `isEnabled` reads `profile.json` `hooksEnabled`; a test that needs both must account for the two different stores.
- **Command runner tests** prefer a mocked `child_process.spawn` (deterministic branches: error/close/timeout/abort/cap) plus a small real-process integration smoke test that uses `process.execPath` / `node -e` instead of POSIX-only commands so Windows runs stay green.
- **HTTP runner tests** mock `global.fetch` (restore in `afterEach`); cover `validateHookUrl` host-blocklist arms, the pre-start abort short-circuit, GET-sends-no-body vs custom method/body, header merge, timeout/parent-abort (a `fetch` that rejects on `init.signal` abort), and `readCappedBody` truncation.
- **Observational events never block.** `Stop`/`PreCompact`/`PostCompact` only buffer `additionalContexts` (session scope); their `blockingError`/`preventContinuation`/`updatedInput`/`updatedToolOutput`/`updatedMCPToolOutput` are intentionally ignored. Do not route them through the blocking tool-dep wrappers. `Stop` fires *after* `runStreamMessage` resolves (outside the `finally`), so it is skipped on cancel/error and does not double-fire on a `UserPromptSubmit` block (that path returns early).
- **Exit code 2 is the only "blocking exit code".** `buildActionOutcome` maps `exitCode === 2` to a `decision:'block'` outcome; any other non-zero exit is a non-blocking failure and its stdout/JSON is ignored. HTTP runner results carry the HTTP status as `exitCode` (always >=100), so they never collide with the exit-2 rule. Successful hooks must emit structured JSON with `hookSpecificOutput.additionalContext` to inject context; plain non-JSON stdout is ignored for every event, including `SessionStart` and `UserPromptSubmit`.
- **`manage_hooks` must not enable the master switch.** Keep the switch in user-facing Settings only. A model-created persistent command hook plus model-controlled master-switch enable would create a durable command-execution path without explicit user activation.
