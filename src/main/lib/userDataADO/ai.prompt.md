# userDataADO — Layer 2 Module Documentation

Central data persistence and profile management layer for the main process.
Owns all reads/writes to `profile.json`, chat session files, app config, and skills metadata.
Nearly every other main-process module depends on this layer.

## Architecture

### Storage Layout

```
{userData}/
├── app.json                                  # AppCacheManager — app-level runtime config, including UI language
└── profiles/{userAlias}/
    ├── profile.json                          # ProfileCacheManager — profile data (incl. the archive list `archived_chats[]`, the SSOT) EXCEPT installed global MCP servers, global skill registry, global Agent Hook library, and per-chat skill snapshots (the Hooks master switch hooksEnabled DOES stay here)
    ├── mcp.json                              # McpConfigManager (via mcpFileStore) — installed global MCP servers { version, updatedAt, mcp_servers: McpServerConfig[] }, own updatedAt
    ├── skills.json                           # SkillsConfigManager (via skillsFileStore) — global skill registry { version, updatedAt, skills: SkillConfig[] }, own updatedAt
    ├── hooks.json                            # HooksConfigManager (via hooksFileStore) — global Agent Hook library { version, updatedAt, hooks: HookDefinition[] }, own updatedAt (hooksEnabled stays in profile.json)
    ├── agents/                               # AgentStoreManager — standalone agents (1 Chat : N Agents)
    │   ├── index.json                        # single agents index { agents: [{ id, name }] } (all agents; archive is a chat concept, agents have no archived state)
    │   └── {agentId}/                        # agentId = stable UUID `agent_{timestamp}_{random}` for new agents (minted at creation, name-independent so renames keep it); legacy migrated agents keep their name-derived `agent-{name}-{source}` id
    │       ├── agent.json                    # AgentConfig (extracted/hydrated from chats[].agent)
    │       └── knowledge/                    # per-agent knowledge
    ├── chat_workspaces/{chatId}/             # chat-scoped working dirs (keyed by chat_id)
    ├── chat_sessions/{chatId}/
    │   ├── index.json                        # ChatSessionManager — chat-level month index
    │   └── {YYYYMM}/
    │       ├── index.json                    # ChatSessionManager — month-level session metadata
    │       └── {chatSessionId}.json          # ChatSessionFileOps — full session file
    └── skills/{skill-name}/                  # Skill package directories
```

`chat_id` format: `chat_{YYYYMMDDHHmmSS}_{deviceId}_{random}`.
`chatSessionId` format: `chatSession_{YYYYMMDDHHmmSS}_{deviceId}_{random}`.
`schedule job id` format for newly created schedules: `sched_{YYYYMMDDHHmmSS}_{deviceId}_{random}`.
Month indexing still derives from the leading `YYYYMM` segment, and legacy `chatSession_{YYYYMMDDHHmmSS}` plus legacy `sched_{YYYYMMDDHHmmSS}_{random}` IDs remain readable for backward compatibility.

### Agent/Chat separation (`AgentStoreManager` + `agents/`)

`profile.json.chats[]` map chats to agents (1 Chat : N Agents) via `ChatConfig.agent_ids`. Standalone agents live under `agents/{id}/agent.json` with a single `index.json` (all agents; archive is a chat-only concept so agents have no archived state), owned by **`agentStoreManager.ts`** (Electron-free, path-takes-`profileDir`). Migration **V6** derives `agent_ids` from inline `agent`/`agents`; on every load `ProfileCacheManager.ensureV2ProfileIntegrity` runs `runAgentStoreMigrations`, which sequences `consolidateLegacyAgentIndexes` (merge any legacy `index_active.json`+`index_archived.json` into the single `index.json`, then delete the split files), `extractAgentsToStore` (mirror inline→store, idempotent), `hydrateChatsFromStore` (rebuild inline from store via `agent_ids`), `ensureChatAgentIds` (heal missing ids), `consolidateWorkspaceDirsToChatId`, `migrateKnowledgeToAgentStore`, `migrateArchivedAgentsToStore` (migrate legacy archived agents into the single `index.json` — one `agents/{id}/` dir each — and move the archive list onto `profile.archived_chats`, the SSOT; two-phase, retiring the transitional `agents/archived_chats.json` / legacy `archive/archived_agents.json` only after the profile durably owns the list), and `repointCrossAgentKnowledge` (follow any cross-agent `knowledgeBase` to the referenced agent's migrated knowledge), then refreshes the in-memory registry — making the store authoritative. CRUD keeps the mirror consistent: **`addChatConfig` (create) is store-first** — it calls `persistNewChatAgents` to write the new chat's inline agent(s) into `agents/{id}/` and register `agent_ids` at creation time, derives the chat workspace from the **`chat_id`-keyed** `getDefaultWorkspacePath` (runtime/cache only, not persisted), and sets the agent knowledge to the **store-keyed** `getAgentKnowledgePath` (`agents/{id}/knowledge`), so a brand-new agent conforms to the separated model immediately (the very next `writeProfileToFile` strips its inline copy) instead of waiting for the next-load migration; `persistNewChatAgents` never prunes, so a chat that references an existing shared agent by id only keeps it. `updateChatAgent` write-throughs the edited agent and re-stamps `agent_ids` via `syncChatAgentsToStore` (a rename KEEPS the agent's carried id — `agent_ids` is unchanged and no store entry is pruned; only the `agent.json` content is rewritten); `deleteChatConfig` removes the chat→agent mapping from `profile.json`, then after that profile write is durable cleans chat-owned resources: chat session files, the derived chat workspace, schedule jobs, SubAgentTaskStore records, memex memory, and the `agents/{id}/` store directory for each agent id not referenced by another active or archived chat. Shared agents are skipped so deleting one chat never breaks another chat that still references the same agent. **On disk `profile.json.chats[]` carries only `chat_id` + `agent_ids`**: `writeProfileToFile` calls `stripDerivedChatWorkspacesForDisk` plus `stripInlineChatAgentsForDisk`, so workspace and inline `agent`/`agents` are not persisted once the store durably holds every id (read-only durability gate; chats with unseeded agents keep inline) — same strip-on-write / re-attach-on-read pattern as mcp_servers/skills/hooks. The cache and renderer push stay `agent_ids`-only for agents but carry a derived runtime `workspace`; main consumers resolve agents through `agentAccessor`, and renderer consumers resolve through the sidecar agent cache/bridge. Knowledge target is `agents/{id}/knowledge` (`getAgentKnowledgePath`); legacy `chat_workspaces/{agentId|chat_id}/knowledge` is physically relocated into it by `migrateKnowledgeToAgentStore` on load (idempotent), which also repoints the inline and store `agent.json` `knowledgeBase` when it pointed at the chat's OWN legacy dir (user-custom external paths preserved). A cross-agent `knowledgeBase` (one agent referencing ANOTHER agent's dir, e.g. an active agent sharing an archived agent's docs) is NOT used to claim dir ownership — `legacyWorkspaceDirNames` derives owned dirs only from agent ids + legacy workspace fields — and the reference is instead repointed by the final `repointCrossAgentKnowledge` pass to follow the referenced knowledge to its new store home, but only when that knowledge actually migrated (this fixed the MS Agency ↔ M365 corruption where a `knowledgeBase` cross-link made an active agent absorb an archived agent's sessions + knowledge).

### Skills subsystem (`SkillsConfigManager` + `skills.json`)

The global skill registry is owned end-to-end by **`SkillsConfigManager`** (singleton `skillsConfigManager`), which is the **only** writer of `skills.json`. `ProfileCacheManager` writes only `profile.json`. The renderer/IPC wire contract is unchanged: both the `profile:cacheUpdated` push **and** the `profile:getProfile` IPC read still carry `skills`, injected from `skillsConfigManager.getSkills(alias)`.

1. On-disk format changes go in `skillsFileStore.ts` (`SkillsFileV2`, `sanitizeSkillEntries`, `fingerprintSkills`, `readSkillsFile`, `writeSkillsFile`, `loadSkillsForProfile`). Keep `fingerprintSkills` the canonical dirty-check key and make sure it **excludes** `updatedAt` — if the fingerprint includes the timestamp, every write looks changed and the dirty-check never skips.
2. Runtime behavior (cache, CRUD, load handoff, dirty-checked write) lives in `skillsConfigManager.ts`. All persistence funnels through the private disk-first `persistSkills` (`sanitizeSkillEntries` → `fingerprintSkills` dirty-check → `writeSkillsFile` with a fresh `updatedAt` → registry + `lastFingerprint` after success); add new mutators by taking the manager's own `withWriteLock` and calling `persistSkills`, never by writing `skills.json` directly.
3. The load handoff lives in `ProfileCacheManager.readProfileFromFile`: the registry is first resolved into memory via `skillsConfigManager.resolveFromDisk(alias, legacySkillSlice)` **before** the `mcp.json` commit gate (mirroring the MCP `resolveFromDisk`), so a transient `mcp.json` write failure — which returns early from the load — can never leave the registry empty (consumers read only the manager, so an empty registry would hide installed skills and let a follow-up CRUD overwrite `skills.json` from scratch). On the success path past the gate, `skillsConfigManager.loadForAlias(alias, rawProfile)` then reads `skills.json` or migrates legacy inline `profile.skills`, mirrors the resolved skills onto `rawProfile` only so `ensureV2ProfileIntegrity` / `sanitizeProfile` can run, then `delete sanitizedProfile.skills` before caching. The cached `ProfileV2` no longer carries a skills facade; main-process consumers must use `skillsConfigManager.getSkills(alias)` / `getSkill(alias, name)` / `hasSkill(alias, name)`.
4. CRUD orchestration mirrors MCP in `profileEntityCrud.ts`: `addSkillConfig` / `updateSkillConfig` / `deleteSkillConfig` gate via `ensureProfileLoadedForConfigCrud`, delegate the write to `SkillsConfigManager`, invalidate affected in-memory snapshots with `chatSkillSnapshotStore.invalidateAffectedChats(alias, profile.chats, [skillName])`, then notify the renderer (add debounced, update/delete immediate). `ProfileCacheManager.addSkill` / `updateSkill` / `deleteSkill` are thin delegators to these wrappers.
5. Do not write the top-level `skills` field into `profile.json`, and do not touch nested `chat.agent.skills` bindings (those stay in `profile.json`). A pure skill-registry change rewrites only `skills.json`; an unrelated profile edit rewrites only `profile.json`; each file advances only its own `updatedAt`.
6. Sync copies the whole profile directory (except `.git`), so `skills.json` and skill package directories sync automatically with no filter change.

#### In-memory chat skill snapshots

Per-chat skill snapshots are rebuildable runtime cache, not profile data. `ChatConfig.skill_snapshot` was removed from `types/profile.ts`; old persisted `skill_snapshot` objects are ignored by sanitization and drop on the next profile write. `chatSkillSnapshotStore.ts` owns `Map<alias, Map<chatId, ChatSkillSnapshot>>` with `get`/`set`/`clear`, alias/global clear, and affected-chat invalidation. `agentChatPromptService.refreshSkillSnapshotIfNeeded()` rebuilds from `chat.agent.skills` plus `skillsConfigManager.getSkills(alias)` at turn boundaries and stores only changed signatures; `getAgentSpecificSystemPrompt()` injects `chatSkillSnapshotStore.get(alias, chatId)?.prompt`.

### Hooks subsystem (`HooksConfigManager` + `hooks.json`)

The global Agent Hook *library* (the per-profile registered `HookDefinition[]`) is owned end-to-end by **`HooksConfigManager`** (singleton `hooksConfigManager`), which is the **only** writer of the hook list in `hooks.json`. It is a near-exact mirror of the Skills subsystem, with **one deliberate difference: the Hooks master switch `ProfileV2.hooksEnabled` STAYS in `profile.json`** — only the hook *list* moves to `hooks.json`. The renderer/IPC wire contract is unchanged: both the `profile:cacheUpdated` push **and** the `profile:getProfile` IPC read still carry `hooks`, injected from `hooksConfigManager.getHooks(alias)`, while `hooksEnabled` flows through the profile body untouched.

1. On-disk format changes go in `hooksFileStore.ts` (`HooksFileV2`, `sanitizeHookEntries`, `fingerprintHooks`, `readHooksFile`, `writeHooksFile`, `loadHooksForProfile`). `sanitizeHookEntries` is an alias for the canonical `sanitizeHooks` in `profileSanitizer.ts` — **reuse it, do not fork** the hook action/event/timeout validation (single source of truth). Keep `fingerprintHooks` the canonical dirty-check key and make sure it **excludes** `updatedAt` — if the fingerprint includes the timestamp, every write looks changed and the dirty-check never skips.
2. Runtime behavior (cache, CRUD, load handoff, dirty-checked write) lives in `hooksConfigManager.ts`. All persistence funnels through the private disk-first `persistHooks` (`sanitizeHookEntries` → `fingerprintHooks` dirty-check → `writeHooksFile` with a fresh `updatedAt` → registry + `lastFingerprint` after success); add new mutators by taking the manager's own `withWriteLock` and calling `persistHooks`, never by writing `hooks.json` directly. Hook CRUD is id-keyed: `addHook` rejects a duplicate id and validates via `isValidHookDefinition`, stamping `createdAt`/`updatedAt`; `updateHook` refreshes `updatedAt`.
3. The load handoff lives in `ProfileCacheManager.readProfileFromFile`: the registry is first resolved into memory via `hooksConfigManager.resolveFromDisk(alias, legacyHookSlice)` **before** the `mcp.json` commit gate (mirroring MCP/skills), so a transient `mcp.json` write failure — which returns early from the load — can never leave the registry empty. On the success path past the gate, `loadHookRegistryForProfile(alias, rawProfile)` reads `hooks.json` or migrates legacy inline `profile.hooks`, mirrors the resolved hooks onto `rawProfile` only so `ensureV2ProfileIntegrity` / `sanitizeProfile` can run, then `delete sanitizedProfile.hooks` before caching (**`hooksEnabled` is NOT stripped**). The cached `ProfileV2` no longer carries a hook-list facade; main-process consumers must use `hooksConfigManager.getHooks(alias)` / `getHook(alias, id)` / `hasHook(alias, id)`.
4. CRUD orchestration lives in `profileHookCrud.ts`: `getHooks` reads the manager directly; `addHook` / `updateHook` / `deleteHook` gate via `ensureProfileLoadedForConfigCrud`, delegate the write to `HooksConfigManager`, then notify the renderer. `isHooksEnabled` / `setHooksEnabled` are unchanged and still read/write `hooksEnabled` on `profile.json` through `withProfileWriteLock()` + `writeProfileThenCommitCache()`. `ProfileCacheManager` exposes these via `entityCtx()`.
5. Do not write the top-level `hooks` *list* into `profile.json`, and do not touch nested `chat.agent.hooks` bindings (those stay in `profile.json`, are selected Hook ids, and are owned by Agents). **Do** keep writing `hooksEnabled` to `profile.json`. A pure hook-library change rewrites only `hooks.json`; an unrelated profile edit (including a master-switch toggle) rewrites only `profile.json`; each file advances only its own `updatedAt`.
6. The `writeProfileToFile` durability guard mirrors mcp/skills: before stripping the inline `hooks` slice it commits `hooks.json` first (`!hooksConfigManager.hasPersistedHooks(alias) && hasHooksLoaded(alias)` → `tryCommitHooks`), and aborts the profile write if that commit fails, so the legacy slice survives on disk for a retry.
7. Sync copies the whole profile directory (except `.git`), so `hooks.json` syncs automatically with no filter change.



`ProfileCacheManager` keeps the sanitized `ProfileV2` object in memory without sidecar-owned top-level registries.
On any mutation, a 500 ms debounced batch notification is sent to all `BrowserWindow` instances via IPC.
The renderer's `ProfileDataManager` applies a further 200 ms debounce before notifying React components.
**Total maximum UI lag: ~700 ms.**

### IPC Notification Pattern

```
ProfileCacheManager.save()
  → scheduleNotifyFrontend()   // 500 ms debounce, main process
  → webContents.send('profile:updated', payload)
      → ProfileDataManager (renderer)
          → 200 ms debounce
          → React components re-render
```

`AppCacheManager` uses the same pattern for app-level `app.json` and pushes `app:configUpdated` to the renderer. Its `appearance.themeSource` path also synchronizes Electron `nativeTheme.themeSource` and the main `BrowserWindow` background color, because the macOS hidden titlebar/traffic-light strip is outside the renderer DOM and will otherwise keep the light default while the app content is dark.

### Profile Migration V1 → V2

`isProfileV2()` detects the format on load.
If a V1 profile is found, `ProfileCacheManager` migrates it automatically to the V2 `AuthData` structure before caching.
No manual migration step is required.

### Portable Path Conversion

`portablePath.ts` compares the stored absolute paths in `profile.json` against the current `userData` root.
If a mismatch is detected (e.g., the OS user account was renamed), paths are rewritten in-place before use.

### `@OPENKOSMOS_*` Placeholder Substitution

`openkosmosPlaceholders.ts` is called by `AgentChat` at turn boundaries to expand placeholders in rendered system prompts. Persisted `ChatAgent.system_prompt` is a file map (`Base.md`, `AGENTS.md`); render it before placeholder substitution.
Supported placeholders:

| Placeholder | Type | Resolves To |
|-------------|------|-------------|
| `@OPENKOSMOS_PROFILE_WORKSPACES_FOLDER` | PATH | `{userData}/profiles/{alias}/chat_workspaces` |
| `@OPENKOSMOS_REDDIT_CLIENT_ID` | STRING | `process.env.REDDIT_CLIENT_ID` |
| `@OPENKOSMOS_REDDIT_CLIENT_SECRET` | STRING | `process.env.REDDIT_CLIENT_SECRET` |
| `@OPENKOSMOS_DATA_AI_API_KEY` | STRING | `process.env.DATA_AI_API_KEY` |
| `@OPENKOSMOS_UNWRAP_ACCESS_TOKEN` | STRING | `process.env.UNWRAP_ACCESS_TOKEN` |

## Common Changes

### Adding a New Field to the Profile

1. Add the interface and default value to `types/profile.ts`.
2. Update `DEFAULT_PROFILE_V2` with the default.
3. In `ProfileCacheManager`, add a getter/setter pair and call `scheduleNotifyFrontend()` after any write.
4. Update the `integrityEnsure` block in `ProfileCacheManager` to back-fill the field for existing profiles that pre-date the change.

Confirmation suppression flags should be grouped under `confirmationSettings` in `profile.json`, not added as standalone top-level booleans. Current example: `confirmationSettings.inlineEditRegenerate.skipConfirmation`.

Agent knowledge-related settings are grouped under the agent config (`AgentConfig.knowledge.knowledgeBase` / legacy inline `chat.agent.knowledge` during migration). Chat workspaces are separate and derived from `{profile}/chat_workspaces/{chat_id}` at runtime; do not add new persisted workspace fields to `profile.json` chats or `agents/{id}/agent.json`. Removed legacy Teams/Outlook fields should be stripped during normalization rather than reintroduced on `chat.agent`.

Model-tunable behavior owned by the active model (not the agent persona) is persisted as a top-level field on `ChatAgent`. The current example is `ChatAgent.reasoningEffort?: string`, canonicalized to lowercase on read and write; `undefined` means "do not send a reasoning_effort parameter" so the server-side default applies. The renderer reads it via `profileDataManager.getReasoningEffort(chatId)` (defensive `.toLowerCase()` on read for legacy mixed-case values). The chat engine consumes it through `agentChat.getCurrentModelConfig()` → `agentChatStreamingService.buildReasoningParams()` (see [Chat Engine](../chat/ai.prompt.md) and [LLM](../llm/ai.prompt.md)).

### Adding a New `@OPENKOSMOS_*` Placeholder

1. Add the enum member to `OpenKosmosPlaceholder` in `openkosmosPlaceholders.ts`.
2. Register its `PlaceholderType` in `PLACEHOLDER_METADATA`.
3. Implement the resolver in `getPlaceholderValue`.

### Adding a New App-Level Config Field

1. Add the field to `AppConfig` and its default in `types/app.ts`.
2. Update `isAppConfig` type-guard if needed.
3. Add a getter/setter to `AppCacheManager`; the setter must call `notifyFrontend()`.
4. Wire the field into **all three** hardcoded per-field sites in `AppCacheManager`: `integrityEnsure` (fill/merge defaults), `appConfigSanitize` (coerce/retain the field), and `updateConfig` (merge/assign writes). **The merge is per-field hardcoded — skipping it silently drops writes to the new field.** Scalar fields such as `uiLanguage` still need explicit handling; object-valued fields should follow the `voiceInput` / `VoiceInputSettings` deep-merge pattern.

If the new field is a **user-facing master switch that gates a built-in tool** (like the per-profile `browser.enabled` / `memex.enabled` / `computerUse.enabled`), it belongs at the **profile level**, not the app level: add it to `ProfileV2` in `types/profile.ts`, sanitize it in `profileSanitizer.ts`, add CRUD in `profileSettingsCrud.ts` + delegates in `profileCacheManager.ts`, expose IPC in `startup/ipc/profile.ts` + `preload/main.ts`, and read it in the renderer via `useProfileData()`. Critically, the renderer must call `mcpClientCacheManager.refresh()` in `profileDataManager.handleProfileCacheUpdate` when the switch flips between the previous and next profile, or the Agent page tool list stays stale until the next chat switch.

### Changing Chat Session Storage

`ChatSessionFileOps` is keyed by `userAlias`. Any path restructuring must also update the helpers in `pathUtils.ts` (`getChatSessionFilePath`, `getChatSessionsMonthPath`, etc.) and the index maintenance logic in `ChatSessionManager`.

### Creating a New Chat / Agent (`addChatConfig`)

New-agent creation is **store-first** — the agent dir + chat→agent mapping are created at creation time, NOT deferred to the next-load migration:

1. The renderer custom-agent creation flow calls `chatOps.addChatConfig` with a full inline `agent` and no `agent_ids`.
2. `addChatConfig` mints a stable id for each inline agent (`ensureInlineAgentIds`→`buildAgentUuid`), derives the runtime chat workspace by `chat_id` (`getDefaultWorkspacePath(alias, chat_id)`, stripped before disk write) and the agent knowledge by store id (`getAgentKnowledgePath(alias, agentIdOf(agent))` = `agents/{id}/knowledge`).
3. It then calls `persistNewChatAgents(profileDir, chatConfig)`, which writes each inline agent into `agents/{id}/` (`agent.json` + `knowledge/` + `index.json` entry) and stamps `chat.agent_ids` from them. It is **create-safe**: it NEVER prunes/deletes, so a chat that references an existing shared agent by id only (no inline) keeps that agent.
4. `writeProfileToFile` → `stripDerivedChatWorkspacesForDisk` + `stripInlineChatAgentsForDisk` then drops the runtime workspace and inline copy on the very first write (the store now durably holds the id), so `profile.json.chats[]` carries only `chat_id` + `agent_ids`.

Do NOT call `syncChatAgentsToStore` on the create path — its prune step would `deleteAgent` any id in `chat.agent_ids` not derived from the inline agents, destroying a shared/referenced agent. Use `persistNewChatAgents` for create, `syncChatAgentsToStore` only for edits.

### Moving Workspace or Knowledge Paths

Workspace is chat-owned; knowledge is agent-owned.

1. Do not write workspace changes to `profile.json`; the chat workspace is fixed at `getDefaultWorkspacePath(alias, chat_id)`. Legacy `agent.workspace` / `chat.workspace` input is accepted only as migration compatibility and stripped before disk write.
2. Write knowledge changes through `updateChatAgent` with `agent.knowledge.knowledgeBase`; `writeAgent` persists it in `agents/{id}/agent.json`.
3. Keep `agentStoreManager.writeAgent` stripping `workspace` and `profileSanitizer.sanitizeChatAgent` deleting it so no new caller can persist a working directory on an agent.
4. Runtime consumers must resolve working directories with `getChatWorkspace(chatConfig)` and knowledge directories from the resolved agent. Do not read `agent.workspace` outside migration/fallback helpers.



Installed global MCP servers are owned end-to-end by **`McpConfigManager`** (singleton `mcpConfigManager`), which is the **only** writer of `mcp.json`. `ProfileCacheManager` writes only `profile.json`. The renderer/IPC wire contract is unchanged: both the `profile:cacheUpdated` push **and** the `profile:getProfile` IPC read still carry `mcp_servers`, **injected from the manager** — so this stays a main-process concern, never add an IPC/renderer change for it.

1. On-disk format changes go in `mcpFileStore.ts` (`McpFile`, `serializeMcpFile`, `fingerprintMcpServers`, `readMcpFile`). Bump `MCP_FILE_VERSION` for a real format change and handle the old shape in `readMcpFile`. Keep `fingerprintMcpServers` the canonical dirty-check key and make sure it **excludes** `updatedAt` (and anything else volatile) — if the fingerprint ever includes the timestamp, every write looks "changed" and the dirty-check never skips.
2. Runtime behavior (cache, CRUD, load handoff, dirty-checked write) lives in `mcpConfigManager.ts`. All persistence funnels through the private disk-first `persistServers` (`sanitizeMcpServerList` → `fingerprintMcpServers` dirty-check → `writeMcpFile` with a fresh `updatedAt` → cache + `lastFingerprint` only after success); add new mutators by taking `withWriteLock` and calling `persistServers`, never by writing `mcp.json` directly. CRUD reads must go through `getServers` / `getServerInfo`, never `ProfileV2.mcp_servers`.
3. The load handoff lives in `ProfileCacheManager.readProfileFromFile` (`resolveFromDisk(alias, legacySlice)` → transient `rawProfile.mcp_servers` attach → **early** `commitResolvedServers` → `ensureV2ProfileIntegrity` commits post-migration MCP configs before profile write → `delete sanitizedProfile.mcp_servers` → prime `lastProfileFingerprint`). Keep the transient attach **before** `ensureV2ProfileIntegrity` (so V1/V4 migrations see installed server configs) and the strip **after** the post-migration MCP commit. The **early** commit persists `mcp.json` *before* `ensureV2ProfileIntegrity` can write a stripped `profile.json`, so an upgrade-time `mcp.json` write failure can't lose installed server configs from both files. The **post-migration** commit must happen before writing `profileMigrationVersion`; if it fails, return the pre-migration valid profile and leave profile.json/mcp.json retryable. `writeProfileToFile` retries a pending handoff before any later strip and aborts if it still cannot persist `mcp.json`. Prime `lastProfileFingerprint` from the **re-sanitized** profile (`this.sanitizeProfile(...)`) so the load-time prime and the write-time check hash the identical canonical shape.
4. Do not write the top-level `mcp_servers` field into `profile.json`, and do not touch nested `chat.agent.mcp_servers` bindings (those stay in `profile.json`). When changing `getServers` consumers, repoint them to `mcpConfigManager.getServers(alias)` (not the cached profile).

## Gotchas

- **Agent ids are confined to a single safe path segment at the store boundary (`isSafeAgentId`).** Every per-agent path (`agents/{id}/agent.json`, `agents/{id}/knowledge`, and `deleteAgent`'s recursive `rmSync` target) is derived from the id via `getAgentDir`. Ids DERIVED by `buildAgentId` are already sanitized (it strips path-unsafe chars to `-`), but ids carried verbatim on `ChatAgent.id` / `chat.agent_ids` (renderer- or profile-supplied, e.g. a corrupted `profile.json`) bypass that. An id like `../../evil` would let `writeAgent`/`deleteAgent` escape `agents/` — `deleteAgent` would recursively delete an arbitrary directory. `getAgentDir` therefore throws for an unsafe id (the single choke point), `writeAgent` rejects it (`not a safe path segment`), and `deleteAgent` early-returns a no-op before touching the filesystem. Because `runAgentStoreMigrations` is not internally try/catch-wrapped, the two migration sites that call `getAgentKnowledgeDir` directly — `migrateKnowledgeToAgentStore` (primary `targetId`) and `repointCrossAgentKnowledge` (`followTarget`'s resolved id) — pre-check `isSafeAgentId` and skip, so one malformed `agent_ids` entry can never throw out of and abort the whole migration. **Two more sinks that build store/workspace paths from a caller-supplied id are guarded the same way:** `pathUtils.getAgentKnowledgePath(alias, agentId)` (the create-path twin of `getAgentDir`, reached from `addChatConfig` with `agentIdOf(chat.agent)`) throws for an unsafe id, and `consolidateWorkspaceDirsToChatId` **skips** any `legacyWorkspaceDirNames` id that fails `isSafeAgentId` before building `chat_workspaces/{id}` — otherwise a corrupt `agent_ids: ['../evil']` would let `moveContentsToDirectory` + `rmdirSync` move/delete a directory OUTSIDE `chat_workspaces`. **`migrateKnowledgeToAgentStore` guards the same way on BOTH ends:** its primary `targetId` (line ~194) AND every knowledge SOURCE dir it iterates (`legacyWorkspaceDirNames` seeded from raw `getChatAgentIds`, plus the raw `chat_id`) are `isSafeAgentId`-checked before `path.join('chat_workspaces', dir, 'knowledge')` — without the per-source guard a corrupt `agent_ids: ['agent_safe', '../../outside']` would make its `renameSync`/`rmdirSync` read-move-delete a directory outside `chat_workspaces` (the primary-id guard alone does not protect the sources). Keep any NEW `getAgentDir`/`getAgentKnowledgeDir`/`getAgentConfigPath`/`getAgentKnowledgePath` caller (or any code that joins an id into a filesystem path) behind this guard (or a try/catch) — do not build store/workspace paths from an unvalidated id. **The chat-keyed workspace path (`chat_workspaces/{chat_id}`) is confined the same way at EVERY sink**, because a `chat_id` is just as caller-supplied as an agent id (a corrupt/imported `profile.json`): `pathUtils.getDefaultWorkspacePath(alias, chatId)` (the canonical runtime resolver — its `ensureDirectoryExists` would otherwise CREATE the escaped dir) THROWS for an unsafe `chatId`; `pathUtils.removeDefaultWorkspaceDirectory(alias, chatId)` — a **recursive `rmSync`**, the most dangerous sink — returns `false` (its bool contract) and logs instead of deleting; `consolidateWorkspaceDirsToChatId` skips the whole chat when its TARGET `chat.chat_id` is unsafe (the SOURCE legacy dirs were already guarded); and `syncIPC.copyKnowledgeBasesToProfile` `continue`s past an unsafe `item.chatId` before the `mkdir`+copy. Without these, a `chat_id: '../../evil'` would let create/move/delete escape `chat_workspaces` during runtime resolution, migration consolidation, delete cleanup, or a sync import. **The chat-session path (`chat_sessions/{chat_id}`) is confined the SAME way — it is the exact twin of `chat_workspaces`:** `pathUtils.getChatSessionsChatPath(alias, chatId)` is the canonical resolver every chat_sessions sink derives from (`getChatSessionsChatIndexPath`, `getChatSessionsMonthPath`, `getChatSessionFilePath`, …) and its `ensureDirectoryExists` would CREATE the escaped dir, so it THROWS for an unsafe `chatId`; and `pathUtils.removeChatSessionsDirectory(alias, chatId)` — a **recursive `removeDirectoryRecursively`**, called by `deleteChatConfig` immediately before the already-guarded `removeDefaultWorkspaceDirectory` — returns `false` and logs instead of deleting. Guarding only `chat_workspaces` while leaving `chat_sessions` open was an asymmetric hole (same profile-supplied `chat_id`, same recursive-delete primitive); keep BOTH families of sinks guarded whenever you add a new one.

- **Creating a NEW chat must FAIL (not silently succeed) when the agent-store `writeAgent` throws.** For a brand-new chat there is no prior `agent.json` to fall back on, so a thrown `writeAgent` leaves NOTHING resolvable — yet the create path would still stamp `agent_ids`, `writeProfileToFile` → `stripInlineChatAgentsForDisk` would strip the inline agent (store is SSOT), and the renderer's `resolveChatAgent` would return null → an agent-less chat that persists across reload. The only reliable signal is that `writeAgent` THREW, so `persistNewChatAgents` and `seedNewProfileAgents` take an optional `writeFailedSink: string[]` (threaded into `writeInlineAgentsToStore`'s `failedSink`). All THREE create callers drain it and bail BEFORE `writeProfileToFile`: `addChatConfig` (`writeFailedAgentIds` non-empty → `return false`, no write/cache/notify), `deleteChatConfig`'s last-chat replacement (same guard around the replacement default chat), and `handleProfile`'s first-run seed (`seedFailedAgentIds` non-empty → `return null`). This is the CREATE-path twin of the UPDATE-path `writeFailedSink` guard above — both refuse to strip the inline agent when its durable store copy was never written.

- **The renderer push strips a chat's inline agent facade ONLY when the agent is DURABLE in the registry — symmetric with `stripInlineChatAgentsForDisk` on the disk copy.** `buildRendererProfilePayload(profile, alias, sidecars, registeredAgents)` takes the registered-agent snapshot (`profileCacheManager.getRegisteredAgents(alias)` = `getAllRegistryAgents(profileDir)`) and deletes a chat's inline `agent`/`agents` only when `agent_ids.length > 0 && every id is in the registry`. If a chat's store write failed, `stripInlineChatAgentsForDisk` keeps the agent inline on the CACHED profile; stripping it unconditionally in the push would drop the inline copy while `agents:changed` (also registry-derived) lacks it too, so the renderer's `resolveChatAgent` (`cache.get(id) ?? chat.agent ?? null`) would resolve null and render the chat agent-less (no model/tools) until a later load succeeds. This is the push-side twin of the disk-side durability gate — never strip the inline facade for a non-durable agent. (`reinjectInlineChatAgents` already does the inverse for the `getProfile` fallback path.)

- **Archiving a chat must persist its inline agents into the store FIRST, and abort on failure — an `agent_ids`-only archived entry can't hydrate a never-written agent.** This PR made `archived_chats[]` entries `agent_ids`-only (symmetric with active chats); `hydrateArchivedEntry` resolves them via `readAgent`. So if a chat is archived while its agent is still inline-only (the store `writeAgent` never succeeded), folding it into `archived_chats` as ids-only drops the last copy — the archived (and any later restored) chat can never hydrate an agent. `archiveChatConfig` therefore calls `persistNewChatAgents(profileDir, chatToArchive, archiveWriteFailed)` BEFORE building the archived entry and, when `archiveWriteFailed` is non-empty, `return false`s (chat stays active, no profile write / notify) rather than archiving into a dangling reference. For an already-durable id-only chat this is a no-op (empty sink → archive proceeds).

- **Deleting a chat now deletes its chat-owned resource graph, but only after the profile write is durable and only for unshared agents.** `deleteChatConfig` first removes the chat→agent mapping from `profile.json`; only after `writeProfileToFile` returns true does it clean `chat_sessions/{chat_id}`, `chat_workspaces/{chat_id}`, schedule jobs, SubAgentTaskStore records, memex memory, and `agents/{id}` directories. Agent deletion is guarded by `collectAgentIdsReferencedByOtherChats(profile, chatId)`, which scans active and archived chats; any id still referenced elsewhere is skipped so a shared agent and its knowledge are not deleted out from under another chat. Keep new cleanup work in this post-durable phase — never remove files before the profile mutation commits.

- **Workspace is chat-owned but derived, not persisted; knowledge is agent-owned.** `ChatConfig.workspace` is a runtime/cache field derived from `getDefaultWorkspacePath(alias, chat_id)` for chat-session deliverables, Hooks cwd, built-in tool roots, and `@workspace:` mention resolution. `writeProfileToFile` strips `chats[].workspace` / `archived_chats[].workspace` with `stripDerivedChatWorkspacesForDisk`, so `profile.json` keeps only `chat_id` + `agent_ids`. `AgentConfig.knowledge.knowledgeBase` is the source of truth for agent knowledge. `ChatAgent.workspace` remains typed only as deprecated legacy migration input; `migrateWorkspaceToChat`, `profileMigration` V6, and `consolidateWorkspaceDirsToChatId` use it only to find and consolidate legacy physical dirs, while `writeAgent` and `sanitizeChatAgent` strip it. New runtime code must use `getChatWorkspace(chatConfig)` (or receive the derived `ChatConfig.workspace`) rather than `agent.workspace`, and new store writes must not add workspace back to `profile.json` or `agents/{id}/agent.json`.


- **Built-in-defaults migration edits inline agents AFTER the store is seeded — re-sync durably or do not advance the version.** `ensureV2ProfileIntegrity` runs `runAgentStoreMigrations` (seeds `agents/{id}/agent.json` from the hydrated inline `chat.agent`) BEFORE `applyBuiltinDefaultsMigrations`, which mutates that same in-memory inline agent (adds the `builtin-tools` server + any newly shipped builtin skills) and bumps `builtinDefaultsVersion` on the working copy. But `writeProfileToFile` → `stripInlineChatAgentsForDisk` strips inline agents on the disk write WITHOUT re-syncing them to the store. So without a durable re-sync those mutations reach neither `profile.json` (stripped) nor the store (already written) — they are lost while the version is bumped, so the migration never reruns. `ensureV2ProfileIntegrity` therefore calls `syncInlineChatAgentsToStore(profileDir, profile, failedIds)` right after `applyBuiltinDefaultsMigrations` returns true. It is a pure overwrite-in-place writer (same id, no prune, no `agent_ids` re-stamp — the version bump does not change ids) built on `writeInlineAgentsToStore`; if any write fails, `ensureV2ProfileIntegrity` returns the original profile without writing `profile.json`, so `builtinDefaultsVersion` stays old on disk/cache and the migration retries on next load. If you add any other post-`runAgentStoreMigrations` step that mutates `chat.agent`, it must re-sync to the store with the same failure gate, or the change dies on the next write.

- **`syncChatAgentsToStore` prune + re-stamp are gated on a DURABLE store write — a failed replacement write must not delete the old agent.** `writeInlineAgentsToStore` is best-effort: it records an intended id in `nextIds` BEFORE the `agents/{id}/agent.json` write and swallows a write failure, so `nextIds` can name an agent that is NOT actually on disk. The two destructive steps in `syncChatAgentsToStore` — deleting the chat's previous store entries (`deleteAgent`, which recursively `rmSync`s the agent's folder + knowledge) and re-stamping `chat.agent_ids` — therefore run ONLY after a durability check: `nextIds.every((id) => readAgent(profileDir, id) !== null)`. If any intended agent is missing, the rebind is ABORTED (nothing pruned, `agent_ids` unchanged, pre-edit ids returned). Without this gate, a swap A→B whose `writeAgent(B)` fails would compute `stale=[A]`, delete A's folder+knowledge, and stamp `agent_ids=[B]` — destroying A while B was never written and binding the chat to a nonexistent agent. The edited inline agent stays on the chat, so `writeProfileToFile` keeps it inline on disk (`stripInlineChatAgentsForDisk` only strips once ids resolve) and the next successful edit / reload heals it. In tests, the `/mock` store makes every `writeAgent` throw, so `readAgent` (a spy) returns null and the gate ALWAYS aborts by default — a happy-path restamp test must simulate a durable write with `(readAgent as any).mockReturnValue(<agent>)`.

- **`readAgent !== null` cannot detect a failed SAME-ID update — an UPDATE's `writeAgent` failure is surfaced via `writeFailedSink`, and CRUD callers FAIL the op instead of stripping the inline edit.** The durability gate above (`readAgent(...) !== null`) is sufficient for a SWAP to a new id (the new `agent.json` is absent → null → abort) but BLIND to a same-id content edit (change model/prompt, id unchanged): `writeFileAtomicallyWithRetry` leaves the PREVIOUS `agent.json` intact when it throws, so `readAgent` returns the STALE copy and the gate — and `stripInlineChatAgentsForDisk`, which keys on the same check — both see the id as durable. Result before the fix: `writeProfileToFile` strips the edited inline agent, `profile.json` keeps only `agent_ids`, and the edit reverts to the old store content on reload (silent data loss on any `writeAgent` IO failure during an edit). The only reliable signal that an UPDATE failed is that `writeAgent` THREW, so `writeInlineAgentsToStore` records those ids in an optional `failedSink`; `syncChatAgentsToStore` folds `writeFailed.length === 0` into `allPersisted` (so a thrown write also aborts the prune/re-stamp) and pushes them to an optional `writeFailedSink` out-param (5th arg). `updateChatConfig`/`updateChatAgent` pass a `writeFailedAgentIds` array and, when it is non-empty, `return false` BEFORE `writeProfileToFile` — the profile (and its inline strip) is never written, so the edited inline agent is preserved, the editor stays dirty (save reported failed), and the durable old content is untouched. This deliberately supersedes the earlier "return true + heal via inline retention" behavior for the swap case: that heal only works when the chat's remaining bound ids are ALSO unresolved, which is NOT the production norm (the old agent is normally durable, so its id resolves and strip drops the inline anyway). In `profileChatCrud.test.ts` the store mock now defaults `writeAgent` to a no-op SUCCESS (`vi.fn(async () => {})`, reset in `beforeEach`) because the real impl throws under `/mock`; a failed-store-write test opts in with `(writeAgent as any).mockRejectedValue(...)`.

- **A chat edit is a TWO-HALF transaction (agent store + `profile.json`); the destructive half is deferred to after the durable `profile.json` write.** Persisting an agent edit touches two files: the agent store (`agents/{id}/agent.json` + `index.json`) and `profile.json` (`agent_ids`). `syncChatAgentsToStore` does the ADDITIVE store half (write new agents, re-stamp `agent_ids` in memory); the caller then does the `profile.json` half via `writeProfileToFile`. The DESTRUCTIVE store cleanup — pruning agents that fell out of the binding — must NOT run until the `profile.json` write is durable, because deleting an agent and then failing the profile write leaves the persisted profile (and the on-success-only cache) bound to an agent already erased (agent loss on reload). So `syncChatAgentsToStore` takes an optional `staleSink: string[]`: when provided (the `updateChatConfig`/`updateChatAgent` CRUD paths), it COLLECTS the stale ids instead of deleting them, and the caller invokes the exported `pruneStaleStoreAgents(profileDir, staleSink)` only AFTER `writeProfileToFile` returns true (on `false`/throw it returns early, leaving every agent intact). Sink-less callers (unit tests, any path with no subsequent profile write) keep the original eager prune. This mirrors `deleteChatConfig`'s pre-existing "clean up directories only after the profile deletion is durable" ordering — any new CRUD path that removes agents must follow the same defer-destruction-until-durable rule.

- **`writeAgent` is not atomic across `agent.json` + `index.json`; a NEW agent whose index write fails is rolled back so it can't masquerade as durable.** `writeAgent` writes `agents/{id}/agent.json` first, then `upsertIndex` (`index.json`), then the in-memory registry. The `syncChatAgentsToStore` durability gate keys on `readAgent` (which reads `agent.json`), but `listAgents` and the load-time registry rebuild are INDEX-driven. So if `upsertIndex` fails after `agent.json` was written for a NEWLY created agent, the gate would see it as durable while every index-driven reader omits it — the chat strips its inline copy and binds `agent_ids` to an id that resolves to nothing now and after restart. `writeAgent` therefore snapshots `isNewAgent = !exists(agent.json)` up front and, on an index-write failure, `rmSync`s the just-created agent dir (best-effort) before rethrowing, so `readAgent` correctly reports it as absent. An UPDATE (`isNewAgent === false`) is NOT rolled back: its pre-existing index entry already makes it reachable, and the freshly written `agent.json` is the newer content — deleting the dir + knowledge would itself be data loss.



- **700 ms UI lag ceiling.** The 500 ms main-process debounce + 200 ms renderer debounce means profile changes are never reflected in the UI immediately. Do not rely on synchronous reads from the renderer right after an IPC write.

- **`ChatSessionFileOps` is per-alias, not a single global singleton.** It uses `Map<string, ChatSessionFileOps>`. Calling `getInstance(aliasA)` and `getInstance(aliasB)` returns two distinct objects with different `basePath` values.

- **Month-index write locks.** `ChatSessionManager` serializes concurrent writes to the same month index using promise-chained locks (`monthIndexWriteLocks: Map<string, Promise<void>>`). Bypassing `ChatSessionManager` and writing month indexes directly via `ChatSessionFileOps` will race with these locks and corrupt the index.

- **Windows `EPERM` on atomic `index.json` rename is transient — never fail the write on the first one.** On Windows, `fs.rename` onto an existing target throws `EPERM`/`EACCES`/`EBUSY` whenever antivirus (Defender real-time scan) or a concurrent reader briefly holds a handle to the destination. The scheduler rewrites `chat_sessions/{chatId}/{YYYYMM}/index.json` on every run, so a single contended rename used to fail the whole flush, surfacing as "Failed to flush chat session ..." and orphan **"New Chat"** scheduled runs (the run threw during its initial save, before the title was updated). All `ChatSessionManager` atomic writes now go through `writeFileAtomicallyWithRetry` (`atomicFileWrite.ts`), which retries the rename with short backoff. Keep this retry — do not revert to a single bare `fs.rename`, and route any new high-frequency JSON writes in this layer through the same helper.

- **`CorruptedMonthIndexError` is thrown, not swallowed.** If a month index file cannot be parsed, `ChatSessionManager` throws a typed `CorruptedMonthIndexError`. Callers in `ProfileCacheManager` and `AgentChat` must handle this explicitly.

- **`pathUtils` falls back to `os.tmpdir()` in tests.** When Electron is not importable (Jest environment), `getUserDataPath()` returns a temp path. Tests that write real files must set `global.electron.app` (or `OPENKOSMOS_TEST_USER_DATA_PATH`) before importing this module.

- **`portablePath` runs on every profile load.** The conversion is lightweight, but editing `profile.json` by hand with absolute paths from a different machine will trigger a rewrite of those fields on the next app start.

- **`BUILTIN_SKILL_NAMES` cannot be deleted.** `ProfileCacheManager` rejects delete requests for skills whose names appear in `BUILTIN_SKILL_NAMES` (currently `['skill-creator']`).

- **The global skill registry is in `skills.json`, not `profile.json`.** The old in-memory `ProfileV2.skills` facade is gone: `ProfileCacheManager.readProfileFromFile` mirrors skills only during migration/sanitization, then strips them from the cached profile. Runtime consumers must read `skillsConfigManager.getSkills(alias)` / `getSkill(alias, name)` / `hasSkill(alias, name)`. Do **not** expect `profile.json` on disk to contain a `skills` array (legacy files still do until their first rewrite). When asserting persisted skills in tests, read `skills.json` via `skillsFileStore.readSkillsFile()`, not `profile.json`. Skill add/update/delete orchestration lives in **`profileEntityCrud.ts`** wrappers and persistence lives in **`skillsConfigManager.ts`**; split/migration/IO logic lives in `skillsFileStore.ts`. Keep all of them out of the allowlisted `profileCacheManager.ts`.

- **Legacy skill source metadata is inert.** Existing `source: 'IN-LIBRARY'` and `remoteVersion` values survive sanitization for backward compatibility only. They grant no remote lookup or update behavior. The installed skill registry remains local and is owned by `SkillsConfigManager`.

- **The global Agent Hook *list* is in `hooks.json`, but the master switch `hooksEnabled` stays in `profile.json`.** This is the one asymmetry vs. mcp/skills. The old in-memory `ProfileV2.hooks` facade is gone: `ProfileCacheManager.readProfileFromFile` mirrors hooks only during migration/sanitization, then strips the `hooks` list from the cached profile — but **never strips `hooksEnabled`**. Runtime consumers must read `hooksConfigManager.getHooks(alias)` / `getHook(alias, id)` / `hasHook(alias, id)` for the list, and read `hooksEnabled` straight off the cached profile. When asserting the persisted hook list in tests, read `hooks.json` via `hooksFileStore.readHooksFile()`, not `profile.json`; when asserting the master switch, read `profile.json`. `fingerprintProfileForDirtyCheck` strips `hooks` but **not** `hooksEnabled`, so toggling the switch still dirties (and rewrites) `profile.json`. Hook-list add/update/delete orchestration lives in **`profileHookCrud.ts`** (delegating to **`hooksConfigManager.ts`**); split/migration/IO logic lives in `hooksFileStore.ts`, which reuses the canonical `sanitizeHooks` from `profileSanitizer.ts`. Keep all of them out of the allowlisted `profileCacheManager.ts`.

- **`integrityEnsure` is the startup backfill gate.** It handles missing-field backfills and still-supported compatibility normalization on each profile load. Do not add new required persisted fields without updating `integrityEnsure()`, or existing users will hit `undefined` reads.

- **Unreadable profile files are not treated as new users.** If `profile.json` exists but cannot be parsed or validated, `handleProfile()` copies it to `profile.json.corrupt-<timestamp>` before creating a default profile. Do not remove this safety net or reintroduce silent `null` reads that can overwrite real user data.

- **Installed global MCP servers live in `mcp.json`, owned by `McpConfigManager` — not `profile.json`.** `mcpConfigManager.getServers(alias)` is the runtime source of truth; `ProfileV2.mcp_servers` is optional/deprecated and is populated **only transiently** during the load/migration window, then stripped from the cached profile. On load, `ProfileCacheManager.readProfileFromFile` calls `mcpConfigManager.resolveFromDisk(alias, legacySlice)` (a valid `mcp.json` wins and primes the manager's `lastFingerprint`; an absent file seeds from the legacy `profile.json` slice and clears the fingerprint; a corrupt file is backed up to `mcp.json.corrupt-<ts>` and installed server configs are treated as empty — never silently dropped), transiently re-attaches installed server configs so `ensureV2ProfileIntegrity` (V1/V4 migrations) sees them, persists them early before any profile strip, commits the post-migration configs before writing bumped migration state, then `delete`s the field. Required `mcp.json` writes are disk-first: failed writes do **not** update cache/fingerprint, a failed early load handoff returns the valid profile while leaving the legacy slice in `profile.json`, and a failed post-migration handoff leaves profileMigrationVersion old so MCP cleanup retries next launch. The manager is the **only** writer of `mcp.json` (its own per-alias write lock + dirty-check + `updatedAt`); `ProfileCacheManager.writeProfileToFile` writes **only** `profile.json` (without the top-level `mcp_servers`, dirty-checked on everything except its own `updatedAt`) after retrying any loaded-but-not-persisted MCP handoff and aborting if that retry fails. So a pure-MCP change rewrites only `mcp.json` and an unrelated profile edit rewrites only `profile.json`, each with an independent `updatedAt`. The renderer still receives installed server configs because BOTH wire surfaces **re-inject** `mcp_servers: mcpConfigManager.getServers(alias)` — the `profile:cacheUpdated` push **and** the `profile:getProfile` IPC read (the renderer's `getProfile` fallback in `profileDataManager.initialize` forwards the configs to `mcpClientCacheManager`, so a stripped read would otherwise initialize an empty server set if the push races). Do **not** read/write `ProfileV2.mcp_servers` at runtime (use the manager), do **not** re-add `mcp_servers` to the `profile.json` writer, and do **not** strip nested `chat.agent.mcp_servers` (per-agent name+tool bindings legitimately stay in `profile.json`). Never fold `updatedAt` into a fingerprint or the dirty-check never skips.

- **`getChatConfig` / `getAllChatConfigs` return the raw `agent_ids`-only cached chat — resolve agents through `agentAccessor`, never off `chatConfig.agent`.** `sanitizeProfileV2` strips inline `chat.agent`/`chat.agents` on every write and the load pipeline strips them from the cached profile (`stripInlineChatAgentsForDisk`), so the cache holds only `agent_ids`; the standalone store (`agents/{id}/agent.json`, mirrored into the in-memory `registry`) is the SSOT. `getChatConfig`/`getAllChatConfigs` (`profileChatCrud.ts`) return the cache chats **as-is** — they do **not** re-attach inline agents. Every main-process chat-runtime consumer resolves agents through the accessor: `getChatPrimaryAgent(chat)` (= `chat.agent ?? getChatAgents(chat)[0]`; for an ids-only chat this resolves `agent_ids[0]` via the registry resolver) or `getChatAgents(chat)` for the full list — e.g. `agentChat.ts` (`.model`/`.mcp_servers`/`.system_prompt`), `agentChatManager.ts`, `agentChatManagerSessionCoordinator.ts`, `agentChatPromptService.ts`, and `agentChatHookRuntime.resolveActiveAgent`, plus `buildStarredChatSessionIndexItem` (`profileSanitizer.ts`, the starred-session index metadata) and `deleteChatConfig`'s built-in guard (`profileChatCrud.ts`). **History (2026-06-30 → Phase 5):** a temporary read-path facade (`hydrateChatAgents`) once made these getters return a shallow copy with inline agents re-attached, added because opening a chat in a migrated (`agent_ids`-only) profile otherwise failed with `[AgentChatManager] No chat config or agent found for chat: <id>` and fell back to the **built-in** agent (skills/tools/mcp all `0`, no model, no primary). **Phase 5 of the sidecar-renderer normalization removed that facade** and migrated ~25 direct `chatConfig.agent` readers to the accessor, so the read path no longer forks between hydrated and raw chats. Do **not** re-introduce inline-agent hydration on read, and never read `cache.get(alias).chats[i].agent` — it is `undefined` for every migrated chat.

- **`agentAccessor` (`getChatPrimaryAgent`/`getChatAgents`) is MAIN-PROCESS-ONLY — renderer code MUST resolve chat agents through `src/renderer/lib/agent/resolveChatAgent.ts`, never import the main accessor.** The accessor's `agent_ids → AgentConfig` resolver is a module-level singleton (`let agentResolver = () => []`) installed via `setAccessorAgentResolver`, and that install happens **only** in the main process (`profileCacheManager.ts`). The renderer bundles its **own** copy of `agentAccessor.ts` with the default **empty** resolver, so in the renderer `getChatPrimaryAgent(chat)`/`getChatAgents(chat)` return `undefined`/`[]` for any `agent_ids`-only chat (i.e. every chat post-migration, since the renderer wire push strips inline `chat.agent`). The renderer's equivalent is `resolveChatAgent(chat)` (backed by `agentClientCacheManager`, populated via the `agents:changed` push): `agentClientCacheManager.getAgent(chatAgentId(chat)) ?? chat?.agent ?? null`. **Historical bug (2026-07-02):** `profileDataManager`'s imperative readers (`getSelectedModel`/`getCurrentAgent`/`getReasoningEffort`/starred-session index), plus `workspaceSearchService` and `mentionAssetUrl`, imported `getChatPrimaryAgent` from the main accessor — so the ChatInput model selector showed **"Select Model"** (and the workspace/mention agent lookups silently returned nothing) for every separated chat, because the renderer resolver was the empty default. Fixed by switching all three files to `resolveChatAgent`. Rule: any renderer module that needs a chat's agent uses `resolveChatAgent`/`resolveChatAgents` (imperative) or `useChatAgent`/`useChatAgentMap` (reactive) — never the `main/lib/userDataADO/agentAccessor` import.

- **`updateChatAgent` MUST resolve the chat's existing agent before merging — reading `cache.get(alias).chats[i].agent` directly destroys data.** This is the **write-side** counterpart to the accessor-read Gotcha above. `updateChatAgent` (`profileChatCrud.ts`) reads the chat straight from the cache (NOT via `getChatConfig`), so post-migration it sees an `agent_ids`-only chat with **no inline `.agent`**. The merge logic then takes its `else` branch and builds the "updated" agent from `{ ...DEFAULT_CHAT_AGENT, ...agentUpdates }` — and `DEFAULT_CHAT_AGENT.name` is **"Kobi"**. A model-only edit (which omits `name`) therefore produces an agent named "Kobi"; `syncChatAgentsToStore` derives its id from the *name* via `buildAgentId("Kobi", source)` = `agent-kobi-on-device`, **overwrites the real Kobi** with defaults+the leaked model, re-stamps the chat's `agent_ids` to the wrong id, and **prunes the chat's actual agent** via `deleteAgent` (which `rmSync`s the whole `agents/{id}/` dir, *including its knowledge*). **Historical data-loss bug (2026-06-30):** one model edit on the "OpenKosmos" chat silently deleted the OpenKosmos agent (config + knowledge, unrecoverable) and reset "Kobi" to defaults, leaving two chats both pointing at `agent-kobi-on-device` ("two Kobi"). The fix is `resolveExistingPrimaryAgent(ctx, alias, chat)` — a 3-tier resolver (inline facade → `getChatAgents` registry accessor → direct `readAgent(profileDir, agent_ids[0])` store read) called at the top of `updateChatAgent` to hydrate `currentChat.agent`/`oldAgent` onto the **real** existing agent, forcing the in-place merge branch (preserving name+id, no wrong-id write, no prune). Returns `undefined` only for a genuinely new chat (no resolvable agent), where creating from `DEFAULT_CHAT_AGENT` is correct. Keep this resolver; never merge an agent update onto `DEFAULT_CHAT_AGENT` for a chat that already has `agent_ids`. (Post stable-UUID: a real existing agent carries its `id`, so the recovered agent keeps it across the merge — the resolver is still required to avoid the DEFAULT_CHAT_AGENT fallback.)
- **Agent ids are stable UUIDs minted at creation — a rename never re-keys the store or churns `profile.json`.** New agents get `agent_{timestamp}_{random}` (`buildAgentUuid`), minted once by `ensureInlineAgentIds` on the create path (`addChatConfig`/`persistNewChatAgents`) and carried on `ChatAgent.id`. Everywhere the store/migration derives an agent id it goes through `agentIdOf(agent)` = carried `id`, else the `@deprecated` name-derived `buildAgentId` fallback (only for legacy inline agents that predate the id field). Because the id no longer encodes the name, `updateChatAgent`/`syncChatAgentsToStore` on a rename keep the same id → `agent_ids` is unchanged → `writeProfileToFile`'s fingerprint dirty-check skips the `profile.json` write (only `agent.json` content changes), and no store entry is pruned. Do NOT reintroduce id derivation from the name at write time. Because the primary is now keyed by the stable `chat_id` (`profile.primaryChat`), renaming even the primary agent no longer rewrites `profile.json`.
- **`primaryChat` is a stable `chat_id`, not an agent name.** The profile-level primary is stored in `ProfileV2.primaryChat` (the primary chat's `chat_id`). The legacy `primaryAgent` (an agent *name*) was removed: it broke on rename and could not disambiguate two chats sharing one agent name. `findChatByPrimaryChat(chats, primaryChat)` = a plain `chat.chat_id === primaryChat` lookup; `profileSettingsCrud.updatePrimaryChat(alias, chatId)` validates the chat exists. Empty/unset `primaryChat` means "no explicit primary" → runtime + renderer fall back to the first chat (`?? chats[0]`). The `set_primary_agent` built-in tool keeps its external `agent_name` input/`primaryAgent` result fields (user-facing) but internally maps the name to its owning chat's `chat_id` via the hydrated `getAllChatConfigs` + `getChatPrimaryAgent`, then calls `updatePrimaryChat`. Migration **V6** (`PROFILE_MIGRATION_VERSION = 6`) is the one-time converter: it resolves the legacy `primaryAgent` name to its owning `chat_id`, stores it in `primaryChat`, and deletes `primaryAgent` (unmatched name → `primaryChat` unset). This runs in the SAME `< 6` gate as the agent_ids derivation — this whole PR is unreleased (main is at V5), so all of its profile-shape changes collapse under one version bump. `sanitizeProfileV2` whitelists only `primaryChat`, so any lingering `primaryAgent` is dropped on the next write.
- **Deleting a chat KEEPS its agent(s) in the store.** `deleteChatConfig` unregisters the chat→agent mapping from `profile.json` only; it does NOT delete `agents/{id}/`. An agent can be shared/re-referenced by another chat, so destroying it as a side effect of removing one chat would lose config + knowledge. There is deliberately no `removeChatAgentsFromStore` — it was removed. Agent deletion, if ever needed, must be a separate explicit operation.
- **`manage_agents` tool has NO destructive actions.** Its `VALID_ACTIONS` are `create`, `update`, `list`, `set_primary`, `status` — the `remove` action was removed (it deleted a chat, contradicting the chat-owns-agent model and the delete-keeps-agent rule above). `create` mirrors the OpenKosmos "New Agent" store-first path; `update` only rewrites `agents/{id}/agent.json`. Do not re-add `remove`/archive/delete to this facade.
- **The renderer agent editor MUST save via `updateChatAgent`, never `updateChatConfig({ agent })`.** `AgentChatEditingView`'s Save/Save-All (`useAgentChatEditingViewModel.handleSave`/`handleSaveAll`) go through `useChats().updateChatAgent` → `chatOps.updateChatAgent` → `profile:updateChatAgent`, which calls `syncChatAgentsToStore` and writes `agents/{id}/agent.json`. Routing an agent edit through `updateChatConfig` (`updateChat`) instead only merges an inline `agent` onto the chat entry in `profile.json` and, on its own, **never touches the store**; because `writeProfileToFile`/`stripInlineChatAgentsForDisk` strips inline agents once `agent_ids` resolve, that write is discarded and `agent.json` stays stale — the Save silently no-ops. **Historical bug (2026-07-01):** post-separation the editor still called `updateChat(chatId, { agent })`, so editing an agent appeared to succeed but the on-disk `agent.json` never changed. Keep full agent-field edits on `updateChatAgent` (it also runs rename guards, Quick Start image-cache invalidation, and `zero_states` sanitization that the generic path does not).
- **`updateChatConfig` has a store-sync SAFETY NET for agent-bearing updates.** Bulk paths such as `applySkillToAgents` / `removeSkillsFromAgents` and the multi-agent branch of `ApplyHookToAgentsDialog` legitimately pass full agent objects through `updateChatConfig`. Multi-agent chats have no singular `updateChatAgent` equivalent, so `profileChatCrud.updateChatConfig` calls `syncChatAgentsToStore` and re-stamps `agent_ids` whenever an update carries `agent` or `agents`. Non-agent updates skip the guard. Prefer `updateChatAgent` for single-primary-agent edits; reserve this guard for bulk or multi-agent mutations.
- **Migrated ARCHIVED agents get the SAME UUID id scheme as active agents — never name-derived.** Active chats are minted `agent_{timestamp}_{random}` UUIDs during migration by `profileMigration` (`ensureInlineAgentIds` over `profile.chats`). Archived agents live in a **separate** source (`archive/archived_agents.json`, inline, no id) that `profile.chats` never contains, so they used to skip minting and fall back to the `@deprecated` name-derived `agent-{name}-{source}` id (via `resolveArchivedEntryIds` → `agentIdOf`) — leaving the profile with **two** id schemes. `migrateArchivedAgentsToStore` now calls `ensureInlineAgentIds({ agent: entry.agent })` on each archived entry **before** deriving its id, so archived and active agents share one UUID scheme. **Consequence for cross-agent knowledge:** an active agent's `knowledgeBase` that points at an archived agent's legacy `chat_workspaces/agent-{name}-{source}/knowledge` dir can no longer be followed by assuming the store id equals that dir name (the old `?? refDir` coincidence). `repointCrossAgentKnowledge` therefore builds `dirNameToStoreId` from `listAgents()` mapping each stored agent's `buildAgentId(name, source)` (legacy dir name) → its store `id` (UUID), covering active AND archived. Do NOT reintroduce name-derived ids for archived migration, and keep the legacy-dir-name→UUID mapping so cross-refs survive the switch.
- **`writeAgent`/`deleteAgent` MUST write-through the in-memory `registry` hot cache — it is the ONLY thing the IPC boundary re-injects agents from.** `agentStoreManager`'s `registry` (`Map<profileDir, Map<id, AgentConfig>>`) is the hot cache that BOTH read surfaces resolve agents from: `performNotification`'s `getRegistryAgentsByIds` re-injection into the `profile:cacheUpdated` wire payload, and `getChatConfig`/`getAllChatConfigs` hydration on the main side (Gotcha above). It used to be populated **only** at load (`runAgentStoreMigrations` → `setRegistryAgents(listAgents())`), and **no write path refreshed it**. So after an agent edit, `writeAgent` updated `agents/{id}/agent.json` (disk SSOT) + `index.json` but the registry kept the **load-time snapshot**, and `performNotification` pushed the STALE agent to the renderer. **Historical bug (2026-07-01):** editing an agent (e.g. adding two MCP servers, or changing skills) persisted to `agent.json` correctly, yet the renderer received `chat.agent` with the **pre-edit** values; `AgentChatEditingView`'s `chats`-effect re-derived `agentData` from that stale push, clobbered the just-saved optimistic state, and the tab's frozen `initial*` snapshot no longer matched the reverted `selected*` → the editor **re-dirtied ~1 ms after a clean Save** ("saved but still shows unsaved", ● indicator + Save-All button stayed lit). The fix makes writes write-through: `writeAgent` calls `upsertRegistryAgent(profileDir, agent)` **after** the disk write + index upsert (it lazily creates the per-`profileDir` map so a write before the load-time `setRegistryAgents` still seeds the cache), and `deleteAgent` calls `removeRegistryAgent(profileDir, id)` — keeping the registry in lockstep with disk, exactly like the `mcp.json`/`skills.json`/`hooks.json` managers already update their own `Map` inside every mutator. **The Agents registry was the ONE sidecar hot cache that wasn't write-through** — the agent store split the *writer* (`writeAgent`) from the *cache updater* (`setRegistryAgents`), whereas mcp/skills/hooks fused them. Keep the write-through in `writeAgent`/`deleteAgent`; never rely on the next load's `setRegistryAgents` to reconcile a runtime edit.
- **Duplicating an agent MUST strip the source agent's store `id` so the copy mints a fresh UUID.** `duplicateAgent` (`agentDuplicator.ts`) builds the copy by spreading the source agent (`{ ...sourceAgent, name, source, version, workspace:'', knowledge:{knowledgeBase:''} }`). The store dir (`agents/{id}`), knowledge path, and `agent_ids` all key off `agentIdOf(agent)`, so a carried source `id` makes `ensureInlineAgentIds` (a no-op when an id is already present) skip minting, `addChatConfig → persistNewChatAgents` write `agents/{sourceId}/agent.json` — **overwriting the SOURCE agent** — and point the duplicate at the source's knowledge dir. **Historical data-corruption bug:** duplicating an agent silently overwrote the original with the copy's fields. The spread now includes `id: undefined` so `ensureInlineAgentIds` mints a fresh `agent_{ts}_{rand}` UUID for the copy. Keep the `id: undefined` — never carry a source id into a duplicate.
- **Archived-agent migration DEFERS the import (keeps the transitional source file) if any `writeAgent` fails — never commit a half-written archive to Phase 2.** `migrateArchivedAgentsToStore` is two-phase: Phase 1 imports the archive list from `archive/archived_agents.json` (or `agents/archived_chats.json`) into `profile.archived_chats` while KEEPING the source file; Phase 2 (next load, once the profile durably owns the list) retires the source. For a legacy inline-only archived agent (no pre-existing store copy) the source file holds the ONLY copy of that agent's config, so if its `writeAgent` throws (e.g. an fs error) the migration must NOT set `profile.archived_chats` — doing so would let the next load's Phase 2 retire the source, leaving an unrestorable archived chat pointing at a missing `agents/{id}/agent.json`. Phase 1 tracks `allPersisted` and, on ANY write failure, returns WITHOUT setting `profile.archived_chats` or retiring the source, so the failed write is retried next load. (Idempotent: an id-less entry re-mints a fresh UUID on retry, so a transient failure may leave a harmless orphan `agents/{uuid}/` dir — never data loss.) Do NOT hoist the `profile.archived_chats = rewritten` assignment above the `allPersisted` guard.
