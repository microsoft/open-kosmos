# Scheduler

> Registers and fires time-based jobs (cron or one-time) that each launch a new chat session against a bound agent.

## Architecture

### Job lifecycle
```
createJob → scheduleStore.createJob → SchedulerManager.registerJob
  ├─ cron  → node-cron.schedule → on tick: executeJob('scheduled')
  └─ once  → setTimeout → on fire: executeJob('scheduled') → if guard-skipped, retry periodically until the catch-up window expires

executeJob
  → overlap guard: skip if job.id has an in-flight count (except manual triggers)
  → concurrency guard: skip if executionSlots ≤ 0 (except manual triggers)
  → increment job.id in-flight count, decrement executionSlots
  → MCP-readiness preflight (except manual triggers): ensureSchedulerJobMcpReady(job, alias) →
      await mcpClientManager.waitForServersSettled(waitTargets, MCP_READY_GATE_TIMEOUT_MS);
      if any requiredServers still not 'connected' → build preflightError and continue
  → scheduleStore.markJobExecutionStarted
  → agentChatManager.runScheduledJob(job, { chatSessionId?, onReady?, preflightError? })
  → on success: markJobExecutionCompleted (cron stays 'pending'; once becomes 'completed' + disabled)
  → on failure: markJobExecutionFailed   (cron becomes 'failed'; once becomes 'failed' + disabled)
  → finally: decrement job.id in-flight count, increment executionSlots capped at max
```

### MCP-readiness preflight
On cold start, `mcpClientManager.initialize()` (Chain A, fired from `profileCacheManager.initializeBackgroundServices`) connects external MCP servers asynchronously over several seconds, while `schedulerManager.initialize()` (Chain B) can run catch-up immediately. `getAllTools()` only returns `status === 'connected'` servers, so a job that fires before its server connects would otherwise run with a **partial toolset** and could silently "succeed". The preflight closes this race for **all** non-manual trigger sources (cold-start/resume/watchdog catch-up and normal cron ticks landing in the early window) because they all funnel through `executeJob`, but it must not suppress run visibility.

`schedulerMcpReadiness.resolveSchedulerJobMcpServers(job, alias)` mirrors `agentChatPromptService.getCurrentAvailableTools()` to scope the wait per job:
- Resolves the job's agent(s) via `profileCacheManager.getChatConfig(alias, job.chat_id)` (single `agent` or multi `agents`).
- `explicit` = union of each agent's `mcp_servers[].name`, excluding `builtin-tools`, stale bindings no longer present in `profile.mcp_servers`, and servers the profile has disabled (`in_use === false`).
- **Explicitly-bound agent** → `waitTargets = requiredServers = explicit`.
- **No-tools agent** (missing or empty outer `mcp_servers`) → `waitTargets = requiredServers = []`. The outer empty list means no servers; only an inner server entry with `tools: []` means all tools from that one explicit server.
- Any resolution error / no alias / no chatConfig / no agents → `{ waitTargets: [], requiredServers: [] }`, which **disables the preflight** (pre-preflight behavior).

"Settled" means the server reached a terminal-ish status (`connected`/`error`/`disconnected`/`needs-user-interaction`), not `connecting`/`disconnecting`. If any `requiredServers` are still not `connected` after the bounded wait, `executeJob` formats a clear error such as `Required MCP server disconnected: teams`, still calls `markJobExecutionStarted`, and passes that error to `agentChatManager.runScheduledJob(..., { preflightError })`. The scheduled runner creates the chat session, persists the initial `running` metadata, appends a visible assistant failure message, marks the session `failed`, sets unread state, and sends the normal failed completion notification. This makes the missed run observable instead of silently skipping it. Manual triggers bypass the preflight entirely.

### Storage layout
Jobs are partitioned into monthly JSON files under `{userData}/profiles/{alias}/schedules/YYYYMM.json`. The month key for `once` jobs comes from `runAt`; for `cron` jobs it is embedded in the job ID. `runtime-state.json` lives in the same directory. Each job's `chat_id` field holds the owning chat's id (it does NOT identify an agent). Pre-v6 jobs persisted this as `agentId`; `normalizeSchedulerJob` reads the legacy `agentId` as a fallback so older files load transparently, and re-persists as `chat_id`. Cleanup IPC options pass `chatId` (renderer prop) which maps to `job.chat_id`.

### Cold-start, resume, and watchdog catch-up
On `initialize()`, `SchedulerManager` reads `SchedulerRuntimeState`. If `isActive === true` at startup the previous session was an unclean exit; the catch-up window opens from `lastActivatedAt`. Missed cron occurrences within `MAX_RESUME_CATCH_UP_DELAY_MS` (6 hours) are executed immediately. Pending catch-ups are checkpointed in `runtime-state.json` so that a crash during catch-up itself is retried on the next boot.

A cold-start catch-up keeps its persisted pending entry until a successful run clears it. Failed attempts, including MCP preflight failures, still call `markJobExecutionFailed`, so a later heartbeat or restart refreshes the job and `planPendingColdStartReplays()` drops pending entries whose `lastFinishedAt` already covers the occurrence. Pending entries that are not covered by a completed/failed attempt are replayed by the heartbeat: `replayPendingColdStartCatchUps()` → `cronRecovery.runPendingColdStartReplays()` re-reads persisted pending entries, **drops** stale/superseded entries (job missing/disabled/no-longer-cron, occurrence outside the 6 h window, or already covered by a later `lastFinishedAt`), and **replays** the rest via `executeColdStartCatchUp(job, occurrenceAt, /* alreadyPending */ true)`. Re-entrancy is safe because `executeJob`'s per-job overlap token prevents a heartbeat replay from double-running a job that a live tick is already executing.

`initialize()` registers all live cron tasks and starts the heartbeat watchdog **before** invoking `handleColdStartCatchUp()` (a `scheduler.initialize.live-armed` log marks the boundary). This ordering means the live schedule is armed first, and catch-up enters the same MCP preflight path as normal ticks (see **MCP-readiness preflight** above). Because live cron ticks can mutate job state after the startup snapshot is loaded, `coldStartCatchUpRunner.runColdStartCatchUp()` re-reads each job from `scheduleStore.getJob()` immediately before pending replay and baseline execution. Pending entries whose refreshed job is gone/inactive are cleared. Pending entries whose refreshed `lastFinishedAt` already covers the occurrence are also cleared, which avoids duplicating a catch-up that completed or failed but crashed before `clearPendingColdStartCatchUp()` ran; pending entries with only `lastRunAt` advanced still replay because that indicates an interrupted/incomplete run. Baseline catch-up uses the refreshed job's cron expression and `lastRunAt` before deciding whether to execute, so a live tick that already started the same occurrence is not duplicated from the stale startup snapshot.

System sleep/resume is handled separately via `handleSystemResume(suspendedAtMs, resumedAtMs)` — called externally from the Electron power-monitor listener.

While the app remains alive, the scheduler heartbeat also runs a watchdog pass. It compares each active cron task's last checked time with `now - HEARTBEAT_INTERVAL_MS`; if `node-cron` missed an occurrence and the job has not already started that occurrence, it executes the job with `triggerSource: 'watchdog-catchup'`. If that catch-up is guard-skipped (a `skipped-*` result such as overlap or concurrency-limit), the watchdog records the exact skipped occurrence in `pendingCronWatchdogRetryAt` and holds its checkpoint back to just before that occurrence (instead of advancing past it) as long as the occurrence is still inside the catch-up window. The next heartbeat retries that same pinned occurrence rather than selecting a newer cron tick; once the occurrence ages out of the window the pending retry is cleared, the checkpoint advances, and the run is given up. MCP preflight failures are **not** retryable skips: the run is created, marked failed, and the checkpoint advances like any attempted execution. The same heartbeat additionally calls `replayPendingColdStartCatchUps()` to retry or clean up pending cold-start catch-ups (see above); this pending cleanup runs even when there are no active cron tasks, so disabled/deleted jobs do not leave stale runtime-state entries indefinitely.

### IPC push events (main → renderer)
`scheduleStore:jobCreated`, `scheduleStore:jobPatched`, `scheduleStore:jobDeleted` — sent via `BrowserWindow.webContents.send`.

## Anti-Patterns
- Do NOT call `scheduleStore` methods directly from outside this module to execute jobs — always go through `SchedulerManager` so runtime task registration stays in sync.
- Do NOT bypass `normalizeSchedulerJob` when reading job data from disk — raw JSON can have missing or wrong-typed fields.
- Do NOT register a new cron task without first calling `unregisterTask` for the same `jobId` — duplicate `node-cron` tasks will silently double-fire.
- Do NOT use `Date.now()` directly in cron tick callbacks — use `new Date().toISOString()` and pass timestamps explicitly so logs are consistent.

## Verification Steps
1. Create a cron job and confirm `activeTasks` contains it (`schedulerManager.getRuntimeDiagnostics()`).
2. Toggle the job off — confirm the cron task is stopped and removed from `activeTasks`.
3. Kill the app while a job is `running`; on next launch confirm the session's `schedulerExecutionStatus` is patched to `failed`.
4. Set `runAt` 2 seconds in the future; confirm `executeJob` fires and the job transitions to `completed`/`enabled: false`.

## Gotchas
- ⚠️ **`initialize()` is called from two auth paths — it MUST NOT block sign-in.** The callers are `auth:setCurrentSession` (session restore / auto-login) and `auth:startGhcDeviceFlow` onSuccess (first-time device flow login). Both use fire-and-forget semantics after v2.7.10 P1 where `handleColdStartCatchUp()` (which runs LLM jobs sequentially) blocked sign-in for 12+ minutes. If you add any new `await` inside `initialize()`, verify both auth paths still return instantly. See [CLAUDE.md Postmortem: v2.7.10 signing hang](../../../CLAUDE.md#postmortem-v2710-signing-hang).
- ⚠️ **`handleColdStartCatchUp` runs jobs sequentially.** Each `executeColdStartCatchUp` call `await`s an LLM-powered agent chat. If you increase the catch-up window or add more eligible jobs, total cold-start time grows linearly. Consider adding per-job timeouts or parallelism if this becomes an issue again.
- ⚠️ **Execution guardrails: overlap guard + concurrency cap.** `executeJob` checks `SchedulerExecutionGuards` (per-job in-flight counts + global max 3 slots) before running. Manual triggers (`'manual'`) bypass these checks but still participate in tracking (increment the job's count, decrement slot), so if a manual run finishes before an already-running scheduled run, the scheduled run still keeps the same-job overlap guard active. Catch-up triggers (`resume-catchup`, `cold-start-catchup`, `watchdog-catchup`) are subject to both guards — a catch-up for a job already executing from a cron tick will be silently skipped with `error: 'skipped-overlap'`. One-time timer fires retry periodically when guard-skipped so they do not remain enabled/pending in the past; if guard pressure lasts beyond the catch-up window, the one-time job is marked failed. Both guards are released in a `finally` block, and slot release is capped at `MAX_CONCURRENT_EXECUTIONS` so an execution completing after `dispose()` cannot overfill capacity. `dispose()` resets the guard state.
- ⚠️ `node-cron` uses the **system timezone** by default; `getSchedulerTimeZone()` reads `Intl.DateTimeFormat` and is passed explicitly to both `cron.schedule()` and `CronExpressionParser` in `cronRecovery.ts`.
- ⚠️ `once` jobs become `enabled: false` after execution (success **or** failure). Re-enabling them via `toggleJob` will re-register a new timeout — check that `runAt` is still in the future, otherwise the timeout fires immediately.
- Warning: `runJobNow(jobId, options?)` normally rejects disabled schedules (`'Only enabled schedules can be run manually.'`). It permits re-running a **spent one-time job** ONLY when the caller passes `{ isManualRetry: true }` **and** `isRerunnableOnce(job)` holds. "Spent" is detected as `scheduleType === 'once' && (status !== 'pending' || lastRunAt != null)`. The `lastRunAt` fallback is **load-bearing**: `markJobExecutionStarted` transiently resets `status` back to `'pending'` (and stamps `lastRunAt`) for the duration of a run, and `recoverInterruptedScheduledSessions` only patches the **chat session** metadata to `'failed'` on the next launch — it never restores the **job's** terminal status. So a retry that was itself interrupted mid-run is left as a disabled `'pending'` job with `lastRunAt` set; without the `lastRunAt` check it would surface a Retry button that always rejects, stranding the user. This relaxation is scoped to the explicit **Retry** intent so plain "Run now" callers cannot accidentally rerun a spent `once` schedule. A `once` job is auto-disabled once its single run concludes — whether it completed, failed, or was cancelled/interrupted. A cancelled/interrupted run resolves as `{ success: true, cancelled: true }`, so it is recorded via `markJobExecutionCompleted` as a disabled `'completed'` job, **indistinguishable at the job level from a clean completion** — there is no way to allow retrying the interrupted case without also allowing the completed case, so both go through under `isManualRetry`. Only the Schedules "..." menu **Retry** action passes `isManualRetry: true` (and the renderer only shows Retry for **failed/interrupted/cancelled** display states, so a cleanly-completed run never offers it). All other callers — the schedule cards & Agent editor "Run now" buttons (`GeneratedScheduleCards.tsx`, `AgentSchedulesTab.tsx`) and the `run_schedule` built-in tool — omit the flag and keep the strict `enabled`-only gate. A `once` job that has **never run** (`status === 'pending'` and no `lastRunAt`) and is disabled stays blocked even under Retry (explicitly turned off, not spent); disabled cron jobs also stay blocked (cron is never auto-disabled). The manual run goes through `executeJob('manual', …)` from scratch in a fresh `chatSessionId`, so the `once` terminal-state transitions re-apply at the end.
- Warning: A user-initiated cancel of a *running* scheduled session returns `{ success: true, cancelled: true }` from `runScheduledJob`. `executeJob` treats it as a clean completion (no failure backoff, `once` jobs still unregister). The interrupted outcome is recorded on the session metadata (`schedulerExecutionStatus: 'failed'` + `INTERRUPTED_SCHEDULED_SESSION_ERROR`) by the runner, not by the scheduler.
- ⚠️ `MAX_TIMEOUT_MS` (2 147 483 647 ms ≈ 24.8 days) caps `setTimeout` for far-future `once` jobs. Jobs beyond this window will never fire; the UI should warn users.
- ⚠️ `schedulerGeneration` is incremented on every `initialize()` call (alias switch or re-login). Stale closures from a previous generation can still hold a reference to the old `job` object — always re-fetch from `scheduleStore` inside the cron callback if the latest state matters.
- ⚠️ The heartbeat watchdog is a safety net for missed `node-cron` callbacks while the process is alive. Keep its one-heartbeat grace window to avoid racing the normal cron callback at the exact minute boundary, and always check `lastRunAt` before executing a missed occurrence so the same occurrence is not recovered twice. Different cron occurrences may still overlap, matching the normal `node-cron` path. The watchdog advances `lastCronWatchdogCheckedAt` every pass; the **one** exception is when its catch-up returns a `skipped-*` result (the run did not happen and `lastRunAt` is untouched) and the occurrence is still inside the catch-up window — then it records the exact occurrence in `pendingCronWatchdogRetryAt` and rolls the checkpoint back to just before it so the next heartbeat retries the same occurrence, not a newer cron tick. Do NOT make the checkpoint advance unconditional again, and do NOT rely on checkpoint rollback alone: either choice can silently drop occurrences missed during overlap/concurrency pressure. `executeJob`'s overlap token still prevents a retry from double-running a job a live tick is already executing.
- ⚠️ **MCP-readiness preflight failures must create visible failed runs.** When a job's required MCP servers are not connected, `executeJob` must still call `markJobExecutionStarted` and `agentChatManager.runScheduledJob` with `preflightError`. The runner owns the user-visible session failure (`schedulerExecutionStatus: 'failed'`, assistant failure message, unread badge, failed notification). Do NOT reintroduce a pre-start `skipped-mcp-not-ready` return: it makes schedules appear to do nothing, hides actionable MCP disconnection state from users, and bypasses session history.
- ⚠️ **The MCP-readiness wait is the one `executeJob` await that can outlive its own alias/generation — it is guarded.** Right after the preflight wait (and before `markJobExecutionStarted`/`runScheduledJob`, which both read the live `this.currentUserAlias`), `executeJob` re-checks the alias and `schedulerGeneration` it captured at entry. If a sign-out (`dispose()` → `currentUserAlias = null`) or alias switch / re-login (`initialize()` → new alias + incremented generation) landed during the ≤30 s wait, it returns `{ success: false, error: SCHEDULER_ALIAS_CHANGED_ERROR }` (`'skipped-alias-changed'`) **before** marking or running, so an old user's job can never execute against the new user's profile. The `skipped-` prefix keeps it in the watchdog's retryable-skip class (lastRunAt untouched), but it is deliberately **not** in the once-timer's exact-match retry set (a re-login re-registers the once timer) and **not** in `SCHEDULER_SKIP_REASON_LABELS` (it never reaches session metadata or the UI). This does NOT fix the pre-existing, much wider window where an alias switch during the multi-minute `runScheduledJob` makes the post-run `markJobExecutionCompleted/Failed` use the new alias — that is out of scope for the readiness preflight.
- ⚠️ **`resolveSchedulerJobMcpServers` must mirror the chat tool-gating logic and fail open.** It computes `waitTargets` (servers to wait on) and `requiredServers` (servers that must be `connected` or produce a visible preflight failure) by reading the job's agent config exactly like `agentChatPromptService.getCurrentAvailableTools()`. `builtin-tools` is never required because it is an in-process virtual server, and requiring its runtime state before initialization would incorrectly fail default builtin-only agents. Stale agent bindings for servers already deleted from `profile.mcp_servers` are also never required because waiting for them would permanently fail the schedule. An all-tools agent (no explicit external `mcp_servers`) waits for in-use external servers derived from the resolved cached profile alias, not `mcpClientManager.getInUseServerNames()`, so early scheduler runs do not depend on MCPClientManager already being initialized/bound; it is **never** failed for a flaky one (`requiredServers = []`). Any resolution error or missing profile is caught/handled and returns empty arrays, which disables the preflight and preserves pre-preflight behavior — keep this defensive fallback so a config edge case can never wedge the scheduler. The `in_use !== false` active-server predicate is **not** a divergence from `mcpClientManager.initialize()`'s `if (in_use)` connection-start rule: cached profiles are normalized by `sanitizeProfileV2` (`in_use: Boolean(...)`), so `in_use` is always a strict boolean and both predicates resolve identically. Using `!== false` keeps the preflight aligned with the chat tool-gating path while remaining equivalent to what initialization actually connects, so the preflight can never permanently require a server that was never brought up.
- ⚠️ **Heartbeat replay of pending cold-start catch-ups is cleanup plus retry, not an MCP-disconnect retry loop.** A failed MCP preflight run marks job metadata failed, so the next pending replay should drop that occurrence once the refreshed job's `lastFinishedAt` covers it. Entries that are not covered by `lastFinishedAt` still replay because they may represent an interrupted attempt. `replayPendingColdStartCatchUps()` is fire-and-forget from the heartbeat (`void ...catch(log)`) so a replay failure never stalls the heartbeat or the watchdog pass. Do NOT add a re-entrancy flag around it: `executeJob`'s per-job overlap token already prevents double-execution, and `clearPendingColdStartCatchUp` is idempotent, so a replay overlapping a live run is harmlessly `skipped-overlap`. Keep `SchedulerManager.replayPendingColdStartCatchUps` as thin wiring and the decision logic in `cronRecovery.planPendingColdStartReplays` (file-length cap + unit-testability).
