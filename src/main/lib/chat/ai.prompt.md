## Architecture

### Instance Model
`AgentChatManager` is a singleton that maps `chatSessionId → AgentChat`. Each browser tab has exactly one `AgentChat`; switching tabs switches `currentInstance`. Instances idle for >5 min are destroyed and recreated on demand, **except the current session** — `cleanupIdleInstance` unconditionally skips the session matching `currentChatSessionId` regardless of foreground state, because "window not foreground" (Alt+Tab) does not mean "user is not viewing this session". This current-session guard is separate from `isProtectedSession`, which checks foreground state and runtime mode; both must be considered when modifying idle cleanup behavior.

`AgentChat` is now refactored toward a facade architecture. Prompt-building, chat-session persistence/edit logic, context/compression logic, interactive request lifecycle, tool-result post-processing, tool execution/cancellation cleanup, Copilot API streaming, per-session runtime state, output dispatch, and the main turn loop now live in dedicated modules while `AgentChat` remains the public per-session entry point. The remaining public turn-entry wrappers (`streamMessage`, `retryChat`) now delegate their multi-step setup through `AgentChatTurnRunner` instead of rebuilding turn orchestration inline.

### Agent Hooks integration (Layer B)
`AgentChat` hosts the [Agent Hooks](../agentHooks/ai.prompt.md) runtime (OFF by default behind profile.json `hooksEnabled`) through the extracted `AgentChatHookRuntime`. External Agent chats are outside this local runtime: when `agent.source === 'EXTERNAL'` and `openkosmosFeatureExternalAgent` is enabled, `streamMessage`, `retryChat`, and `editUserMessage` route through the WS external-agent path instead of running `UserPromptSubmit` / `SessionStart` / `Stop` or tool hooks; retry resends the latest persisted user message without duplicating it, and edit applies the history replacement before sending the edited prompt without re-persisting it. Local-agent integration stays at the **tool dependency boundary**: `SessionStart` (official `source: 'startup' | 'resume'` plus legacy `trigger: 'new' | 'resume'`) runs from `startChat`; it can block the first model turn, and the runtime's `sessionStartHookFired` guard is set only after SessionStart allows continuation so blocking or cancelled startup policy work is retried on the next prompt instead of being bypassed. `streamMessage` and edit/regenerate mark the chat `SENDING_RESPONSE` before Hook preflight starts so `AgentChatManager`'s send gate cannot accept overlapping turns while slow `UserPromptSubmit` or `SessionStart` work is still running. `streamMessage` captures and preserves the fresh/resume state before `UserPromptSubmit` or persisted block messages can grow history, so a blocked first-turn retry still emits `startup`/`new`; retry and edit/regenerate both defer final `IDLE`, run `Stop`, and clear turn-scoped Hook buffers from the public entrypoint. Edit/regenerate prepares the edited user message, runs the same `UserPromptSubmit` policy check before writing it, applies the edit only after policy approval, then runs `SessionStart`, the model turn, `Stop`, and turn-buffer cleanup through the same public-turn lifecycle. `UserPromptSubmit` runs with a prompt string built from text plus attachment metadata (image/file/office/other summaries, without embedding raw data URLs), and the three deps handed to `createTurnRunner` are wrapped — `preToolUseAndApprove` (PreToolUse: runs hook validation for all tool calls in parallel, then processes results in original assistant order; block / `updatedInput` / re-approval on final args; official `permissionDecision: 'allow'` skips the normal permission prompt only when the hook did not mutate input, `ask` routes through a hook-specific confirmation prompt and fails closed to rejected tool decisions when UI interaction is unavailable or forbidden, and `defer` makes no hook decision; assistant tool-call messages persist after this pass so mutated args become durable context; if validation/approval throws, the assistant tool-call message is persisted before rethrowing so visible tool-call turns are not lost), `executeToolCallWithHooks` (blocked tools short-circuit to a synthetic denied `role:'tool'` result; PostToolUseFailure on throw with `is_timeout`/`is_interrupt` flags derived from the error), and `postProcessToolResultWithHooks` (PostToolUse: block replaces output with a synthetic denied result; otherwise official `updatedToolOutput` replace first, legacy `updatedMCPToolOutput` second, refused on cancel; returned tool failures run PostToolUseFailure instead of PostToolUse and carry the same failure flags). Hook inputs emit official aliases (`session_id`, `agent_type`, `transcript_path`, `permission_mode`, `tool_use_id`, `tool_response`) alongside the legacy OpenKosmos field names; `agent_id` is the chat-scoped stable id (`chatId`) and `agent_name` / `agent_type` stay the current display name. In multi-agent chats, `AgentChatHookRuntime` resolves `hookIds` from the matched active agent via `getChatAgents`/`getChatPrimaryAgent`, but it resolves `workspacePath` from `getChatWorkspace(chatConfig)` because workspace is chat-owned. Tool hook calls receive the active turn `CancellationToken` bridged to `AgentHookRunContext.signal` so command/HTTP hooks, including async fire-and-forget actions, abort with the turn instead of waiting for their timeout. Hook outputs now maintain separate bounded buffers for `additionalContexts` and `systemMessages`: additional context syncs through `promptService.setHookAdditionalContexts`, while `systemMessages` sync through `promptService.setHookSystemMessages` and are inserted into the combined system prompt.

**Observational events (Phase 3).** `Stop` fires in `streamMessage` after `runStreamMessage` resolves (so it is skipped on cancel/error, which throw earlier, and does not double-fire when `UserPromptSubmit` blocks and returns early). Public `streamMessage` defers the final `IDLE` status until after `Stop` and turn-buffer cleanup complete, so the manager send gate cannot accept a new turn while a synchronous `Stop` hook is still running. `PreCompact`/`PostCompact` fire through the optional `onBeforeCompaction`/`onAfterCompaction` deps wired into `createContextService` → `agentChatContextService` (`onBefore` before compression, `onAfter` only after a successful compaction, both with `trigger: 'auto' | 'manual'`). Compaction callbacks are protected by a short non-fatal timeout and receive an `AbortSignal`; on timeout the signal aborts and `AgentChatHookRuntime.runCompactionHookWithSignal` refuses to apply late observational buffers, so slow hook work cannot mutate later turns after the compaction path has moved on. All three are **observational**: `AgentChatHookRuntime` buffers their `additionalContexts` and `systemMessages` at **session scope** with oldest-first eviction and ignores blocking/mutation fields.

### Status Flow
```
IDLE → SENDING_RESPONSE → [COMPRESSING_CONTEXT → COMPRESSED_CONTEXT →] RECEIVED_RESPONSE → IDLE
```
All managed `AgentChat` instances, including `scheduled-silent` sessions, must surface runtime `chatStatus` through `AgentChatManager`'s manager-owned listener path. `AgentChatOutputPort` still emits directly when a sender is attached, but sender-less instances must continue to propagate status through the manager bridge so renderer consumers observe the same runtime status model regardless of runtime mode. This runtime `chatStatus` is distinct from persisted `schedulerExecutionStatus` metadata.
Compression is triggered via an **adaptive threshold** based on the model's raw `contextWindowSize` (not `effectiveContextWindow`):

| Model context window | Threshold | First trigger example |
|---|---|---|
| ≥ 500K (e.g., claude-opus-4.7-1m) | 40% | ~400K tokens |
| 200K–499K (e.g., claude 200K) | 50% | ~100K tokens |
| < 200K (e.g., GPT-4o 128K) | 70% | ~90K tokens |

The `tokenUsageRatio` is still computed against `effectiveContextWindow` (context window minus output reserve), but the threshold tier is selected from the raw window size so that the output reserve does not cause unexpected tier demotion. After compression, `context_history` shrinks to `[SUMMARY_MSG, recent_5_msgs]` (~5–15K tokens) — the threshold does not re-fire until substantial new history accumulates, so lower thresholds do not cause compression loops. This "implicit incremental compression" means the previous summary message is simply re-compressed along with new messages on subsequent cycles — no explicit `previousSummary` tracking is needed.

`AgentChatContextService` now estimates compression need from the formatted final-send message view built by `formatMessagesForApi(...)`, rather than only from raw `context_history` token counts. Token estimation uses a **three-pillar approach** to prevent context overflow:
1. **VS Code Copilot alignment**: message overhead constants (+3/msg, +3 completion, +1 name), tool definitions (+16 base, +8/tool, ×1.1 safety, key+value tokenization), tool_calls ×1.5 safety, encoder selection from CAPI model metadata (`o200k_base`/`cl100k_base`).
2. **API Usage anchoring**: after each API response, `usage.prompt_tokens` is fed back via `anchorTokenEstimate()` to compute a `correctionRatio` that calibrates subsequent local estimates against server-side reality.
3. **Model correction factor**: pre-first-API-call, models with known tokenizer gaps (Claude ×1.4, Gemini ×1.1) apply a preset correction factor; this is superseded once API anchoring takes effect.

Output token space is reserved by subtracting `min(maxOutputLength, 20000)` from the context window before threshold comparison.

It still reports additive token components by deriving a formatted-payload total first, then splitting it into approximate `systemPromptTokens` and `contextHistoryTokens` for compatibility with existing consumers. Compression only runs inside the active send / start-chat turn loop and must not run during standalone session initialization. `AgentChat.initialize()` may still kick off context-stat recalculation, but that refresh must remain fire-and-forget so session-open cache hydration is not blocked on token counting or prompt/tool enumeration. `FullModeCompressor` now structurally trims oversized message bodies before summarization, splits large middle-history spans using a conservative token-aware prompt budget, runs first-layer conversation chunk summaries with bounded concurrency, and still keeps merge-stage recursive summarization sequential so chunk ordering remains deterministic. It also re-truncates any single message that would still exceed that prompt budget and recursively re-chunks merge summaries so the second-stage merge cannot fall back to one unbounded prompt. The compression helper in `../llm/contextCompressionLlmSummarizer.ts` owns the structured summary template, output language, and prompt-overhead calculation; that overhead must be computed against the real summary request shape, including both the dedicated system prompt and the generated user prompt. `summaryPromptTokenBudget` is treated as a hard ceiling against that helper-owned request shape. If it is lower than the request overhead, compression fails fast and falls back instead of silently widening the budget. Recursive merge also has a bounded depth limit so pathological sessions fall back instead of triggering unbounded serial LLM calls. `COMPRESSED_CONTEXT` must only be emitted after a shorter context history is actually installed.
If the provider still rejects the payload with an overflow-style `GhcApiError`, `AgentChatTurnRunner` now performs one forced compaction retry before surfacing the failure. This retry is intentionally bounded to a single attempt to avoid infinite retry loops on irreducible sessions.

### Cancellation
Every send creates a `CancellationTokenSource` stored in `AgentChatManager`. `CancellationToken` is threaded through the LLM streaming call and all tool executions. Calling `stopChat` cancels the source; `CancellationError` propagates up and is caught silently.
When cancellation happens while a `choice` or `form` interactive request is pending, `AgentChatManager.cancelChatSession()` must also interrupt the pending request via `interactiveRequestManager` so the turn does not remain blocked waiting for UI input after the chat is already cancelled. Persist this as a distinct `chat-cancelled` interaction resolution instead of collapsing it into renderer-unavailable fallback or explicit user skip semantics.
When cancellation happens during LLM streaming, `AgentChatStreamingService` can raise a `StreamCancellationError` carrying the accumulated partial response. `AgentChatTurnRunner` persists visible partial assistant text before rethrowing the cancellation so session switch, refresh, and restart reload the same text the user already saw. If the partial response has begun emitting tool calls, only the text portion is persisted; unmatched partial tool calls are discarded to avoid orphaned tool-call history. `AgentChatManager.cancelChatSession()` waits for the cancelled turn to unwind to idle before returning so this partial-response save has a chance to drain through the serialized save chain.

### Scheduled Runner Tracing
`AgentChatManager.runScheduledJob()` and `AgentChatManagerScheduledRunner` now emit `scheduler.runtime.*` logs that bridge scheduler execution with chat runtime creation. Preserve the `chatSessionId`, `chatId`, and `runtimeMode='scheduled-silent'` correlation fields when modifying scheduled execution flow.

### Scheduled Preflight Failures
`AgentChatManager.runScheduledJob()` accepts `preflightError` from `SchedulerManager.executeJob` when a non-manual scheduled run's required MCP dependencies are unavailable. The runner must still create/register the scheduled-silent chat session, save initial `running` metadata, append the injected user prompt plus a visible assistant failure message, then enter the normal failure cleanup path (`schedulerExecutionStatus: 'failed'`, unread state, failed completion notification, background instance disposal). It must not call `streamMessage` on this path because the agent would run with a known-missing tool dependency and could incorrectly succeed.

### Scheduled Run Cancellation
`AgentChatManagerScheduledRunner.run()` registers a `CancellationTokenSource` via the registry (`getOrCreateCancellationSource(chatSessionId)`) and threads `source.token` into `agentChat.streamMessage(...)`, mirroring foreground chats. This is what makes a *running* scheduled session cancellable: opening it promotes the instance from `scheduled-silent` to `interactive` (the foreground/current session), so the renderer's Cancel button routes `agentChat:cancelChat` → `cancelChatSession()` to that registered source. Without it, cancel only flips the UI to idle while the stream keeps running. A user cancel surfaces as a `CancellationError` in the runner's catch and is treated as **interrupted**: the session is marked `failed` with `SCHEDULER_USER_CANCELLED_ERROR` so the sidepane renders `Interrupted · Cancelled by user`, and unlike a real failure it skips the unread badge. Instance disposal on cancel is **runtime-mode dependent** (the runner reads `getRuntimeMode(chatSessionId)`): if the run was opened it was promoted from `scheduled-silent` to `interactive`, so disposal is **skipped** to keep the foreground session open like a normal chat; if it is still a background `scheduled-silent` run — cancelled from the Schedules sidepane "..." menu without ever being opened — the runner **disposes** the managed instance so it does not leak a cached instance with no idle timer. The runner returns `{ success: true, cancelled: true }` so the job resolves without failure backoff. The source is always cleared afterwards in a `finally`.

### Per-Chat Reasoning Effort
`agentChatStreamingService.ts` injects an endpoint-specific reasoning fragment into the outbound request when the active model advertises `capabilities.supports.reasoning_effort`. The persisted choice lives on `chat.agent.reasoningEffort` (see [userDataADO](../userDataADO/ai.prompt.md)) and is plumbed through `agentChat.ts` → `getCurrentModelConfig()` → `AgentChatStreamingServiceDeps.getCurrentModelConfig().reasoningEffort`. The streaming service computes a vendor-aware default via `getDefaultReasoningEffort(modelId, supportedEfforts)` (Claude→high, GPT→medium) and passes both the user's choice and the default to `buildReasoningParams()` (see [LLM](../llm/ai.prompt.md)). When the user has not explicitly chosen a tier, the default is sent — an explicit `reasoning_effort` is **always** included for models that support reasoning, ensuring the wire payload matches the UI's "(default)" label. A diagnostic `🧠 reasoning_effort` log records `model / endpoint / requested / supported / applied` for every send so the actual wire payload can be inspected at runtime.

### Global System Prompt Injection
`getGlobalSystemPromptAsMessages()` prepends a fixed system message to every API call. It enforces the file workspace restriction and `execute_command` safety rules. `{{OPENKOSMOS_*}}` placeholders (e.g. `{{OPENKOSMOS_WORKSPACE_PATH}}`) are resolved by `openkosmosPlaceholderManager` at send-time, not at session creation.

Custom agent prompts are persisted as `ChatAgent.system_prompt = { "Base.md": string, "AGENTS.md": string }`. Keep `AgentChat.AgentConfig.system_prompt` in that object shape so config callers see the persisted schema; only `AgentChatPromptService.getLatestCustomSystemPrompt()` should render it to text before creating the system message.

An `INFORMATION RETRIEVAL PRIORITY` section (placed just before `FILE OPERATIONS WORKSPACE RESTRICTION`) instructs the agent to search its Knowledge Base and Current Chat Session Deliverables BEFORE answering, falling back to general knowledge / web / wider file system only when those cannot answer. It includes a file-type routing table because using the wrong reader silently fails: `.txt/.md/.csv/.json`/code → `read_file`, `.html` → `read_html`, and `.pdf/.docx/.xlsx/.pptx` → `read_office_file` (`read_file` rejects them as binary and `search_file_contents` silently skips them). The `read_file` tool description (`mcpRuntime/builtinTools/readFileTool.ts`) carries the same routing hints so the model is steered toward the correct reader at tool-selection time. The section also carries an **OVERRIDE** clause (Phase 1.5): named-entity questions (device/service/VM/host/account/person/file/project) MUST consult these two directories BEFORE invoking any execution, agent, or ask-the-user tool — this counters keyword-triggered tool shortcuts observed in production where the agent skipped the KB even when the answer was a file in it.

### Knowledge-Source Directory Index Injection (Phase 1.5)
`getAgentSpecificSystemPrompt()` (`agentChatPromptService.ts`) injects a **bounded, flat relative-path listing** of the Knowledge Base directory (right after the KB path line) and the Current Chat Session Deliverables directory (right after its path line). This lets the model SEE which files exist — giving keyword association a correct anchor (e.g. `Azure-VM/yanhu-claw-2-key.pem`) — without injecting file content. The walk is synchronous (`buildDirectoryIndex` / `formatDirectoryIndexLines`, reusing the same `fs.readdirSync` pattern as the skills scan, so it stays inside the synchronous prompt path — do NOT switch to the async `SearchFilesTool`). Bounds: `MAX_FILES = 100` per directory (overflow → `... and N more file(s) (use search_files / search_file_contents to explore)`), `MAX_DEPTH = 3` levels, `SCAN_LIMIT = 5000` entries, skipping `.git`/`node_modules`/`dist`/`build`/`.claude`/`.DS_Store` (`.claude` skills are surfaced separately). The whole walk is wrapped in try/catch and fails open (the path line stays, the index is omitted). A deliverables directory that does not yet exist emits "No deliverables have been produced in this session yet." instead of an index. Full PRD: [../../../../ai.prompt/kb-directory-index-prd.md](../../../../ai.prompt/kb-directory-index-prd.md).

The global prompt no longer injects task-CRUD-specific instructions or brand-specific task confirmation behavior. Scheduled-silent jobs keep their normal non-interactive policy through `interactionPolicy`.

`AgentChat` also appends session-specific knowledge metadata to the runtime prompt from `chat.agent.knowledge`. The persisted knowledge contract is limited to the configured Knowledge Base directory; external message or email source metadata does not participate in chat-time prompt assembly.

### Tool Argument Normalization
LLMs occasionally emit malformed or concatenated JSON in tool-call `arguments`. `normalizeToolCalls()` in `agentChatUtilities.ts` splits these into multiple valid calls and assigns synthetic IDs. This is transparent to the LLM — results are returned under the original IDs.

### Skill Snapshots
Skills are snapshotted via `buildChatSkillSnapshot()` at the next turn boundary and stored in the in-memory `chatSkillSnapshotStore` (`Map<alias, Map<chatId, ChatSkillSnapshot>>`), not in `profile.json`. `AgentChatPromptService.refreshSkillSnapshotIfNeeded()` reads `chat.agent.skills`, resolves the registry through `skillsConfigManager.getSkills(alias)`, compares binding and registry signatures against the store entry, and sets or clears the store synchronously. `getAgentSpecificSystemPrompt()` injects `chatSkillSnapshotStore.get(alias, chatId)?.prompt`. Binding changes and skill CRUD clear affected store entries; old persisted `skill_snapshot` values are dropped on profile load.

### Interactive Requests
`AgentChat` now routes all user-blocking interactions through one model: `approval`, `choice`, and `form`. Each request is stored as the session's `pendingInteractiveRequest`, resolved via `interactiveRequestManager`, and persisted as `interaction_history` on the chat session file. This keeps interactive artifacts visible in the renderer without inserting synthetic assistant messages between `tool_calls` and `tool` results. Current runtime behavior temporarily bypasses outside-workspace path validation and approval requests in `batchValidateAndRequestApproval()`, so tool calls are auto-approved until that gate is re-enabled. Dynamic tool-driven input can now enter the same lifecycle through the `request_interactive_input` built-in tool, which is post-processed into a `choice` or `form` request before the turn resumes.

Interactive availability is controlled by a runtime interaction policy. Foreground chats use `allow-ui`; scheduled-silent runs and sub-agent auto-wake synthetic parent turns use `forbid`. `AgentChatToolExecutor` copies the interaction policy into `ToolExecutionContext` so built-in tools that require a visible local UI (for example `computer_use`) can reject scheduled/non-interactive turns before executing. When the policy is `forbid`, interactive requests throw `NonInteractiveRuntimeInteractionError` so unattended runs fail fast instead of silently skipping hidden input requests.

## Gotchas
- ⚠️ **`getAgentSpecificSystemPrompt` identifies the current chat by `chat_id` (via `getChatId()`), never by agent name.** Under 1 Chat : N Agents an agent name can be shared/duplicated across chats, so a name-based `allChats.find(...)` can select a DIFFERENT chat and inject the wrong knowledge base, workspace, and skill-snapshot path (cross-chat data leakage into the prompt). The lookup matches `chat.chat_id === chatId` first and only falls back to a name match when no chat matches the id (a transient chat not yet in the cache). Because `getAllChatConfigs` returns agent_ids-only cache chats, the matched chat's agent is then resolved with `getChatPrimaryAgent`, never raw `chat.agent`. Keep both properties when editing this method.
- ⚠️ **Workspace is chat-owned; knowledge is agent-owned.** Chat-session deliverables, Hook cwd, `{{OPENKOSMOS_WORKSPACE_PATH}}`, built-in tool workspace roots, and fork/session directories must use `getChatWorkspace(chatConfig)`. Knowledge-source prompt text and `@knowledge-base:` resolution must use the resolved agent's `knowledge.knowledgeBase`. Do not reintroduce `agent.workspace` reads except as migration fallback inside `getChatWorkspace`.
- ⚠️ **Memex capture provenance must come from the current persisted turn, not model-authored paths alone.** `AgentChatToolExecutor` passes `chatHistory`, `currentUserMessageId`, `chatSessionFilePath`, `chatSessionFilesPath`, `ensureChatSessionSaved`, `skipPersistence`, and agent identity into the captured tool context. Do not let `capture` resolve arbitrary message ids from model text, do not capture streaming assistant output, and do not skip the save barrier for `source_type:'chat-session'`.
- ⚠️ The KB/deliverables directory index (`buildDirectoryIndex`) walks the filesystem **synchronously on every prompt build** (every turn). It is bounded by `MAX_FILES=100`, `MAX_DEPTH=3`, and `SCAN_LIMIT=5000` entries specifically to cap this per-turn cost — do NOT relax these without measuring event-loop impact (a huge KB, e.g. a home dir mistakenly set as KB, could otherwise issue thousands of blocking `readdirSync` calls per turn and stall streaming, echoing the excessive-logging UI-freeze postmortem). When `SCAN_LIMIT` is hit the formatter emits a generic "directory too large" note instead of an exact `N more` count, because the truncated walk's `totalFiles` would understate the real total. The walk is intentionally NOT cached across turns: the deliverables dir changes mid-session (tools write files), and a stale KB cache would risk the same class of bug as the Phase 1 stale-estimate incidents. A session-scoped mtime cache is a possible Phase 2 optimization, deliberately deferred.
- ⚠️ `AgentChat` instances are keyed by `chatSessionId`, not `chatId`. A single agent (chatId) can accumulate multiple stale instances if sessions are created rapidly — idle cleanup is the only eviction path.
- ⚠️ Idle cleanup protection has two distinct layers: `cleanupIdleInstance` unconditionally skips `currentChatSessionId` (the session the user last selected), and `isProtectedSession` checks foreground state plus runtime mode. Modifying either layer without understanding both can reintroduce the v2.8 idle-eviction bug (current session destroyed on Alt+Tab) or the inverse (non-current sessions incorrectly kept alive).
- ⚠️ `AgentChat` is now a thin facade over lazily-instantiated services and a dedicated turn runner. Public wrapper methods should stay shallow; do not move orchestration logic back into the facade.
- ⚠️ `AgentChat` no longer supports inheritance-based overrides such as `Object.create(AgentChat.prototype)` hook injection. Extend behavior through the extracted services or manager-level composition instead.
- ⚠️ Cancel chat must interrupt any pending interactive request. Cancelling only the main cancellation token is insufficient because the turn may be suspended inside `interactiveRequestManager.createPendingRequest()` rather than inside an abort-aware tool or streaming call.
- ⚠️ When a user clicks `Skip` or cancels an interactive input card, the post-processed tool result must explicitly state that the user declined the request. Returning only an empty payload or bare `status: 'skipped'` is insufficient and can cause the model to immediately re-issue the same interaction.
- ⚠️ Do not collapse renderer-unavailable fallback into a user skip when post-processing `request_interactive_input`. If no active event sender exists, the returned tool result must say the UI receiver was unavailable rather than claiming the user explicitly declined.
- ⚠️ Computer Use approval cards are security-sensitive choice requests. `agentChatToolPostProcessor` must trust only `selectedPresetValues === ['approve']` with no `customValues`; do not approve from merged `selectedValues` alone, because the renderer's generic "Other" entry can also submit the literal text `approve`.
- ⚠️ That same distinction must survive persistence: `interaction_history` entries need the fallback/timeout source recorded and summarized accurately, or the renderer timeline and audit trail will drift from the tool result semantics seen by the model.
- ⚠️ Scheduled-silent runs must remain `forbid` for interaction policy. They cannot degrade to silent skip or plain-text follow-up, or unattended jobs will produce unreliable results instead of explicit failures.
- ⚠️ Scheduled-silent runs must keep runtime `chatStatus` and persisted `schedulerExecutionStatus` as separate dimensions. Do not persist `chatStatus` into session metadata to satisfy UI state; manager-driven runtime propagation is the correct layer.
- Warning: A *running* scheduled session is only cancellable because `AgentChatManagerScheduledRunner` registers a cancellation source and threads its token into `streamMessage`. If you stop registering the source (or pass `undefined`), `cancelChatSession()` finds nothing to cancel and the Cancel button silently no-ops while the stream keeps running — the exact bug this wiring fixes. A user cancel must be persisted as `interrupted` before the runner returns `{ success: true, cancelled: true }`; if that persistence fails, return `{ success: false }` so the scheduler does not mark the job completed while the session remains persisted as running. Disposal on cancel is **conditional on runtime mode**: keep the instance only when it was promoted to `interactive` (the user opened it); a still-`scheduled-silent` background run cancelled from the sidepane "..." menu must be disposed or it leaks a cached instance with no idle timer.
- Warning: Scheduled preflight failures are user-visible run failures, not skipped runs. Keep the `preflightError` path before `streamMessage`, after initial session persistence, and inside the same catch/failure cleanup semantics as model/tool errors so the sidepane, unread state, and failed notification remain consistent.
- ⚠️ `executeToolCall()` must keep returning structured tool errors for truncated JSON, invalid JSON, and approval denial. Throwing instead of returning will break the assistant/tool message pairing and can cascade into 400 follow-up API failures.
- ⚠️ `executeToolCall()` is the **central no-response watchdog** for builtin tools. It owns the per-call `AbortController` (wired to the cancellation token + active-tool handler), so it arms an `InactivityTimer(TOOL_IDLE_TIMEOUT_MS)` for builtin tools (gated by `mcpClientManager.isBuiltinTool(name) && !SELF_MANAGED_IDLE_TOOLS.has(name)`), injects `reportActivity` into the execution context, and races the tool promise against an idle-rejection so the loop unblocks even if a tool ignores the abort signal. Do **not** arm it for external MCP tools (they self-manage their idle budget — double-watching false-kills streaming servers) and do **not** feed it from synthetic heartbeats (only real output). Full rationale in [mcpRuntime/ai.prompt.md](../mcpRuntime/ai.prompt.md) "Time constraints".
- ⚠️ `NonInteractiveRuntimeInteractionError` is the one intentional exception to the “do not throw out of tool execution flow” rule. The turn runner must persist a failure tool message first, then rethrow so scheduled execution fails fast.
- ⚠️ Replay sanitization must only preserve the first contiguous tool result for each tool-call id immediately adjacent to its parent `assistant(tool_calls)` message. Cross-turn late tool errors/results and duplicate same-id tool messages must be stripped before API replay, or Claude-compatible endpoints can reject the history with `tool_use` / `tool_result` pairing errors.
- ⚠️ `AgentChatManager.streamMessage()` must reject non-idle sends. Renderer/UI guards are advisory only; the main process is the final boundary that prevents cross-turn user-message insertion while a tool or response turn is still active.
- ⚠️ Each queued steering prompt is a FULL turn, not a tail appended to the original turn. The shared drain in `steeringQueueConsumption.ts` runs, per queued prompt: UserPromptSubmit hook -> persist + emit -> `runFollowUpTurn` (model turn) -> `runStopHook` -> `clearTurnHookBuffers`. Critically, `AgentChat.streamMessage()` runs the ORIGINAL turn's `runStopHook` + `clearTurnHookBuffers` BEFORE the drain begins (not once after it), because the turn-scoped hook buffers (`turnHookContexts` / `turnHookSystemMessages`, fed by UserPromptSubmit/PostToolUse `applyHookResultIfActive`) are injected into every subsequent model call via `syncHookBuffersToPrompt`. If they are not reset between queued prompts, prompt N's model turn inherits prompts 1..N-1's accumulated hook context (a real leak). Stop's own context uses the separate `observationalHookContexts` buffer, so clearing turn buffers after Stop is safe. The queued drain runs the UserPromptSubmit hook via `runQueuedUserPromptSubmitHook` (NOT `runUserPromptSubmitLifecycle`): the hook runs but its block is NOT surfaced and its allowed-context is NOT applied yet — both are deferred until AFTER the still-queued commit check. This matters four ways: (1) a user Cancel (token) that lands while the hook awaits does NOT throw (the hook resolves benignly), so the drain re-checks the token immediately after the hook and throws BEFORE committing — the peeked prompt stays queued instead of being persisted without a response; (2) a prompt the user removed during the hook window fails the commit-time `takeQueuedSteeringMessageById` (returns null) and is skipped WITHOUT surfacing any block, so a cancelled prompt leaves no stray "blocked" message; (3) a blocked prompt is surfaced (persist + emit) WITHOUT idling the session — `surfaceBlock()` omits `setIdle` because the drain holds SENDING_RESPONSE across queued prompts, and idling mid-drain would break that mutex and let a concurrent send/steer interleave; a blocked prompt gets NO Stop/clear (it never ran a turn), but a surfaceBlock failure before it is announced restores it to the front; (4) an allowed prompt's hook context is applied (`applyAllowed`) only AFTER the commit succeeds, so a prompt removed during the hook never leaks context into a later prompt's turn. Restore-on-throw and cancel-safety: the drain PEEKS each prompt (does not remove it) and runs its UserPromptSubmit hook while it is still queued, then COMMITS by taking it by id at the commit point. It persists/runs the PEEKED hook-validated snapshot (`message`), NOT the value the commit-time take returned (`committed`) — an in-place edit landing during the hook window mutates the queue entry but cannot change the content the hook already approved (the take is only the atomic presence check that lets a concurrent cancel win). A hook throw leaves the peeked prompt in the queue untouched (no take, no restore — cancellation still propagates to `agentChatManager`). Only AFTER the commit-take succeeds does the prompt leave the queue; a persist/turn failure before it is consumed (persisted + announced) restores it to the FRONT via `restoreQueuedSteeringMessageToFront` and rethrows, so a cancelled/failed drain never strands the prompt in FIFO order. A throw AFTER the prompt is consumed (during its model turn or Stop hook) does NOT restore, because the prompt is already in the transcript and its renderer draft already removed; restoring then would duplicate it. The restore always re-queues the COMMITTED entry the take returned (`committed`), NOT the stale peeked snapshot (`message`): if the user edited the prompt during the hook window, `updateSteeringMessage` REPLACED the queue entry with a new object, so `committed` holds the edited content the renderer still shows — restoring `committed` keeps main's queue in sync with the renderer draft and never loses the edit (there is no policy concern because the restored prompt is re-hook-validated on the retry before it is persisted; only the immediate persist within a single attempt uses the hook-validated `message`). Invariant: a prompt leaves the queue only when it is consumed/committed or explicitly removed. Finally, `AgentChat.streamMessage()`'s PRIMARY-prompt block path also drains: instead of returning early on a UserPromptSubmit block it calls `runUserPromptSubmitLifecycle(..., { idleOnBlock: false })` to keep the session SENDING_RESPONSE, clears turn buffers, then runs the SAME drain with the block messages as the initial result. Without this, prompts the user queued while the (possibly slow) primary block hook ran would be stranded — the enqueue IPC saw the session busy and never started the idle pump, and the old early-return skipped the end-of-turn drain. `idleOnBlock` defaults to true, so `editUserMessage` (the other `runUserPromptSubmitLifecycle` caller) is unchanged and still idles on block.
- ⚠️ Queued-steering consumption is now UNIFIED onto ONE cancel-safe drain. There are three triggers, all funneling through the shared `drainQueuedSteeringFollowUpTurns` (peek -> hook -> commit-by-id) in `steeringQueueConsumption.ts`: (1) the end-of-turn FIFO drain inside `AgentChat.streamMessage()` (the normal path — a prompt enqueued mid-turn is consumed when that turn finishes); (2) manual Steer (`agentChat:steerQueuedSteeringMessage`), which promotes the draft to the head and, if idle, schedules the same fire-and-forget idle pump; and (3) the fire-and-forget idle pump (`consumeQueuedMessagesWhileIdle`) that `agentChat:enqueueQueuedSteeringMessage` / `agentChat:updateQueuedSteeringMessage` kick off **only when the session is already idle**, closing the busy->idle race where the enqueue IPC arrives after the drain finished. Triggers (2) and (3) both go through `agentChatManager.drainQueuedSteeringWhileIdle(chatSessionId)` -> `AgentChat.drainQueuedSteeringWhileIdle(token)`; the manager method obtains the session's registry cancellation token via `getOrCreateCancellationSource` EXACTLY like `streamMessage`, so a user Cancel during an idle/manual drain reaches `source.cancel()` and aborts it. The instance method sets status to SENDING_RESPONSE synchronously (before its first `await`) and back to IDLE in a `finally`, which (a) makes a second concurrent drain's `getChatStatus()!=='idle'` guard reject it — a built-in mutex — and (b) re-emits IDLE afterward to restart idle timers; it returns `[]` immediately for external-agent sessions and for an empty queue. The idle pump is additionally serialized per session by the module-level `idleConsumingSessions` Set and MUST stay fire-and-forget — never `await` it in a queued-steering IPC handler (it can run a full turn; awaiting it would block the response far past the <100ms critical-path budget). After the drain, `consumeQueuedMessagesWhileIdle` releases the `idleConsumingSessions` guard and then RE-CHECKS the queue (`steeringQueue.hasPending()`), but ONLY after a SUCCESSFUL, non-cancelled drain (`drainResult.success && !drainResult.cancelled`): the manager drain awaits unread persistence AFTER the instance drain flips status back to IDLE, so an enqueue that lands in that window sees idle, binds its WebContents, and schedules a pump the still-held guard silently skips — the re-check re-pumps any such otherwise-stranded message (reusing the racing enqueue's still-bound sender so its `queuedSteeringMessageConsumed` still reaches the renderer) and only releases the bound sender (`setEventSender(null)`) once the queue is genuinely empty. A CANCELLED drain (the cancel-safe drain deliberately leaves the peeked prompt queued after a user cancel) or a FAILED drain (a prompt restored to the front) is NEVER re-pumped — re-pumping would undo the user's cancel by resending the cancelled prompt, or spin forever on a deterministic hook/persist failure — so those paths release the bound sender and leave the queue for manual action, mirroring the end-of-turn cascade's `!result.success || result.cancelled` break. The pump breaks on `!result.success || result.cancelled`, so a user cancel mid-drain stops auto-consumption instead of marching through the remaining queue. The take-then-stream `streamTakenQueuedMessage` helper and its committed/not-committed loss contract were REMOVED — the peek->hook->commit-by-id drain now owns all cancel-safety/restore behavior for every trigger. Residual: a prompt enqueued during a non-steering turn's `runStopHook` tail window with no subsequent enqueue stays queued until the next action (still manually steerable); the dominant race (enqueue right after the turn visibly ends) is fully closed because that IPC arrives when main is already idle.
- ⚠️ An in-progress EDIT holds its queued prompt in main so no drain can consume the stale pre-edit content mid-edit. `startEdit` (renderer) fires `agentChat:setQueuedSteeringMessageEditing(id, true)` -> `AgentChatRuntimeState.setSteeringMessageEditing`, which records AT MOST ONE `_editingSteeringMessageId` (mirrors the renderer's single-edit invariant; setting a new id auto-releases the prior one, and `(id, false)` clears only when it matches so a stale unmark can't free a different draft's hold). A held id is INVISIBLE to the shared drain: `peekNextSteeringMessage` returns null when the head is held (the drain STOPS/waits at that head — it does NOT skip ahead to a later prompt, preserving FIFO and the user's "update the message at its original queue position" requirement), and `takeSteeringMessage`/`takeNextSteeringMessage` return null for a held id/head (so the rare edit-DURING-this-draft's-hook-window case fails the commit-time take -> `continue` -> next peek sees the now-held head -> drain exits with the draft still queued+held, instead of persisting the peeked pre-edit snapshot and losing the edit). The hold is released by `updateSteeringMessage` (the submit-edit signal — content updated + pump-if-idle so the edited content is consumed) and defensively by `removeSteeringMessage`/`clearSteeringMessages`. The IPC handler (`agent-chat-steering.ts`) is fire-and-forget: hold (`editing:true`) must NOT pump; release (`editing:false`, i.e. cancelEdit) re-pumps ONLY when the session is idle (binds `event.sender` + `scheduleIdleQueueConsumption`) so a head the drain skipped while held is consumed once the edit is abandoned. Renderer `startEdit`/`cancelEdit` use `syncQueueError` with NO optimistic rollback — a setEditing failure means main lost the instance (nothing to consume anyway); forcing the draft out of `editing` would yank the in-progress edit out of the composer.
- ⚠️ Two idle-pump edge cases guard the shared fire-and-forget pump (`consumeQueuedMessagesWhileIdle` in `agent-chat-steering.ts`): (1) **Deleting the editing-held head must re-pump.** The drain WAITS behind a held head, so if the user cancels (removes) the draft they were editing while the session is idle, nothing else re-drives the drain and the messages queued behind it are stranded. The `removeQueuedSteeringMessage` handler captures `steeringQueue.editingMessageId() === messageId` BEFORE `remove` (remove clears the hold) and, only when that held draft was removed AND the session is idle, binds `event.sender` + `scheduleIdleQueueConsumption`. An ORDINARY delete (no hold — e.g. trimming the queue after a cancel or while the start-with-queue dialog is open) must NOT auto-send the rest of the queue. (2) **The post-drain re-check requires real consumption progress, not just `hasPending()`.** `AgentChat.drainQueuedSteeringWhileIdle` returns `[]` WITHOUT consuming for EXTERNAL-agent sessions (`shouldRouteToExternalAgent()`), so `hasPending()` stays true forever; re-pumping on `hasPending()` alone would reschedule the same no-op drain in a hot infinite loop (event-loop starvation). The re-pump is therefore gated on `consumedSomething = (drainResult.data?.length ?? 0) > 0` AND `hasPending()` — real progress bounds the loop while still catching the documented busy->idle race (whose drain DID consume the head, so `data` is non-empty). A held head does NOT trigger this loop because `hasPending()` is already false for a held head (peek returns null); the loop is specifically the external-agent drain-returns-empty-with-a-consumable-head case.
- ⚠️ The renderer's "start with queued prompts?" confirmation (`useQueuedComposer.pendingQueueStartMessage`) is scoped to the session that raised it. The session-change effect clears it UNCONDITIONALLY (before the `isEditMode` guard) so confirming after switching chats cannot send the old session's prompt into the new one or clear the new session's queue. Because a pending start-message is only ever set for a truthy `chatSessionId` and is dropped on any switch, `chatSessionId` is guaranteed unchanged (and truthy) inside `submitPendingQueueStartMessage`, so that callback intentionally has no redundant `&& chatSessionId` guard (clearSession is null-safe regardless). Copying only the JSON history will leave `execute_command` and other workspace-scoped tools pointed at a missing `{workspace}/{YYYYMM}/{chatSessionId}` directory. Workspace provisioning failures must abort the fork instead of returning a seemingly usable session.
- ⚠️ `globalSystemPrompt.ts` content is injected on every API call. Changes to it affect all active and future sessions immediately (no versioning). Large additions here directly inflate token usage for every turn.
- ⚠️ `normalizeToolCalls` can split one LLM tool call into N calls with synthetic IDs. Downstream code in `agentChat.ts` that correlates tool results by ID must tolerate these synthetic IDs.
- ⚠️ Do not insert ordinary assistant summary messages for approval/form/choice outcomes while a tool turn is in progress. That can break the `assistant(tool_calls)` → `tool` pairing expected by downstream rendering and replay.
- ⚠️ Outside-workspace validation is currently bypassed in `batchValidateAndRequestApproval()`. If you re-enable `SecurityValidator`, update the runtime flow, renderer UX, and docs together.
- ⚠️ On Windows, `Notification` objects must be kept in `activeNotifications` map or click events are silently dropped due to GC. Do not remove entries before the click handler fires.
- ⚠️ `AgentChatManager` no longer owns the core registry Maps/Sets, BrowserWindow/notification lifecycle, or scheduled-silent orchestration directly. New stateful lifecycle logic should usually land in `agentChatManagerRegistry.ts`, `agentChatManagerSessionCoordinator.ts`, `agentChatManagerNotificationBridge.ts`, or `agentChatManagerScheduledRunner.ts`, not back in the singleton facade.
- ⚠️ Compression uses `claude-haiku-4.5` as a secondary LLM call inside an active chat turn. Auth token failures during compression fall back to truncation — the user sees no error, but conversation context may be degraded.
- ⚠️ Compression gating should follow the formatted final-send payload, not only raw `context_history` message arrays. Tool replay sanitization and payload formatting can materially change real prompt size.
- ⚠️ `COMPRESSED_CONTEXT` is a verified outcome state, not just evidence that a compaction branch executed. If no shorter history is applied, the status must not advance to `COMPRESSED_CONTEXT`.
- ⚠️ Compression must stay inside the active send / start-chat loop. Do not reintroduce standalone initialization-time compaction, or oversized session opens can block renderer cache hydration behind hidden LLM work.
- ⚠️ Context token refresh during `AgentChat.initialize()` must remain non-blocking. If you await it in the open path, large sessions can regress back to the same `Opening chat history...` stall pattern even without compression.
- ⚠️ Token estimation correction factors (Claude ×1.4, Gemini ×1.1) are empirically derived. If API anchoring consistently shows a different ratio, consider updating the preset values. The `correctionRatio` is per-session and resets on session creation.
- ⚠️ `ToolsTokenCalculator` now recursively tokenizes both keys and values of tool definitions (aligned with VS Code Copilot). Modifying tool schema shapes can significantly change token counts.
- ⚠️ Only first-layer conversation chunk summaries are allowed to run concurrently. Merge-stage recursive summarization must remain sequential unless its ordering, retry pressure, and fallback behavior are redesigned together.
- ⚠️ Overflow recovery is bounded to one forced compaction retry in `AgentChatTurnRunner`. Preserve that bound unless you also add explicit retry diagnostics and loop guards, or unrecoverable oversized sessions can get stuck in retry cycles.
- ⚠️ `FullModeCompressor` no longer assumes either the raw middle history, any single dense message, or the summary-merge stage is safe in one call. Any future changes must preserve structural pre-trimming, hard prompt-budget enforcement, per-message re-truncation, and recursive merge chunking, or imported giant tool-result sessions can break compression again.
- ⚠️ `AgentChatSessionService.saveChatSession()` still relies on `saveChain` serialization. Any future turn-runner or persistence refactor must preserve this ordering guarantee.
- ⚠️ `AgentChat.drainBackgroundSubAgentResults` is the ack site for the durable sub-agent **delivery ledger**: after it injects the `<task-notification>` into `context_history`, it calls `saveChatSession()` and only acks (`ackPendingDeliveries(sessionId, taskIds)`, imported statically from `../subAgent/subAgentDeliveryLedger`) when `saved.success` is true. Ack-after-**successful**-persist is load-bearing — acking before the save re-opens a crash-after-drain loss window, and never acking (letting the ledger entry survive a restart) replays an already-delivered result. Note `saveChatSession()` resolves `{ success: false }` on a failed write WITHOUT throwing, so the surrounding empty `catch` does NOT cover that path; the explicit `saved.success` gate is what stops a silent persist failure from deleting an undelivered entry. Both the gate and the catch leave entries unacked for safe re-delivery on a later turn. See [SubAgent](../subAgent/ai.prompt.md) for the full peek-then-ack-on-persist contract.
- ⚠️ Chat session rename is not store-only. If a session is active in `AgentChatManager`, its in-memory `currentChatSession.title` must be updated together with the persisted session metadata or the next save can revert the renamed title.
- ⚠️ `getCurrentAvailableTools()` treats `mcp_servers` as an **allowlist of servers**, and an empty allowlist grants **nothing**. `mcp_servers: []` (or undefined) MUST yield `[]` (no tools) — never `return allTools`. The per-server loop already encodes the model: an entry `{ name, tools: [] }` = ALL of that server's tools, `{ name, tools: [a,b] }` = only those, a server absent from the array = not used; `builtin-tools` is a normal server under the same rules. Do NOT reintroduce an `if (mcp_servers.length > 0)` gate with an all-tools fallback: it inverts the boundary and leaks every builtin/MCP tool to an agent the user has cleared. Note the two different empty arrays — inner `tools: []` means "all tools of this server", outer `mcp_servers: []` means "no servers → no tools". See [Postmortem: empty mcp_servers leaked all tools](../../../../ai.prompt/postmortem-mcp-empty-servers-all-tools.md).
- ⚠️ Withholding tools from the API is **not enough to stop tool-use hallucination** — the static `getGlobalSystemPrompt()` unconditionally documents the full builtin tool manual (`bing_web_search`, `read_file`, `execute_command`, and other builtin tools) every turn, so a tool-less agent still reads that manual and *imitates* tool calls (emits `<function_calls>…` as plain text with `toolcalls=False`, then fabricates results). Defense: `getCombinedSystemPromptForCurrentTurn()` computes `getCurrentAvailableTools().length` and passes it to `getCombinedSystemPromptForContext(availableToolCount?)`; when the count is exactly `0` it appends `wrapInSystemReminder(NO_TOOLS_AVAILABLE_REMINDER)` overriding the manual. `undefined` = no reminder (non-send/estimation callers). Keep the count computed in the **async** wrapper (`getCurrentAvailableTools` is async) and passed into the **sync** assembler, so the estimated and sent prompts agree. Only the zero-tools case is covered today; the **partial**-tools case (some tools, but not the ones the manual describes) is known debt requiring a dynamic tool manual in `globalSystemPrompt.ts`.

## Anti-Patterns
- Do NOT directly access chat session JSON files — always go through `ChatSessionManager` or `ProfileCacheManager`.
- Do NOT send streaming tokens via IPC invoke/handle — use the `mainToRender` push pattern (see `data-flow.md`).
- Do NOT modify message history arrays in place — always create new arrays to avoid stale references in the renderer.
