## Architecture

### Component Hierarchy
```
ChatView (route sync, session operations)
  └─ ChatViewContent (message filtering, isEmpty/zeroStates, replay)
       ├─ ChatContainer (scroll management, render-item iteration)
       │    └─ ChatRenderItemComponent (per-item type dispatch)
       │         ├─ MessageComponent (completed messages)
       │         ├─ ToolCallsSection (tool call accordions)
       │         ├─ InteractiveRequestCard
       │         ├─ InteractiveAuthCard
       │         └─ ChatInput (inline edit mode)
       ├─ ChatZeroStates (quick-start prompts)
       ├─ ChatInput (main composer)
       └─ ChatSide (schedule / workspace / sub-agent / memex sidepanes, file preview, per-session embedded browser)
```

`ChatView` sits under the `/agent/chat/:chatId/:sessionId` route. It synchronizes the route with the backend session state via `agentChatSessionCacheManager`, handles session fork/select, and dispatches navigation events for agent editing.

### Message Rendering Pipeline
Messages flow through a clear pipeline:
1. `ChatView` reads session status via `CurrentSessionStatus.use()`
2. `ChatViewContent` receives messages via `useMessagesWithStream()`, filters out say-hi messages, determines `isEmpty`/`showZeroStates`, and optionally wraps messages through the replay system
3. `ChatContainer` receives the final message list as props, converts them to `ChatRenderItem[]` via `useRenderItems()` from `ChatRenderItem.tsx`, manages auto-scroll
4. `ChatRenderItemComponent` dispatches each item to the appropriate renderer by type

Completed messages go through `Message.tsx` (static markdown pipeline), in-progress messages go through `StreamingV2Message` (RAF typewriter). Tool calls within a message are rendered inline via `ToolCallsSection` → per-type view components in `toolCallViews/`.

### Render Item System
`ChatRenderItem.tsx` owns the transformation from flat `Message[]` to a typed discriminated union of render items. This centralizes the logic for:
- Grouping consecutive tool-result messages into `tool-calls-section` items
- Detecting in-progress `execute_command` tool calls for activity indicators
- Extracting interactive auth hints from tool results
- Surfacing `pendingInteractiveRequest` as a timeline item

### Queued Steering Drafts
`queued-message.atom.ts` stores queued user drafts per `chatSessionId`. `ChatInput` appends a draft when compose mode submits valid input while a **local** agent session is non-idle, then clears local text and attachments. External-agent chats do not run the local queued-steering drain, so busy external-agent input keeps the cancel affordance and shows a wait warning instead of queueing a draft that main can never consume. `QueuedMessageList` renders the active session's queue as a floating list above the composer. **Cancel** removes only that draft. **Edit** marks the draft as editing and loads the message back into ChatInput; the next submit updates the same queue position. **Steer** routes entirely through main: it calls `agentChatIpc.steerQueuedSteeringMessage(chatSessionId, draftId)` (guarded against a concurrent steer of the same draft by the module-level `steeringDraftIds` set), and main promotes the draft to the queue head then, if idle, drains it through the shared cancel-safe path. Busy Steer intentionally does **not** cancel the active turn; it reorders the draft so the running turn's end-of-turn drain sends it next. The renderer keeps the item visible until `agentChat:queuedSteeringMessageConsumed` removes it; an IPC failure is surfaced via `agentChatSessionCacheManager.setErrorMessage` and the draft stays in the queue. The renderer no longer cancels the turn or optimistically sends on Steer — main owns cancel-safety and consumption. If Steer is requested while a draft is editing, the draft records `pendingSteer` and submits immediately after the edit is submitted. For a `pendingSteer` edit, `submitEdit` promotes the draft through `steerNow` **before** firing the content update, not after: the draft is still main-held at that point (the hold is released only by the update), so the steer's idle drain skips it and only reorders it to the head, and then the update releases the hold and pumps the now-head steered draft first. Firing the update first would let its idle re-pump drain from the current head — an earlier-queued prompt left behind by a cancelled turn — and start that prompt before the steer could promote this one, sending the wrong prompt next. If the session is idle and the user sends a normal new prompt while queued drafts remain, ChatInput opens a confirmation dialog with **Keep queue** and **Clear queue** choices before sending. Queued drafts are not written to persisted chat history and never enter model context until submission succeeds. Queue/cancel/edit/clear mutate the renderer atom optimistically, then mirror to main through `agentChatIpc`; because those IPC wrappers throw on `{ success: false }`, `syncQueueError` rolls back the specific mutation on failure (enqueue removes the ghost draft, cancel re-inserts the draft at its original index, clear restores the pre-clear snapshot only if no new draft was queued meanwhile, edit restores the draft's prior content/status) so the renderer never diverges from main's queue, and it also surfaces the error on the session cache manager. The atom also subscribes to `agentChat:chatSessionCacheDestroyed` (alongside `queuedSteeringMessageConsumed`) and drops that session's drafts when main disposes its instance (idle-cleanup after ~5 min backgrounded, tab close, etc.): main's in-memory queue is gone, so retaining the drafts would leave ghosts main can never consume (an edit+submit would silently no-op against the recreated empty queue). Queued drafts are ephemeral runtime state — never persisted — so mirroring main's disposal is the correct behavior.

### Scroll Management
`ChatContainer` separates scroll ownership from reverse message layout: the outer `.chat-container-reverse` element is the scroll container, while an inner reverse-flow wrapper handles `column-reverse`. The scroll state itself lives in `ChatContainer.hooks.ts` (`useAutoScroll`). Initial latest-position resets track `chatSessionId` and appended message count; `chatId` must not drive those resets because session history switches can happen under the same chat identity. Session-switch latest-scroll performs deferred follow-up passes (`requestAnimationFrame` + short timeout) and temporarily watches message-flow resizes. Streaming and resize-driven latest-scroll respect manual scroll-away via a threshold check. `MessageFlowNavigationRail` is an overlay sibling of the scroll container; it listens to window resize plus a couple of post-mount measurement timers, and adds one passive `scroll` listener on the scroll container for current-turn tracking, but intentionally does not create its own `ResizeObserver`, so it does not interfere with the auto-scroll stabilization observer. The rail does not paint a scrollbar of its own — the native scrollbar is hidden (`.chat-container-reverse` hides its scrollbar) and the auto-hiding overlay scroll bar (`ChatScrollbar`) provides that affordance in the adjacent edge lane — and the rail behaves like GitHub Copilot's message minimap: displayed user-message markers are NOT positioned proportionally to scroll offset — instead every marker is aggregated into a fixed-gap cluster centered on the rail's vertical midline (`getMarkerClusterOffset` spreads them symmetrically; `getMarkerClusterGap` compresses the gap when the cluster would overflow the measured rail height). The rail itself spans the FULL height of `.chat-container-reverse` (`.chat-message-navigation-rail` is `top: 0; bottom: 0`, and its overlay parent `.chat-container-with-overlay` fills the same box), so the cluster's midline coincides with the message container's true vertical center and the cluster has the whole height available before the gap compresses — it must NOT reintroduce the old asymmetric `top/bottom` insets, which shrank the rail and pushed the cluster off-center (reported as the minimap "not filling" the container). The cluster fills at most `MARKER_CLUSTER_FILL_RATIO` (84%) of the rail height and, additionally, `getMarkerClusterGap` reserves `MARKER_CLUSTER_END_INSET_PX` (52px) at the top and bottom so the extreme markers stay clear of the two conditionally-shown overlays that share the rail's right edge — the find bar at the top and the jump-to-latest button at the bottom (`z-index: 5`, above the rail's `z-index: 4`). On tall panes the 84% fill is the binding constraint (its ~8% margin already exceeds the inset), so the inset only matters on short panes, where it pulls the outermost markers inward so they do not slide under either overlay; rails too short to honor both insets fall back to the plain 84% fill so the markers do not collapse onto each other. There is no viewport thumb and no track/drag interaction; navigation is click-only — clicking a marker looks the message up fresh via ChatContainer's `data-chat-render-item-key` anchors (`getRenderItemElementsByKey`) and smooth-scrolls to its real DOM offset (`getScrollTopForElement`). Because off-screen user messages are still `LazyRenderItem` placeholders (a fixed 48px), `getScrollTopForElement` initially *undercounts* the height of the messages above a distant target, so a single click would land short on long chats. To fix this, `scrollToMarker` runs a bounded settle loop after the first hop: a recursive `setTimeout` (`MARKER_SCROLL_SETTLE_INTERVAL_MS`, capped at `MARKER_SCROLL_SETTLE_MAX_PASSES`) re-measures the target each pass and re-aims the smooth scroll whenever it grew by more than `MARKER_SCROLL_SETTLE_THRESHOLD_PX`. Placeholders only ever shrink the measured offset and rendered heights latch, so the true target is monotonically non-decreasing as intervening items render — the loop converges with no overshoot or oscillation and stops once the target has held steady for `MARKER_SCROLL_SETTLE_STABLE_PASSES` consecutive passes, the element disappears, or the pass cap is hit. (It keeps polling that short stability window instead of trusting a single no-growth pass, because lazy items render asynchronously while the smooth scroll is still in flight.) The pending timer id lives in a ref and is cancelled on the next marker click, on unmount, and whenever the marker set changes (keyed by a `markerKeySignature` so streaming, which leaves the user-message keys untouched, never aborts a legitimate loop) — this stops a stale loop from re-aiming with a marker key that would otherwise resolve to a different message after a session switch. This is a one-shot click-triggered timer loop, NOT a `ResizeObserver`, so it never touches the auto-scroll stabilization observer. Hovering or focusing a marker reveals a card with the message preview and a relative timestamp (`formatMarkerTimestamp`). The card is itself a click target that mirrors the hovered marker's jump — users instinctively click the card rather than the thin marker, so a pointer-only `<div>` carries `onClick`→`scrollToMarker(hoveredMarker)` (plus `onMouseDown` `preventDefault`, so clicking the card cannot blur/unmount a keyboard-focused marker before the click lands); the marker `<button>` stays the keyboard/screen-reader control and the card has no ARIA role, so it never duplicates the marker in the accessibility tree. To keep the card reachable, it is dismissed from the cluster's `onPointerLeave` (which fires only when the pointer leaves the cluster AND every descendant — markers + card) rather than the marker's `onMouseLeave`, and a transparent `.chat-message-navigation-tooltip::before` bridges the 8px gap between the card (`right: 42px`) and the cluster's right edge (34px) so travelling marker→card never leaves the cluster's hover region (the bridge abuts the cluster edge and does not overlap the markers, so marker clicks are unaffected). Hovering the cluster also drives a macOS-Dock-style "sound wave": each marker's width comes from `getMarkerWaveWidth(markerOffset, focusOffset)`, a Gaussian (`MARKER_WAVE_SIGMA_PX`) that peaks at `MARKER_MAX_WIDTH_PX` directly under the pointer and relaxes to `MARKER_MIN_WIDTH_PX` away from it, so the crest follows the cursor (`onPointerMove` stores the pointer's offset-from-center in `pointerOffset`; `onPointerLeave` clears it). The rest/peak widths are `MARKER_MIN_WIDTH_PX` (10.5) and `MARKER_MAX_WIDTH_PX` (34); the rail still spans the full width to the chat's right edge, but the cluster and markers are inset from that edge by `--chat-scrollbar-lane` (14px, defined on `.chat-container-with-overlay`) so the auto-hiding overlay scroll bar (`ChatScrollbar`) occupies the lane at the very edge and the two do not overlap. While the cluster is hovered, the rail paints a left-to-right scrim behind the markers via a `.chat-message-navigation-rail::before` pseudo-element (`linear-gradient` from fully transparent on the inner side to the fully opaque white surface colour on the right edge), so chat content fades out under the markers; it is hidden by default (`opacity: 0`) and fades in (`opacity: 1`) only on `.chat-message-navigation-rail:has(.chat-message-navigation-cluster:hover)` (the cluster is the hover target because the rail itself is `pointer-events: none`). The transparent stop uses `rgba(…,0)` rather than the `transparent` keyword to avoid a grey midpoint tint. The rail and in-conversation find bar must not use OS-driven `prefers-color-scheme` branches; theme changes are app-controlled by `data-theme`, and Light must remain the pre-dark-mode baseline. Keyboard focus has no pointer, so the crest falls back to the focused marker's own cluster offset and that marker gets the `is-active` class. Independently of hover, a passive `scroll` listener on the scroll container tracks which user message is currently in view: `getCurrentMarkerKey` picks the marker whose anchor top is the greatest still at or above a reading line set `MARKER_CURRENT_READING_RATIO` (0.5) down the viewport (falling back to the topmost marker before the line), and that marker also gets `is-active`. That effect re-subscribes only when the marker set changes (its dependency is the `markerKeySignature`, not the `markers` array identity) and reads the live markers through a `markersRef`, so an assistant reply streaming token-by-token — which recreates the `items`/`markers` arrays on every tick without changing any user-message key — does NOT re-run the O(marker) `getBoundingClientRect` scan or churn the listener on each token; the scan runs only on real scroll events and genuine marker-set changes. `getCurrentMarkerKey` reads true on-screen `getBoundingClientRect().top` values, so it stays correct under ChatContainer's `column-reverse` layout where DOM order is reversed. The listener is read-only and passive (it never writes scroll) and is NOT a `ResizeObserver`, so it does not interfere with the auto-scroll stabilization observer. The `.is-active` marker is styled as a bold near-black bar in the light baseline and inherits dark-mode contrast through the tokenized chat chrome, not the old blue. Widths are applied inline; CSS intentionally does NOT transition `width` (transitioning it made the wave lag a few frames behind the cursor) and only transitions `height`/`background`/`opacity` plus the `.is-active` crest color, so pointer tracking is 1:1 and there is no CSS specificity contest.

### Conversation Find
`FindBar` is mounted by `ChatContainer` but owns its own open/close state so the already-large container does not accumulate more scattered local state. The search scope is only `.chat-message-flow-reverse`; do not use Electron `webContents.findInPage` or preload IPC for this feature. `useConversationFind` creates `Range` objects from text nodes and registers them with CSS Custom Highlight, which keeps React-owned message DOM untouched. Match counters use the user's visual order: `1/N` is the oldest/top match, `N/N` is the newest/bottom match, and a new query starts on `N/N`. Session switches close and clear the bar, while streaming DOM mutations refresh existing highlights without forcing latest-scroll behavior.

### Session Switching
`ChatView` and `ChatViewContent` treat session switching as an explicit transient UI state. While a route-targeted `chatSessionId` is active but its cache snapshot is not ready yet, the message list is replaced with a neutral "Opening chat history..." placeholder and the composer is locked. `ChatContainer` is keyed by `currentChatSessionId` so it fully unmounts and remounts on every session switch; this guarantees all refs, observers, event listeners, and internal state are released — preventing DOM node leaks from stale closures or observer bindings that would otherwise retain detached DOM subtrees across sessions (#767).

### Interactive Requests
Interactive requests are chat-session-native. Pending requests are rendered inline in the timeline via `InteractiveRequestCard` and are dismissed from the UI after submission or resolution. Approval requests auto-submit as soon as every item has an approve/reject decision. Choice requests and form select-like controls render as responsive wrapped option grids with an `Other` fallback card for custom text input. Choice submissions keep preset selections separate from custom values (`selectedPresetValues` and `customValues`) while still sending merged `selectedValues` for compatibility; do not collapse them, because server-side approval gates need to reject custom text that happens to equal a privileged option value.

### User Message Editing
Inline user-message editing is managed via `editMessageAtom`. `ChatContainer` renders an inline `ChatInput` in edit mode for the message being edited. The edit confirmation dialog is owned by `AppLayout` via a window-event bridge; its suppression preference is persisted in `profile.json` under `confirmationSettings.inlineEditRegenerate.skipConfirmation`.

### Sidebar and Editor
The agent sidebar (`agent-area/`) is a sibling panel in `AgentPage`, not a child of `ChatView`. The agent editor (`agent-editor/`) appears when navigating to `/agent/chat/:chatId/settings/*`. Its route entry stays intentionally thin: `useAgentChatEditingViewModel` owns route-derived tab state and save orchestration, `agentChatEditingViewModel.ts` owns pure data mapping/update helpers, and `AgentChatEditingLayout` owns rendering. Schedule creation lives in `Schedules`: `AgentSchedulesTab` opens `AddScheduleOverlay` for local scheduled jobs. Scheduled chat sessions live in the dedicated `SchedulesSidepane` (accessed via `ChatSide`); conversation search excludes scheduled sessions.

### Workspace Deliverables
`WorkspaceExplorerSidepane`, `workspaceSearchService.quickSearchFiles`, `chat-input/context-menu.atom.ts` chat-session file search, and mention-asset URL resolution all render current session deliverables from the chat-owned workspace (`currentChat.workspace`). The legacy `agent.workspace` fallback is compatibility-only for pre-migration data. "Agent Knowledge Files" still come from the resolved agent's `knowledge.knowledgeBase`. `useFileExplorerSort` owns the sort cycle and keeps directories grouped before files. Modified-time sorting requires `includeMetadata` on the legacy workspace IPC calls so main process handlers attach `mtime` to returned file tree nodes only when callers need it.

## Anti-Patterns
- **Reading `useMessages()` inside `ChatContainer`**: causes session-switch stale renders. Message list must be owned by `ChatViewContent` and passed as props.
- **Driving scroll resets from `chatId`**: history switches can swap sessions under the same chat identity. Always key scroll resets to `chatSessionId`.
- **Async sidepane loads without a generation guard**: `MemexMemorySidepane`'s `loadCards` is keyed by `useCurrentChatId()`; a slow load for a previous agent can resolve *after* a faster newer one and overwrite the correct list (seen switching from a card-heavy agent to a brand-new empty one — the old cards stuck around). Every async list load must claim a monotonic `loadSeqRef` ticket and drop its result if superseded, and a `chatId`-keyed effect must clear the list immediately on switch (mirror the detail view's `cancelled` guard). Do not rely on `key={chatId}` — the pane is not remounted on switch.
- **Treating `null`/`undefined` chatStatus as idle**: reopens the race where the composer fires before session state hydrates.
- **Showing zero-state before session cache is ready**: use the "Opening chat history…" placeholder gate in `ChatViewContent`.
- **Adding streaming logic to `Message.tsx`**: `Message.tsx` is for completed messages only. In-flight state belongs in `StreamingV2Message`.
- **Growing legacy oversized renderer components**: `InlineFilePreviewPanel.tsx`, `workspace/FileExplorerSection.tsx`, and `StreamingV2Message.tsx` are known legacy exceptions above the 500-line threshold. Do not add substantial behavior directly to them; keep changes as thin data/adapter wiring or extract to focused components/hooks first.
- **Writing workspace onto agent updates**: post-separation workspace belongs to `ChatConfig.workspace`; agent configs own knowledge. Agent editor helpers must delete `updateData.workspace` before calling `updateChatAgent`, and workspace changes must be sent separately through `updateChat`.
- **Adding render-item logic to `ChatContainer`**: item type definition and rendering dispatch belong in `ChatRenderItem.tsx`.
- **Importing `mermaid` directly in chat files**: `MermaidDiagram` is a lazy async webpack chunk; a synchronous import breaks code splitting.
- **Rendering `ToolCallsSection` outside the main timeline without overriding its message source**: it reads `useMessages()` (the global current session), so a sub-agent / preview host must supply `ToolCallsMessagesContext` *and* a real `chatStatus`, otherwise the status icon is permanently the alert/`interrupted` icon.
- **Bypassing `installAndActivateSkill` for new skill flows**: all install paths must funnel through the single authoritative entry point.

## Verification Steps
After modifying components in this directory:
1. Send a message and confirm streaming renders progressively (no flash to completed state).
2. Switch chat sessions mid-stream and verify the previous session's messages are not briefly shown.
3. Trigger an `approval` interactive request and confirm it auto-submits once every item is decided.
4. Open an agent with a workspace; confirm `@`-mention context menu populates file results.
5. Attach an image and an Office file; confirm both appear in the composer preview and are included in the sent message payload.
6. For tool call changes: expand the tool call accordion and verify the correct view renders with no console errors.
7. Run `npm test` — the `__tests__/` suite covers interactive request card behavior and message rendering edge cases.

## Gotchas

- `ChatInput.tsx` is large (~920 LOC). Read and understand the full component structure before making localized edits — state is densely threaded.
- `StreamingV2Message` (in `src/renderer/components/streaming/`) handles in-flight messages; `Message.tsx` only renders completed messages. Do not add streaming-specific logic to `Message.tsx`.
- `<IMAGE_REGISTRY>` image URLs are not always web URLs. Assistant messages register locally-saved deliverables (e.g. screenshots) using the agent prompt's mention schemes (`@chat-session:`, `@knowledge-base:`, `@workspace:`). `Message.tsx` `parseNewFormatMessage` resolves these to encoded `file://` URLs at registry-build time via `resolveMentionAssetUrl` (`src/renderer/lib/chat/mentionAssetUrl.ts`), so every downstream consumer (`cacheImage`, gallery, viewer) inherits the resolved URL from one touch-point. The image pipeline only understands `http(s)://`, `file://` and absolute paths — an unresolved mention URL falls through to `fetch()` and renders as "Image failed to load".
- Tool result messages are not always final. A `tool` message with `streamingComplete === false` is an in-progress snapshot and should still render as executing.
- `ToolCallsSection` resolves tool results **and** its overall status from `useMessages()` — the *current main chat session* cache — not from props. Reused outside the main timeline (e.g. the Sub-Agent Tasks sidepane via `SubAgentTaskDetailView`) it would never find the sub-agent's tool results, so every section degraded to the `interrupted` (alert) icon. The host must (1) wrap the rendered items in `<ToolCallsMessagesContext.Provider value={subAgentMessages}>` so result lookup and `computeToolCallsSectionStatus` run against the correct conversation (the same array passed to `useRenderItems`, so `sourceMessageIndex` math stays consistent), and (2) pass a real `chatStatus` — map the sub-agent run state (`running → 'sending_response'`, else `'idle'`). Passing `chatStatus={undefined}` collapses status to `interrupted` via the `!chatStatus` branch, defeating the icon entirely.
- Interactive auth cards are intentionally ephemeral. Once the command ends, times out, or the user cancels it, the timeline card should disappear.
- `ChatContainer` is not the source of truth for session messages. Message selection lives in `ChatViewContent` (or replay state); the active list is passed down as props.
- Session switching is not the same as an empty chat. Do not show empty-state or zero-state UI until the target session cache is ready.
- `ChatInput` send availability must be based on explicit `chatStatus === 'idle'`. Treating missing status as idle reopens a race where the composer can submit before the session state hydrates.
- `ChatInput` compose draft hydration must sync both `chatSessionInputDraftManager` and `profileDataManager.currentEditingPrompt`; otherwise prompt-history Down can revive another session's draft. Prompt-history Up/Down selections should update the visible per-session draft without calling `setCurrentEditingPrompt`, because resetting the prompt cursor would break multi-step history navigation.
- Inline edit submission failures are recoverable chat errors. If `onSubmitEditedMessage` rejects, capture the message in the chat-session cache so `ErrorBar` can render it.
- Timeline auto-scroll is not driven solely by message-count changes. If a pending interactive request or similar non-message timeline item is inserted, `ChatContainer` still needs an explicit latest-scroll trigger.
- The scheduled-run "..." menu is the shared `ChatSessionDropdownMenu`, which has no React access to `SchedulesSidepane` state. The sidepane passes per-run state by writing to the trigger element's `dataset` in the more-button `onClick` (e.g. `dataset.chatSessionMenuSource = 'schedule'`, `dataset.scheduleRunning = isExecuting ? 'true' : 'false'`, `dataset.scheduleRetryable = isFailed || isInterrupted ? 'true' : 'false'`, `dataset.scheduleJobId = session.schedulerJobId || ''`); `toggle()` reads those back into the menu atom. The **Cancel** item is gated on `isScheduleMenu && scheduleRunning` and the **Retry** item on `isScheduleMenu && scheduleRetryable`; both must stay in sync with the sidepane's own `getScheduledSessionDisplayState(session)` checks — Cancel mirrors `'running'`, Retry mirrors `'failed' || 'interrupted'` (a cancelled run renders as `interrupted`). If you add a new run state, update both sides. The **Copy File Path** item is the *same* item the default chat menu renders — it is gated only on `!!alias && !!chatId` (not on `isScheduleMenu`), so it shows in both menus and resolves the scheduled run's persisted file with the same `chatId` (the sidepane's `currentChatId`) and `sessionId` the **Download** item already uses. `dataset` values are always strings, so compare with `=== 'true'` and coerce the jobId with `|| null`.
- Chat sidepane list cards historically used inline `background: var(--color-white)` plus imperative hover handlers that write light colors back to the DOM. Any list item in Agent Memory, Scheduled runs, or Sub-Agent Tasks must carry the shared `sidepane-list-card` class so dark-mode CSS can override those inline styles consistently; do not add a one-off card class that bypasses the shared hook.
- ChatInput action icons must inherit `currentColor`. Custom SVGs that use masked `<rect fill="...">` values can stay dark on dark buttons even when the button token is correct; keep the dark-mode rect override or make new icon internals token/currentColor-driven.
- Agent editor tab routes use nested React Router `<Outlet>` — adding a tab requires touching both the component tree and `AppRoutes.tsx`.
- `useAgentChatEditingViewModel` treats the **route as the single source of truth** for `tabState.activeTab`: one effect syncs `activeTab = currentRouteTab`. Any other place that needs to change the active tab (including the name-validation "force back to Basic" redirect) must do it by `navigate(...)`-ing to the target route, never by calling `setTabState({ activeTab })` directly. Two effects both writing `activeTab` toward different targets infinite-loop: the route-sync effect forces `currentRouteTab` while the validation effect forced `'basic'`, so on a non-basic route with a failing name validation they oscillated forever ("Maximum update depth exceeded"). Reachable by typing a duplicate name on Basic then switching tabs, or deep-linking to a non-basic tab for an agent whose stored name already duplicates another.
- Mermaid diagrams are lazy-loaded as an async webpack chunk; avoid importing `mermaid` directly in synchronously loaded chat files.
- The four singleton sidepanes (Sub-Agent Tasks, Schedules, Workspace Explorer, Memex Memory) are mutually exclusive, but exclusion is enforced **per-action, not centrally**. Any NEW action in `chat-side.atom.ts` that makes a singleton visible must hide the other three first (copy the `effectiveToggle` set). Bare setters like `SubAgentTasks.show` once skipped this and let two panes show at once — every visible-making path now closes its siblings.
